# API-ключи и Admin API

Меню пользователя «Профиль» открывает `#/settings`. Вкладка «API ключи» — `#/settings/keys`. Кнопка «Документация» на этой вкладке открывает встроенную страницу `#/settings/docs`.

На вкладке профиля карточка «Компания» задаёт название (до 64 символов) и логотип — data-URL картинки до 200 КБ в интерфейсе. По умолчанию название и логотип пустые: блок бренда в шапке и на экране входа скрыт, меню начинается от левого края, заголовок вкладки — `TDS`. Значения видны в шапке админки и на экране входа у всех. Сохранение идёт в `PUT /api/ui` вместе с остальными настройками интерфейса. Тема, язык и период по-прежнему хранятся только в браузере.

«Создать новый ключ» спрашивает название и доступы. Название обязательно и не длиннее 64 символов. Доступ — `admin`, `engine` или оба. В окне «Admin API» включён сразу, «Движок» выключен. Пустой набор доступов не сохраняется.

Сырой ключ — `kz_` и 40 шестнадцатеричных знаков, всего 43 символа. В ответе `POST /api/api-keys` поле `key` приходит один раз, вместе с записью `item`. После закрытия окна сырой ключ нигде не хранится. В списке у названия стоит точка состояния: зелёная — активен, красная — отозван, с датой отзыва под именем. Столбец «API ключ» показывает `kz_` и первые 8 знаков секрета с многоточием и кнопку копирования этого префикса; полный ключ из таблицы не достать. Дальше доступы («Admin API», «Движок») и время создания. Кнопка «⋯» сразу после названия открывает меню: у активного — «Перевыпустить», «Изменить», «Отозвать»; у отозванного — «Удалить». В файле лежит sha256 сырого ключа, не сам ключ. Ответ списка хеш не отдаёт.

Отзыв ставит время в `revoked_at` и оставляет запись. Повторный отзыв того же id отвечает `404`. Админка перестаёт принимать отозванный ключ сразу после записи файла. Движок перечитывает тот же файл по тикеру `KUZTDS_RELOAD_INTERVAL`. Пустое или неположительное значение интервала для наблюдателя ключей становится одной минутой. Файл читается заново, когда изменились время модификации или размер. До этого тика режим `?api=` ещё принимает отозванный ключ. Ошибка чтения оставляет прежний набор.

Перевыпуск — `POST /api/api-keys/{id}/rotate`: тот же id, имя, доступы и время создания, новые префикс и хеш; ответ `200` с `{key, item}`, сырой ключ приходит один раз. Старый секрет админка отклоняет сразу, движок — после перечитывания файла, не позже чем через минуту. Отозванный ключ не перевыпускается — `409`. Правка — `PUT /api/api-keys/{id}` с телом `{"name","scopes"}` и теми же правилами, что при создании; секрет не меняется; отозванный — `409`. Удаление записи — `DELETE /api/api-keys/{id}?hard=1`: только для уже отозванного ключа, ответ `204`, запись исчезает из файла; активный ключ — `409`, неизвестный id — `404`. `DELETE` без `hard` остаётся отзывом. Ошибки валидации отвечают `400` с текстом, сбой генерации или записи файла — `500`.

Файл задаёт `KUZTDS_API_KEYS_FILE`. Путь пустой — ключи выключены, заголовок `Api-Key` админка не принимает, создание отвечает `503`. Отсутствующий файл — пустой набор, это не ошибка. `KUZTDS_API_KEY` в файл не пишется и админку не открывает. Для `?api=` движка он подходит рядом с файловыми ключами доступа `engine`.

## Заголовок и что ключу закрыто

Запрос к админке передаёт `Api-Key: kz_...`. Кука сессии и `X-CSRF-Token` для этого запроса не нужны. Непустой заголовок — единственный способ входа: при неверном ключе кука не проверяется. Нужен доступ `admin`. Нет доступа, ключ отозван или неизвестен — `401`.

Ключ не открывает:

- `GET`, `POST /api/api-keys`, `POST /api/api-keys/{id}/rotate`, `PUT` и `DELETE /api/api-keys/{id}` — список, создание, перевыпуск, правка, отзыв и удаление
- `GET`, `PUT /api/ui` — настройки интерфейса на сервере
- `POST /api/password` — смена пароля
- `GET /api/me` — текущая сессия
- `POST /api/logout` — выход
- `POST /api/login` — вход по паролю и установка куки

Управление ключами, пароль, `me`, UI и выход при заголовке `Api-Key` отвечают `403`. Вход по паролю заголовок ключа не читает.

## Текущая сессия (`GET /api/me`)

Только кука, без `Api-Key`. Ответ `200`:

```json
{
  "user": "логин",
  "uid": "id из users.json",
  "type": "ADMIN или USER",
  "csrf": "…",
  "engine": "база ссылок движка",
  "prefs": { "lang": "", "tz": "" },
  "pages": ["dashboard", "flows", "…"],
  "access": { "sections": [], "grants": {}, "hidden": [] }
}
```

У администратора окружения (кука без `uid`) поле `uid` пустое, `type` — `ADMIN`, `pages` — все разделы, `access` нет. У записи `ADMIN` в `users.json` — полный список `pages`, `access` не отдаётся. У `USER` в `access` — сохранённые разделы, гранты и скрытые метрики; `pages` совпадает с видимыми пунктами меню.

## Пользователи (`/api/users`)

Только кука. Раздел `users` в access (тип `ADMIN` в файле или администратор окружения). API-ключ — `403 cookie session required`.

| Метод | Путь | Тело | Успех | Ошибки |
| --- | --- | --- | --- | --- |
| GET | `/api/users` | — | `200`, массив без `hash`; первая строка — администратор окружения (`id` пустой, `source: env`), далее записи файла с `source: file` | при выключенном файле — `200` и только строка администратора окружения |
| POST | `/api/users` | `login`, `password`, `type`, `enabled`, `prefs`, `access` | `201`, запись | `400` валидация; `409` логин занят или зарезервирован; `503` users disabled |
| GET | `/api/users/{id}` | — | `200` | `404` |
| PUT | `/api/users/{id}` | `login`, `type`, `enabled`, `prefs` (частично) | `200` | `400`; `404`; `409` last administrator, себя выключить, логин |
| DELETE | `/api/users/{id}` | — | `204` | `404`; `409` last administrator, себя |
| PUT | `/api/users/{id}/password` | `{"password"}` | `204` | `400` короткий пароль; `404` |
| PUT | `/api/users/{id}/access` | объект `access` целиком | `200`, `access_source: manual` | `400` секция/ресурс/mode; `404` |

Пустой `type` при создании — `USER`. Пароль можно не передавать; пустой пароль в `PUT …/password` снимает вход. Администратор окружения не имеет `id`, маршруты `/api/users/{id}` к нему не применимы (`404`); пароль — `POST /api/password` под своей сессией.

## Ограничения для USER

Без раздела или вне гранта: `403 forbidden` на защищённый маршрут. Невидимая запись каталога или кампания — `404 not found` на GET/PUT/DELETE по id. Статистика и журналы с `f=` по скрытой money-метрике — `400`. Все `/api/spend` при `hidden: cost` — `403`. Подробности — [Пользователи панели](users.md).

## Настройки интерфейса (`/api/ui`, `/api/brand`)

Файл задаёт переменная `KUZTDS_UI_FILE`. По умолчанию `ui.json` лежит рядом с `groups.json` в каталоге состояния админки.

`GET /api/ui` — только сессия. Тело: `{ "cols": { "ключ": [{ "id", "on" }] }, "dash": { "panels", "dim" }, "company": { "name", "logo" } }`. Если путь к файлу не задан, ответ — значения по умолчанию с `200`. Ошибка чтения файла — `500`.

`PUT /api/ui` — сессия и заголовок `X-CSRF-Token`. Тело того же вида. Валидация (`ui.go`): ключи `cols` — `[a-z][a-z0-9_]{0,31}`, не больше 32 групп; в группе не больше 200 столбцов, id обязателен, не длиннее 64 символов, без дубликатов; `dash.panels` — не больше 64 строк по 64 символа; `dash.dim` — не длиннее 64 символов; `company.name` — после trim не длиннее 64, пустое остаётся пустым; `company.logo` — пустой или data-URL `image/png|jpeg|gif|webp|svg+xml` в base64, не длиннее 280 000 байт. Нарушение — `400` с текстом ошибки, `bad json` при невалидном JSON. Без настроенного пути к файлу — `503` «ui file not configured». Без сессии — `401`.

`GET /api/brand` — без сессии. Ответ `{ "name", "logo" }`, заголовок `Cache-Control: no-store`. Столбцы и панели не отдаются. Нужен экрану входа и шапке до авторизации.

## Кампании (`/api/groups`)

`GET /api/groups` по-прежнему отдаёт массив кампаний. `PUT /api/groups` по-прежнему принимает массив целиком и отвечает `200` `{"status":"saved"}`.

`PUT /api/groups/{id}` записывает одну кампанию: строка с этим id заменяется, если её не было — добавляется. Тело — один объект, не больше 8 МБ. Пустой `id` в теле берётся из пути. Непустой `id`, отличный от пути, отвечает `400` `id mismatch`. Успех — `200` `{"status":"saved"}`.

`DELETE /api/groups/{id}` снимает кампанию. Нет такого id — `404` `not found`. Успех — `200` `{"status":"deleted"}`.

Запись и удаление требуют раздел `flows`. Нет хранилища кампаний — `503`.

Ответы админки сжимаются gzip, если в `Accept-Encoding` есть `gzip` и это не переход протокола (`Upgrade` или `Connection: upgrade`). В ответе тогда `Content-Encoding: gzip`, добавляется `Vary: Accept-Encoding`, `Content-Length` снимается. Ответ без тела уходит без `Content-Encoding`.

`GET /api/lookup?ip=` (раздел `tools`) отдаёт объект `visitor`. В нём поле `proxy`: адрес есть в `ip_proxy` либо организация совпала с `proxy_org`. Негодный адрес — `400`.

`POST /api/simulate` (тот же раздел) в ответе тоже кладёт `proxy` в `visitor`. Правила потока, включая `proxy` и `ip_version`, проверяются. Детекция ботов не запускается.

`groups.json` пишется одним компактным JSON, без отступов. Пустые необязательные поля не пишутся. Поле `status` у кампании и у потока пишется всегда.

В правилах потока `proxy` и `ip_version` устроены как `unique` и `bot`: `0` — выключено. У `proxy` значение `1` — только прокси, `2` — только не прокси. У `ip_version` значение `1` — только IPv4, `2` — только IPv6 ([правила потока](router-rules.md)). У потока поле `filter_or`: истина значит «любое из этих условий». В блоке `bots` поля `ch_proxy` и `ch_non_mobile`; оба по умолчанию выключены и в файл не пишутся, пока ложь. Смысл проверок — [защита от ботов](bot-protection.md).

## Режим `?api=`

Движок принимает параметр `api`: JSON в обычном или URL-safe base64. Внутри поле `key_api`. Его принимает ключ с доступом `engine` или значение `KUZTDS_API_KEY`. Неверный ключ — `403`. Остальные поля: `id` (кампания), `ip`, `referer`, `useragent`, `se`, `lang`, `uniq` (`yes` — уникальный визит), `key`, `domain`, `page`, `cf_country`, `pars` (массив строк). Запрос идёт на домен ссылок движка, не на адрес админки. Заголовок `X-Requested-With` в этом режиме в клик не пишется.

## Примеры

В примерах секрет — плейсхолдер `kz_...`. Адрес админки подставьте свой.

```bash
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/groups"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/logs?from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&limit=100&offset=0&f=country:eq:PL"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/postbacks?from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&limit=200&offset=0&f=status:eq:sale"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/log-fields"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/log-values?table=events&field=country&from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/report?from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&f=country:eq:PL"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/stats/breakdown?dim=country&limit=6&from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&f=device:eq:mobile"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/stats/summary?from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&f=country:eq:PL"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/stats/performance?from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&f=device:eq:phone"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/stats/facts?from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&f=country:eq:PL"
curl -H "Api-Key: kz_..." "http://127.0.0.1:8090/api/logs/export?from=2026-10-01T00:00:00Z&to=2026-10-16T00:00:00Z&f=country:eq:PL"
```

Кратко по адресам. Кампании — в разделе выше: `GET /api/groups` массивом, `PUT /api/groups` массивом, одна запись — `PUT` и `DELETE /api/groups/{id}`. Каталоги: список `GET` и `POST`, запись `GET`, `PUT`, `DELETE` на `/{id}`. Офферы `/api/offers`, сети `/api/affiliate-networks`, лендинги `/api/landings`, источники `/api/traffic-sources`. Домены: `GET` и `POST /api/domains`, запись на `/api/domains/{id}`, проверка `POST /api/domains/{id}/check` (подробно — в [офферах и лендингах](offers-landings.md)). Журналы и срез — в примерах выше. Фильтры `f=` описаны в [фильтрах и столбцах журналов](log-filters.md). `GET /api/stats/summary`, `GET /api/stats/timeseries`, `GET /api/stats/performance` и `GET /api/stats/facts` принимают `from`, `to` и повторяемый `f=` по кликам. У ряда timeseries параметр `step` в секундах и не меньше 3600. В точке timeseries поле `cost` — центы клика по коду валюты. `GET /api/stats/performance` в строке несёт `cost` так же; конверсия с `group_id` стыкуется по нему, строка без `group_id` (старые postbacks) — по имени кампании. `GET /api/stats/facts` в клике отдаёт `cost_cents` и `cost_cur`: одна связка ключей может повториться для разных валют. `GET /api/postbacks` отдаёт `rows`, `total` (сумма profit) и `count` (сколько строк подошло под фильтр, не размер страницы). `GET /api/spend` фильтр `f=` не принимает. `GET /api/cron` отдаёт `telegram_configured`, `config_error` (текст проверки конфига, без секретов) и `geo_paths.city_file` / `geo_paths.asn_file`.

Создание ключа доступно только сессии браузера:

```bash
curl -H "Content-Type: application/json" -H "X-CSRF-Token: ..." -b "сессия" \
  -d "{\"name\":\"кабинет\",\"scopes\":[\"admin\",\"engine\"]}" \
  http://127.0.0.1:8090/api/api-keys
```

Тот же набор с заголовком `Api-Key` эти адреса не открывает. Полный текст с примерами режима `?api=` лежит на `#/settings/docs`.

## Статика `/assets/`

`GET /assets/{путь}` — без сессии и без `Api-Key`. Файлы встроены в бинарник админки из `internal/admin/web/vendor` (`//go:embed`). Ответ с `Cache-Control: public, max-age=86400`. Пустой путь, путь с завершающим `/`, каталог и неизвестный файл — `404`; листинг каталогов не отдаётся.

Сейчас в vendor лежит **Ace** (сборка ace-builds **1.44.0**, вариант src-min-noconflict; источник указан в `internal/admin/web/vendor/ace/VERSION`). Лицензия — **BSD-3-Clause** (`LICENSE` в том же каталоге). SPA запрашивает `/assets/ace/ace.js` и `ext-language_tools.js` только при открытии редактора кода (файлы лендинга или HTML-страница потока `@page:`).

Обновление: заменить файлы в `internal/admin/web/vendor` (для Ace — каталог `ace/` и строка в `VERSION`), пересобрать образ админки и пересоздать контейнер `admin`.
