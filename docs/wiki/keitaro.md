# Перенос из Keitaro

Перенос живёт на странице «Интеграции» (`#/integrations`): пункт «Интеграции» в меню пользователя. Маршрут `#/keitaro` открывает ту же страницу. Блок Keitaro читает конфигурацию и журналы трекера и пишет их в локальные каталоги, кампании и ClickHouse. На Keitaro уходят только запросы чтения.

## Настройка

Адрес трекера и API-токен задаются на странице «Интеграции» в карточке «Подключение». Сервер хранит их в файле `keitaro.json` рядом с `keitaro-import.json` (`EMTDS_KEITARO_FILE`, по умолчанию каталог состояния) с правами 0600. Токен в ответах API и в интерфейсе не показывается: поле остаётся пустым, а при сохранённом токене в нём подсказка «сохранён». Пустое поле или маска `***` при сохранении оставляют прежний токен, но только пока хост адреса тот же: при смене хоста нужен новый токен (400 `api_key required for new host`), прежний на другой сервер не переносится.

Источник значений определяет админка. Если `keitaro.json` есть, берётся он. Иначе используются переменные окружения `KEITARO_BASE_URL` и `KEITARO_API_KEY`. Экран показывает источник: `file`, `env` или `none`. Адрес из окружения проходит те же правила, что и при сохранении: логин, query и фрагмент не допускаются. Если адрес из окружения неверен, пара считается не заданной (`none`), а в лог пишется причина без самого адреса. Файл не сбрасывается к окружению, а испорченный файл не даёт админке стартовать, чтобы сохранённая правка не отменялась молча. Без `EMTDS_GROUPS_FILE` путь файла не задан, и сохранение отвечает 503. Cron и движок файл не читают.

Адрес — только `http` или `https`, с хостом, без логина, query и фрагмента. Хвостовой `/` убирается, хост приводится к нижнему регистру. Ответ GET показывает только очищенный адрес: логин и query наружу не выходят. Внутренние адреса не блокируются: трекер может стоять во внутренней сети.

Сохранение отвечает 409 в двух случаях:

- идёт перенос или стирание (`import already running`, `purge already running`);
- хост адреса меняется, а в манифесте переноса записан другой хост или хост не записан вовсе (`manifest_host`). Хосты сравниваются без учёта регистра. Сначала нажимают «Удалить импортированное»: иначе стирание по хосту манифеста не найдёт строки нового трекера. Смена токена на том же хосте разрешена всегда.

Хост пишется в манифест и в колонку `domain` строчными буквами. Стирание удаляет строки хранилища под хостом так, как он записан в манифесте, поэтому уже перенесённые данные находятся и при другом регистре в старом манифесте.

Когда адрес и токен заданы, виден хост и кнопка «Проверить соединение». Кнопка не скачивает список кампаний (около 26 МБ на 9950 кампаний). Ключ проверяет страница из одной кампании `GET /admin_api/v1/campaigns?limit=1&offset=0` (около 1,5 КБ). Число кампаний находится поиском по смещению: те же страницы по одной кампании, пачками до 8 запросов параллельно, сначала смещения +10, +100, … до первого пустого, затем промежуток между последним смещением с кампанией и первым пустым сужается; число кампаний равно первому пустому смещению. Холодная проверка — около 40 запросов и около 60 КБ (на 9950 кампаний 2,5–4 с против 6 с и 26 МБ). Keitaro отвечает на запросы по очереди, поэтому широкие пачки не ускоряют поиск. Админка помнит последнее найденное число для адреса трекера в памяти: следующая проверка шлёт три запроса (смещение 0 и два соседних с запомненным числом) и занимает около 0,4 с; если число изменилось, поиск идёт заново. Если Keitaro игнорирует `limit` и первый ответ длиннее одной кампании, его длина и есть число. Отказ ключа (401) останавливает проверку после первого запроса. Больше 1 000 000 кампаний — ошибка. Успех пишет «Соединение есть, кампаний:» и открывает форму. Если перенос уже идёт или уже есть результат, форма видна и без новой проверки.

Задача переноса и стирание берут адрес и токен один раз при старте. Все этапы, маска токена в потерях и ошибках и хост в манифесте идут из этой копии. Смена настроек во время работы невозможна, а следующий запуск возьмёт новые.

## Что переносится

Галочки по умолчанию включены: домены, партнёрские сети, офферы, лендинги, источники, кампании с настройками. Конверсии, клики и пользователи выключены, пока их не отметить.

Префиксов нет. Id каталога — числовой id Keitaro строкой: оффер «796», лендинг «1», сеть «12», источник «3», домен «47». Домен получает роль links и хост из имени домена Keitaro. Снимок запрашивает группы доменов Keitaro (`groups?type=domains`). Непустая группа из Keitaro заменяет локальную у того же id; пустая оставляет локальную. Чтобы перенести только домены без кликов и конверсий, оставьте включённой только галочку «Домены». Если `offer_param` целиком подходит под токен каталога, он пишется в `offer_param`, иначе в `offer_query` без ведущих `?` и `&`. Адрес postback сети копируется, когда это http или https. У источника остаются keyword и `sub_id_1`…`sub_id_15`. Самый частый исходящий постбек кампаний уходит в общий каталог `s2s.json`, а у кампаний остаётся его id в `postback_ids`; правила выбора — в [postbacks](postbacks.md).

Имя кампании — как в Keitaro. Id кампании равен alias. Пустой alias даёт id `missing-alias-N` и выключает кампанию. Занятый alias даёт `{alias}-dup-N`, N — id кампании Keitaro, и тоже выключает её. Имя потока — имя потока Keitaro. Пустое имя становится `stream N`. В comment потока остаётся `keitaro_stream_id=N`. Подпись группы — имя группы Keitaro, не длиннее 64 символов. Номер кампании `num` равен id кампании Keitaro. Если этот номер уже стоит у локальной кампании, которой нет в манифесте, выдаётся следующий номер после текущего максимума и пишется потеря «номер N занят, выдан M».

Кампания типа weight остаётся включённой, у неё включён вес. Доли офферов и лендингов в потоке — числовые id и `share`.

Локальный лендинг, в типе или действии которого есть local или php, попадает в каталог с `local: true` и пустым url. Поток с ним остаётся включённым: выход `redirect: landing`, доли в `landings`, офферы потока в `offers`. На этапе `landing_files` админка скачивает архив `GET /admin_api/v1/landing_pages/{id}/download` и распаковывает его в `<EMTDS_LANDINGS_DIR>/{id}/`. Точка входа `entry` — `index.php`, иначе `index.html`, иначе первый файл `.php` или `.html` в корне. Она пишется в `landings.json`. Неудача скачивания или распаковки — потеря «архив не скачан». Поток из-за этого не выключается.

## Соответствие фильтров и действий

`filter_or` остаётся одним потоком: флаг копируется, и поток подходит, если прошло любое одно условие. Поток Bot Protection с режимом «или» переносится так же: один поток с `filter_or`, в него входят `proxy` и `ipv_6` / `ip_version`. Эти фильтры не отбрасываются. Без флага условия должны выполниться вместе. Режим reject, blacklist, deny и exclude — исключение, остальное — совпадение.

Фильтр, который после переноса ничего не ограничивает (пустой список, пустой payload), не переносится: потеря `skipped` и запись в заметке потока. Если у потока не осталось ни одного условия, поток выключается, а не ловит весь трафик. Поток без фильтров в самом Keitaro переносится как есть и ловит всех, как и там.

Потоки идут в порядке Keitaro: сначала forced, потом regular, потом default, внутри — по позиции. Bot Protection — первый forced-поток: при `filter_or` в него попадает бот, а также посетитель, прошедший любое другое условие (например, desktop при device_type reject mobile, tablet). Обычные потоки с bot reject получают правило «только люди», так что бот до них не доходит, даже если Bot Protection выключен.

| Keitaro | emtds |
| --- | --- |
| country | страна |
| device_type | computer, phone, tablet; единица отсекает тип |
| isp | организация, поиск подстрокой; потеря `approximated`: Keitaro сравнивает имя провайдера из своей базы ISP целиком, движок ищет его в организации из базы ASN, и названия в двух базах могут не совпасть (в GeoLite2-ASN у AS15169 организация `GOOGLE`, а не `Google LLC`) |
| ip | список IP, файл `ip-` и 12 hex sha1, суффикс `.dat` |
| device_model | правило `model`, точное совпадение |
| sub_id_1…sub_id_30 | правило `sub_ids` с ключом `sub_id_N`: точное совпадение или «содержит» |
| sub_id_31 и выше, parameter | `sub_id_31` и выше не переносятся; `parameter` — параметр URL (`get`) |
| user_agent | текст user agent |
| bot | условие «Бот» в «Когда»: accept → 1 «только боты», reject → 2 «только люди» |
| proxy | правило `proxy`: accept → 1 «только прокси», reject → 2 «только не прокси» |
| empty_referrer | правило `has_referer`: accept → 2 «Referer должен отсутствовать», reject → 1 «Referer обязателен» |
| uniqueness | правило `unique`: accept → 1 «только уникальные», reject → 2 «только повторные»; область `campaign` точная, `stream` и `global` — приближение |
| connection_type, operator, interval, limit, source, x_requested_with, search_engine, ad_campaign_id, creative_id, browser_version, os_version | не переносятся: потеря `skipped`, имя фильтра дописывается в заметку потока |
| ipv4, ipv_4 | правило `ip_version`: 1 «только IPv4»; reject → 2 |
| ipv6, ipv_6 | правило `ip_version`: 2 «только IPv6»; reject → 1 |
| ip_version | то же правило; версия из payload «4», «ipv4», «6», «ipv6» |

Фильтры-признаки `bot`, `proxy`, `empty_referrer` и `ipv_6` Keitaro шлёт с `payload: null`: смысл задаёт только режим IS (accept) или IS NOT (reject). Пустой payload у них значит «признак есть», а не «фильтра нет». Старая форма payload `["1"]` / `["0"]` читается как прежде. У `uniqueness` payload — область: `stream`, `campaign` или `global`; движок считает уникальность в кампании.

Пропущенный фильтр не теряется молча: в отчёте импорта строка `skipped`, а заметка потока получает хвост `; не перенесены фильтры Keitaro: имя, имя` после `keitaro_stream_id=N`. Поток остаётся включённым, если перенёсся хотя бы один фильтр. При «все условия» такой поток шире исходного, при `filter_or` — уже. Хвост строится из данных Keitaro, поэтому повторный импорт даёт ту же заметку.

У фильтра `ip_version` версия читается из payload без учёта регистра: «4», «ipv4», «ipv_4», «6», «ipv6», «ipv_6». Payload — строка, число или список из одного значения. Accept версии 4 даёт 1, версии 6 даёт 2. reject меняет эти два кода местами. Неизвестная версия не переносится. У `ipv4`, `ipv_4`, `ipv6` и `ipv_6` версия берётся из имени фильтра, payload на неё не влияет.

`sub_id_N` переносится как точное правило или как «содержит» (`contains: true`, подстрока без учёта регистра, см. [правила потока](router-rules.md)). Режим подстроки (`contains`, `substring`, `like`; `not_contains` даёт исключение) переносится как «содержит». Регулярка (значение `/…/` или режим `regex`) переносится как «содержит» только когда она по сути список литералов: `/Fonbet/`, `/Fonbet|Bovada/`, обычные символы и экранированные знаки (`\.`, `\-`). Флаг `i` не нужен, а без него в отчёт идёт потеря `approximated`: в Keitaro регулярка различала регистр, у нас нет. Классы, квантификаторы, якоря, группы, `\d`, пустая альтернатива и флаги кроме `i` не переносятся: фильтр пропускается, в отчёт идёт `skipped` «регулярное выражение слишком сложное для «содержит»». Движок регулярки на клике не исполняет. Чтобы подтянуть такое условие позже, достаточно прочитать исходное выражение из Keitaro и заменить его списком слов (`^Fonbet` → `Fonbet`, `(Fonbet|Bovada)` → два слова) в потоке вручную; второго движка регулярных выражений нет. Два фильтра одного ключа с разным способом сравнивания не склеиваются. Фильтр `device_model` движок сравнивает только точно: режим подстроки или регулярного выражения, значение вида `/regex/` и пустой список значений (`[]`, `""`, `null`) не переносятся: фильтр пропускается, в отчёт идёт потеря `skipped` с причиной. Пустой список значений `sub_id_N` тоже не переносится. Каждый перенесённый `device_model` получает потерю `approximated`: словарь моделей Keitaro отличается от токена User-Agent, поэтому совпадение возможно не у всех посетителей. Импорт не задаёт `empty` у `sub_ids`: смысл пустого Sub ID из Keitaro не переносится. Каждый `sub_id_N` занимает свой ключ в `sub_ids`, поэтому accept и reject разных Sub ID не смешиваются, а значение читается по параметру источника кампании. Два фильтра одного ключа или два `parameter` склеиваются, только когда смысл не меняется: два reject при «все условия» и два accept при `filter_or`. Иначе второй фильтр пропускается с потерей. Это относится только к новому импорту; уже импортированные потоки не пересчитываются.

Город, регион, язык, ОС, браузер, referer, keyword, пояс, день недели и уникальность тоже переносятся. Часы внутри дня отбрасываются. ASN оставляет только номера. Неизвестное имя пропускается. Если не перенёсся ни один именованный фильтр, поток выключается. Одинаковый список IP делит один файл. Негодный адрес из списка отбрасывается.

| Действие | emtds |
| --- | --- |
| http, redirect, location | http-редирект |
| show_html | HTML-страница |
| status404 без текста | 404 |
| status404 с HTML | «404 со своим HTML» |
| campaign | другая кампания, в цели её alias |
| неизвестный тип | действие stop, поток остаётся включённым |

Поток с именем Bot Protection или «Замыкающий» и действием `status404` переносится как «404 Not found», свой HTML не переносится.

Пустая цель campaign останавливает выход: целевая кампания не задана. Неизвестный id цели тоже даёт stop. Текст `show_page_html`, `show_html_404`, `show_text` и `javascript` длиннее 512 байт после замены макросов уходит в файл `page-` и 12 hex sha1 с суффиксом `.html`. В поле выхода пишется `@page:` и это имя. Одинаковый текст делит один файл. Текст до 512 байт остаётся в поле. Движок читает файл из каталога `EMTDS_PAGES_DIR` и подставляет тело вместо `@page:` до раскрытия макросов. В compose этот каталог — `/var/lib/emtds/pages` и у движка, и у админки.

При переносе известные макросы становятся метками emtds: `{subid}` → `[SUBID]`, `{country}` → `[COUNTRY]`, `{keyword}` → `[KEY]`, `{sub_id_1}`…`{sub_id_5}` → `[PAR-1]`…`[PAR-5]`. Уже стоящая в тексте метка `[CID]` записывается как `[SUBID]`. Другое имя в фигурных скобках остаётся. `[CID]` — прежнее имя `[SUBID]`: старые ссылки раскрываются так же. На клике `{имя}` из букв, цифр, `_` и `-` длиной до 24 символов берётся из GET-параметра с тем же именем. `{subid}`, `{country}`, `{keyword}`, `{status}`, `{payout}` и `{sub_id_1}`…`{sub_id_15}` из query не читаются.

Переименованный параметр кампании читается отдельно от этой общей замены. У `sub_id_1`…`sub_id_30` placeholder в адресе потока, оффера и лендинга становится `{sub_id_N}` уже после неё, поэтому сами `{sub_id_1}`…`{sub_id_5}` по-прежнему дают `[PAR-1]`…`[PAR-5]`. Placeholder keyword становится `[KEY]`. Имя во входящей ссылке — alias. Если alias пуст, а placeholder — макрос `{имя}`, берётся имя внутри скобок. Если placeholder — обычный текст, имя в ссылке — наше поле (`keyword`, `sub_id_N` и остальные), а сам текст пишется в токен как есть, без скобок и без замены на метку. Подпись без пробелов становится именем, только когда placeholder пуст и подпись не совпадает с нашим полем. Имя и токен пишутся в кампанию (`parameters`, `param_tokens`). Цена и валюта пишутся в `cost_param`, `cost_token`, `currency_param`, `currency_token`. Токен движок не раскрывает: он только попадает в ссылку кампании. То же имя пишется в параметр источника, только если этот слот ещё пуст; токена у источника нет. Имя, заданное источником, не затирается. Две кампании одного источника с разными входящими именами пустого слота оставляют первое, вторая попадает в отчёт как approximated. Если одним оффером или лендингом пользуются кампании, которым нужен разный адрес, запись каталога копируется, а поток второй кампании смотрит на копию. `site`, `ad_campaign_id`, `creative_id` и `external_id` дают только входящее имя: их placeholder в URL не заменяется. Пустой список параметров кампании ничего не меняет в адресах. Уже перенесённая кампания сама адреса не пересчитывает.

Уже перенесённые кампании добирают параметры отдельно: «Интеграции → Keitaro → Что переносить → Добрать параметры», или `POST /api/keitaro/import` с `parameters_only: true` и `all_imported: true`. Кнопка читает список кампаний и источники и заполняет только пустые имена и токены. Клики, конверсии и потоки не читаются и не перезаписываются. Параметр, который уже записан, остаётся, в том числе пустое имя, которым сбросили ключ источника. Повторный проход ничего не меняет. `dry_run: true` только считает, сколько кампаний изменилось бы. Подпись цены без alias и без placeholder в поля цены не пишется.

## Что не переносится

Локальный оффер не скачивается и не исполняется: поток выключается. Это оффер, в типе которого есть local, либо оффер с локальным путём и без http-адреса.

Офферы одного потока с одним URL склеиваются в первую ссылку, доли складываются. То же у лендингов. Пустой URL не склеивается.

## Пользователи

Галочка «Пользователи» на форме переноса. Нужны настроенный `users.json` (`EMTDS_USERS_FILE` или каталог групп) и доступ API Keitaro к списку пользователей. Ответ `403` на `GET /admin_api/v1/users` даёт потерю «нет доступа к /users», строки пользователей не переносятся.

Снимок читает пользователей вместе с каталогами. Этап `users` идёт после `groups`, если отмечены кампании, иначе после `catalogs`. Счётчик `users` в ходе задачи — число обработанных строк.

Keitaro `ADMIN` становится локальным `ADMIN` без грантов. Остальные — `USER` с `access.sections`, `grants` и `hidden` по правилам ниже. Новые записи создаются **выключенными**, без пароля и с `access_source: keitaro`. Пароль и включение задаёт администратор вручную.

Повторный импорт: запись с тем же `keitaro_id` и `access_source` `keitaro` или пустым обновляет тип, доступ и prefs. При `access_source: manual` строка не перезаписывается, в счётчик импорта всё равно попадает. Совпадение логина с другой записью — потеря «логин занят». Логин, совпадающий с `EMTDS_ADMIN_USER`, пропускается.

## Журналы

Галочки «Конверсии» и «Клики» читают журнал за период. Если отмечены обе, сначала импортируются клики, затем конверсии; пустые поля конверсий в том же запуске добираются из индекса кликов по `sub_id` (`importLogs` в `keitaro_logs.go`). «Текущий период» — период шапки админки. «За всё время» начинается в 2000-01-01 00:00 UTC и кончается текущим моментом; в запрос уходят календарные даты этих границ в поясе браузера. «Даты» — два дня `YYYY-MM-DD`. Сервер берёт день включительно, от полуночи до 23:59:59 UTC. Поля дат можно менять, когда отмечены клики или конверсии; в запрос они попадают, только если выбран пункт «Даты».

Клики пишутся в `events`, конверсии в `conversions`, пачками по 1000. В обеих таблицах `domain` — хост из `KEITARO_BASE_URL`. Поле `group_id` берётся из карты `campaigns` в `keitaro-import.json`: для каждой принятой при переносе кампании там хранится пара Keitaro `campaign_id` → id группы emtds. Карта и список id групп в манифесте дополняются на стадии `groups` до записи `groups.json`, только для кампаний, которые реально приняты (новая группа или замена по манифесту). У каждой группы в карте не больше одного `campaign_id`: при новой паре с тем же id группы старый `campaign_id` снимается. Кампания, чей id группы совпал с локальной записью без записи в манифесте, в карту не попадает — строки журнала для неё получают десятичный `campaign_id` Keitaro и учитываются в одной потере kind `approximated`, ref `log_campaign`. До стадии `groups` в манифест не попадают id из снимка маппера. При импорте только журналов карта читается из манифеста; смена alias на трекере не меняет уже сохранённый id группы. Пара из манифеста используется только если id группы есть в текущем `groups.json`; если один id группы указан несколькими `campaign_id` или группы нет в `groups.json`, в журнале остаётся десятичный `campaign_id` Keitaro и пишется потеря `log_campaign`. Если группы в манифесте есть, а карты `campaigns` ещё нет (старый перенос), карта достраивается один раз: GET `/admin_api/v1/campaigns` (или кампании из снимка, если снимок уже читался в этом запуске), затем `ktimport.GroupIDs`, но в карту и в журнал попадают только пары, где id группы есть и в списке `groups` манифеста, и в `groups.json`; существующие ключи карты не перезаписываются, новые пары сохраняются в манифест. Без ClickHouse или без хоста трекера журналы не читаются, карта и `groups.json` для журнала не запрашиваются, в потери пишется `clickhouse unavailable`. Кампания с номером `0` не даёт `group_id`. Неизвестный или не привязанный `campaign_id` даёт десятичный id в `group_id`; в тексте потери — число строк и до 20 id, остальные сворачиваются в «и ещё N». Потеря `log_campaign` пишется и при ошибке записи после частично обработанного журнала. `group_name` — из `groups.json` по итоговому `group_id`, иначе имя кампании из журнала. В `conversions` пустые поля в том же запуске могут добираться из индекса кликов по `sub_id`. `offer_id`, `landing_id`, `source_id` и `network_id` — числовые id Keitaro. Нулевой id остаётся пустым. Статус конверсии — строчными буквами (`lead`, `sale`, `rejected`). Тип устройства: `phone` / `computer` / `tablet` по маркерам в тексте. Страна — `country_code`.

Листание журнала идёт страницами по 10000. Чтение останавливается на пустой странице или когда смещение дошло до `total`. Если `total` больше нуля, страница короче 10000 не считается концом. `total` 0 или его отсутствие останавливает чтение на короткой странице.

Колонка `destination` журнала кликов пишется в `out` («Направление»), не длиннее 2048 байт (`logbuf.CapOut`). Клик с `landing_id` и без адреса в `destination` (Keitaro пишет туда метку вроде `LP`) получает `redirect = landing`, а в `out` — id лендинга, как у клика движка. Остальное — `destination` как есть, `redirect` пустой. Строки, импортированные раньше, остаются с пустым `out`: строки `events` не переписываются, а повторный импорт того же периода пропускает клики с уже записанным `cid` (дедуп ниже) и направление им не добавит. Заполнить старый период можно только стиранием импортированных кликов и новым импортом — это решение владельца, автоматически не делается.

К базовым колонкам запроса добавляется расширенный набор. У конверсий это `previous_status`, `original_status`, `tid`, `language`, `os_version`, `browser_version`, `device_model`, `referrer`, `search_engine`, `keyword`, `isp`, `ad_campaign_id`, `external_id`, `creative_id`. У кликов — `ad_campaign_id`, `external_id`, `creative_id`. Если расширенный набор отвечает статусом не 200 и ни одна строка ещё не принята, чтение один раз повторяется базовыми колонками. В потери пишется kind `approximated` и подробность «расширенные колонки недоступны». Колонки `params`, `visitor_code`, `site` и `x_requested_with` не запрашиваются. `site` и `xrw` в локальной строке остаются пустыми. `click_ts` конверсии берётся из `click_datetime`. `original_status` — сырой оригинальный статус, а если он пустой — сырой `status`. `prev_status` пишется строчными буквами.

## Ход импорта

«Перенести» отвечает сразу и работает в фоне. Один заход ограничен двумя часами; обрыв по этому сроку продолжает тот же перенос. Одновременно идёт один перенос: второй запуск и стирание, пока он не кончился, получают 409. Страница «Интеграции» опрашивает ход раз в две секунды.

На всех страницах справа сверху показывается окно хода импорта: его можно перетаскивать за заголовок, позиция запоминается в браузере. Процент считается на этапах потоков (`streams`), кликов и конверсий по счётчику сделано/всего; на остальных этапах полоски нет. Окно видно пользователям с доступом к разделу «Интеграции»; опрос `GET /api/keitaro/job` идёт каждые 3 с во время переноса и каждые 30 с в простое. Закрытие окна скрывает только текущий запуск до его конца.

Этапы: `snapshot`, `streams`, `catalogs`, `landing_files`, `lists`, `pages`, `groups`, `users`, `conversions`, `clicks`, затем `done` или `failed`. `users` выполняется, если отмечены пользователи. `snapshot` и `streams` идут, пока читается снимок. `landing_files` выполняется, если отмечены лендинги. `lists`, `pages` и `groups` — если отмечены кампании. `conversions` и `clicks` — если отмечены журналы. Конец — «Готово» или «Ошибка». Счётчики и потери, собранные до ошибки, остаются.

После `catalogs`, `landing_files`, `lists`, `pages` и `groups` админка сохраняет манифест и публикует счётчики и потери. На `snapshot`, `streams`, `conversions` и `clicks` в ход пишутся этап и счётчик сделано / всего.

Манифест — `keitaro-import.json` в каталоге состояния, рядом с `groups.json`. В нём хост трекера и списки id групп, офферов, лендингов, сетей, источников, доменов и пользователей Keitaro, а также имена файлов `lists` и `pages`.

Слияние заменяет запись с тем же id только если этот id уже есть в манифесте, прочитанном в начале запуска. Локальная запись с тем же id остаётся, в отчёт пишется потеря «id занят локальной записью». Запись, которой нет в новом снимке, сама не удаляется. Новые строки каталогов и кампаний в этом запуске получают `created_by` — `uid` сессии, которая нажала «Перенести» (у администратора окружения `uid` пустой). После записи каталога счётчики `offer_seq.json`, `landing_seq.json`, `network_seq.json`, `source_seq.json` и `domain_seq.json` поднимаются выше максимального числового id из манифеста.

Таблица потерь сводит одинаковые пояснения. Виды на экране: пропущено (`skipped`), приближено (`approximated`), выключено (`disabled`). Занятый локальный id приходит с kind `conflict`.

## Журнал переноса

Ход и итог последнего ручного переноса пишутся в `keitaro-job.json` в каталоге состояния, рядом с `keitaro-import.json`. В файле нет адреса трекера, ключа API и паролей. Пока перенос идёт, файл обновляется не реже чем раз в 5 секунд и сразу при смене этапа, в конце и когда журнал дочитан. Перезапуск admin файл не стирает: оборванный перенос читается как остановленный, с ошибкой «перенос оборвался перезапуском admin», и тут же продолжается сам (см. ниже).

На «Интеграции → Keitaro», вкладка «Что переносим», виден этот журнал: этап, ошибка, сколько строк кликов и конверсий уже записано, время начала и последнего изменения. Пока перенос идёт, те же числа обновляются. После остановки вкладка открывается сама, если перенос можно продолжить.

Обрыв по таймауту или по `context deadline exceeded`, в том числе когда кончается двухчасовой срок одного захода, не конец переноса. Тот же перенос продолжается сам с последней сохранённой пачки, уже новым сроком и с паузой, если трекер снова не отвечает. Уже записанный клик второй раз не пишется. Отмена (`context canceled`) и любая другая ошибка сами не запускаются: там нужна кнопка. Перезапуск admin переносом не кончается: при старте процесс читает `keitaro-job.json`; если там перенос, который шёл в момент остановки или остановился по таймауту, и его можно продолжить, он продолжается сам, без клика: тот же перенос, с первой не прочитанной кампании и с последней записанной пачки кликов, без второй копии. Пока идёт обновление (`update/pending`), перенос ждёт и подхватывается, когда гейт снят. Подхват после перезапуска делается не больше пяти раз подряд на один перенос: если перенос каждый раз роняет процесс, он остаётся остановленным и ждёт «Продолжить». Два переноса одновременно по-прежнему не идут.

Обновление (`update.sh`, «Обновить») не пересоздаёт admin, пока перенос идёт: гейт проверяет ответ admin и отдельно `keitaro-job.json` на томе; `running: true` в нём останавливает прогон до записи `pending` и ещё раз после `ready.json`. Обход — только `--keitaro-idle`, когда перенос точно не идёт. Watchdog работающий admin не перезапускает.

«Продолжить» есть у полного переноса, который остановился по таймауту, обрыву чтения журнала или перезапуску admin. Кнопка шлёт `POST /api/keitaro/import` с одним полем `resume: true`. Уже импортированное не удаляется. Каталоги, которые успели пройти, заново не читаются. Клики дочитываются с времени последней записанной пачки; клик с уже записанным `cid` второй раз не пишется. Конверсии читаются заново с начала окна: порядок этого журнала не совпадает с диапазоном запроса, а повтор той же пары `cid` и статуса схлопывается в `conversions`. Чтение потоков кампаний (этап `streams`, одна выборка на кампанию) не должно начинаться с нуля: каждая прочитанная кампания сразу пишется в `keitaro-job-streams.jsonl` рядом с журналом, и следующий заход берёт её оттуда без запроса к трекеру; счётчик «сделано из всего» стартует с уже прочитанных. Один запрос потоков ограничен двумя минутами, так что оборванное соединение не держит перенос до конца двухчасового срока. Файл привязан к хосту трекера, живёт не дольше 48 часов, не содержит адреса и ключа и удаляется, когда каталоги прошли, перенос закончился, начат другой перенос или импортированное удалено. Если нажать «Перенести» с теми же флагами и датами, что у оборванного переноса, который можно продолжить, он продолжится так же, как по «Продолжить»; другой набор флагов начинает новый перенос. «Удалить импортированное» не меняется. После удаления импортированного продолжать нечего. Досинк одной кампании и повтор фильтров кнопка не продолжает.

`GET /api/keitaro/job` дополнительно отдаёт `last_stage`, `updated_at`, `interrupted`, `resumable`, `resumes` и `logs`.

## Досинк одной кампании

На вкладке переноса есть поле «Keitaro ID кампании» и кнопка «Досинк одной кампании». Кнопка шлёт `POST /api/keitaro/import` с телом `{"campaign_id": N}`; N — числовой id кампании в Keitaro, не slug группы. Это та же задача и тот же маппер, что у полного переноса: те же этапы, манифест, слияние и отчёт потерь. Одновременно идёт одна задача: пока идёт перенос, стирание или актуализация, ответ 409, а кнопка заблокирована вместе с «Перенести».

С трекера читаются только GET: список кампаний, потоки одной кампании N, каталоги офферов, лендингов, сетей, источников и доменов. Список кампаний нужен целиком, чтобы id групп и alias совпали с полным переносом. В запись попадают группа кампании N, офферы и лендинги её потоков, сети этих офферов, источник и домен кампании. Остальные группы и записи каталогов не меняются. Повторный досинк той же кампании заменяет её группу по манифесту и не создаёт копий.

Тело с `campaign_id` само включает кампании и все каталоги, кроме пользователей. Отрицательный id и `campaign_id` вместе с `users`, `clicks` или `conversions` получают 400. Id, которого нет в трекере, завершает задачу с этапом `failed` и ошибкой «keitaro: кампания не найдена: N»; ничего не записывается. Для ключа API действие то же, что у переноса, — `keitaro_import`.

## Повторный перенос фильтров

Тело `{"filters_only": true, "campaign_ids": [N, …]}` или `{"filters_only": true, "all_imported": true}` перечитывает из Keitaro только потоки кампаний (один GET на кампанию) и переписывает только фильтры уже перенесённых потоков. Каталоги, действия, офферы, веса, имена и порядок потоков не трогаются. `all_imported` берёт кампании из карты `campaigns` в `keitaro-import.json`. С `"dry_run": true` ничего не записывается: отчёт показывает, что изменится.

Поток находится по `keitaro_stream_id` в заметке. Заменяются только правила, которые заполняет импорт, и флаг `filter_or`; ручные `limit`, `domain_text`, `operators`, `yabrowser` и настройки ботов остаются. Поток только выключается, если ни один его фильтр не перенёсся; включённым он не становится. Группа, которая не проходит проверки сохранения, остаётся как была, и в отчёте появляется `skipped`.

Отчёт — обычные потери задачи: `changed` на каждый изменённый поток с перечнем «добавлено / убрано / изменено», `skipped` для кампании без группы, удалённой группы и потока, которого нет с одной из сторон (нужен досинк кампании). Счётчики: `campaigns`, `streams`, `changed`, `groups`, `disabled`, `missing`, `failed`, `lists`, `dry_run`. Хост трекера должен совпадать с хостом манифеста. `filters_only` не сочетается с флагами каталогов, журналов и `campaign_id`; `campaign_ids`, `all_imported` и `dry_run` без него — 400.

## Стирание импорта

Кнопка «Удалить импортированное» спрашивает подтверждение. Стирание идёт по манифесту. Удаляются только id из манифеста: кампании, записи каталогов, файлы списков и страниц, названные в манифесте, и каталоги лендингов по этим id. Строки `events` и `conversions` снимаются, если `domain` равен хосту манифеста. Пустой хост манифеста заменяется хостом трекера. Затем манифест сохраняется пустым. Пустой манифест отвечает нулями и больше ничего не читает и не пишет. Пока идёт перенос или другое стирание, ответ 409 и ничего не снимается. Записи, которых нет в манифесте, не трогаются. Журнал других доменов не трогается.

## Keitaro 10 и 11

Проверка соединения, перенос и досинк ходят в один Admin API v1. Версию продукта этот интерфейс не отдаёт: в публичной спецификации Admin API (`openapi.json`, `info.version` = `v1`) нет пути версии, а чтение с рабочего трекера по путям `version`, `info`, `system`, `status`, `about`, `settings` даёт 404, заголовки ответа версии не несут. Версию определяет сама проверка по признакам, которые читаются без записи. После подсчёта кампаний она шлёт шесть небольших POST-чтений журналов (`/admin_api/v1/clicks/log` и `/admin_api/v1/conversions/log`, не больше 20 строк, от новых к старым, окно 90 дней, общий срок 10 с). Сбой любого запроса не ломает проверку, признак просто остаётся без голоса. Признаки:

| Признак | Голос за 10 | Голос за 11 |
| --- | --- | --- |
| `subid`: sub_id самого свежего клика | одна буквенно-цифровая строка без точки (`1vepsc2qv8h`) | сегменты до 12 знаков через точку (`2k5a13p.ac.2m74`) |
| `click_id` / `event_id`: журнал кликов принял колонку и вернул строку с этим ключом | `click_id` | `event_id` |
| `conversion_id` / `event_type`: то же для журнала конверсий | `conversion_id` | `event_type` |
| тип конверсии среди 20 свежих | `rebill` | любой тип вне lead, sale, rejected, registration, deposit, rebill, trash (`custom_type`) |

Справочника типов конверсий в allowlist нет, поэтому «Rebill удалён» и «пользовательские типы есть» по справочнику не читаются; признаками служат только типы свежих конверсий. Версия решается так: голоса только за одну версию дают «10» или «11»; голосов нет, или они идут за обе версии, дают пустую версию без догадки. Успешный `POST /api/keitaro/check` возвращает `api` со значением `v1`, `product_version` (`10`, `11` или пусто), `version_signals` (голоса: `signal` и `version`) и `version_conflict` (`true` только при голосах за обе версии). Карточка после проверки пишет «Admin API v1. Keitaro 11. Признаки: …», либо «Версия Keitaro не определена: признаков нет», либо «…признаки противоречат (…)». Ошибка проверки эту строку не показывает. Версия не пишется в `keitaro.json`, в курсор досинка и в манифест; админка помнит её в памяти для адреса трекера до следующей проверки.

Имена ключей версии лежат в одном месте, `ktimport.KeysFor`: Keitaro 10 даёт `click_id` (клики) и `conversion_id` (конверсии), Keitaro 11 даёт `event_id` (клики и конверсии) и `event_type` (тип конверсии). Строка журнала читается по тому набору, ключи которого в ней есть (`ktimport.KeysOfRow`); строка с ключами обеих версий не даёт ни идентификатора, ни типа. Значения лежат в `ClickRow.EventID`, `ConversionRow.EventID` и `ConversionRow.EventType`. Перенос журналов просит эти колонки только когда последняя проверка определила версию: для 10 это `click_id` и `conversion_id`, для 11 это `event_id` и `event_type`. Если журнал колонки не принял, чтение повторяется без них, с остальными расширенными колонками, и в отчёте одна строка `approximated` «колонки идентификаторов Keitaro N недоступны». Без определённой версии колонки не просятся, как раньше. Идентификаторы пока никуда не пишутся: в `events` и `conversions` нет колонок под них, `cid` по-прежнему равен `sub_id`. Тип конверсии берётся из `status`, а если он пуст, из `event_type`; свой тип 11 пишется строчными буквами как пришёл и только считается в строке отчёта о статусах вне списка.

Subid с точкой сохраняется в `cid` как пришёл. Колонки `visitor_code` не запрашиваются.

Срок уникальности кампании в часах, кроме 0 и 24, пишется в `uniq_seconds` (часы × 3600). 0 и 24 поле не задают: окно движка и так 24 часа. Срок переносится как есть, но ключи Redis живут не дольше потолка `EMTDS_UNIQ_MAX_SECONDS` (по умолчанию сутки, см. [память Redis](analytics-limits.md#память-redis)); в карточке кампании видно действующее окно. Отрицательный срок и срок, который не помещается в секунды, дают одну строку потери и в группу не пишутся. Привязка посетителя `sl` или `slo`, ненулевая стоимость или включённый `cost_auto`, либо заданная уникальность по параметру по-прежнему дают одну строку `approximated` на вид, со счётчиком кампаний. Поток из-за этого не выключается, `uniq_method` не заполняется. Фильтр потока `unique` переносится как раньше.

Статус конверсии пишется строчными буквами как пришёл. `trash` и свой тип не становятся `rejected`. Если за прогон встретился непустой статус вне `lead`, `sale`, `rejected`, `registration`, `deposit` и `rebill`, в отчёт одна строка. Суммы отчёта и схема ClickHouse не меняются: такой статус не входит в лиды и продажи, его `profit` остаётся в отчёте.

## Безопасность

К трекеру уходит GET только по allowlist Admin API v1: кампании и их потоки, один поток, офферы, лендинги, архив лендинга `/admin_api/v1/landing_pages/{id}/download`, сети, источники, домены, группы, пользователи `/admin_api/v1/users` и справочники схем, типов, фильтров и действий. Журналы — два POST: `/admin_api/v1/clicks/log` и `/admin_api/v1/conversions/log`. Другой метод или путь не отправляется. Запись в Keitaro не выполняется. Ключ уходит заголовком и в URL не ставится. Клиент не идёт по редиректу на другой хост и не уходит с https на http, поэтому заголовок с ключом не попадает чужому серверу; редирект внутри того же хоста работает. В статусе, в ходе задачи, в журнале админки и в тексте ошибки ключа нет: в ошибке он заменён на `***`. Значения query в тексте потерь тоже закрыты.

## Актуализация данных

На странице **Автоматизация** (`#/automation`) карточка **«Актуализация данных»** (`keitaro_sync` в `cron.json`) дотягивает **клики и конверсии** от последнего курсора до текущего момента и догружает **новые кампании** Keitaro (см. «Новые кампании»). Уже перенесённые кампании **обновляет** (см. «Обновление перенесённых кампаний»), каталог только дописывает (см. «Дозагрузка каталога»). Задачу исполняет **процесс admin** (свой тикер); cron-сервис секцию читает для интерфейса, но **не запускает** её и не пишет в свой `.status.json`.

Настройка: `enabled`, `every_minutes` (пол **5** минут, потолок **7** суток = 10080 мин). Путь курсора — `keitaro-sync.json` на томе (`EMTDS_KEITARO_SYNC_FILE`, по умолчанию рядом с `keitaro-import.json`): хост трекера, `clicks_to`, `conversions_to`, `last_run`, `ok`, `message`, `error`, `duration_ms`, `next_run`, `running`, `lag_seconds`, числа последнего прогона.

**Старт без файла:** один раз берутся `max(ts)` из `events` и `conversions` с `domain =` хост Keitaro за **8** суток, только если хост в **манифесте** совпадает с хостом настроек и в манифесте есть карта кампаний. Иначе статус **«нужен полный импорт»**, прогона нет. Если watermark больше «сейчас + 5 мин» — ошибка **«часовой пояс»**.

**Окна прогона:** клики — от `clicks_to − 30 мин` до **сейчас − 3 мин**; конверсии — от `conversions_to − 24 ч` до **сейчас − 3 мин**. Данные читаются **кусками по 6 ч**, за один прогон не больше **24 ч** суммарно. Таймаут прогона — **min(интервал, 30 мин)**. После серии ошибок пауза удваивается до **6 ч**. Telegram досинк **не шлёт**.

**Дедуп:** клики — на каждую пачку до 1000 строк запрос существующих `cid` в ClickHouse за окно плюс множество уже вставленных в этом прогоне; пустой `sub_id` и нулевое время — пропуск с записью в потери. То же дедупирование действует при **ручном импорте** кликов; в счётчиках задачи появляется **`clicks_duplicates`**. Конверсии в досинке с нулевым временем пропускаются; повторы в таблице схлопывает **ReplacingMergeTree**.

**Блокировки:** флаг `syncing` в задаче Keitaro. Ручной импорт, purge и второй досинк получают **409** (`идёт актуализация` / `import already running` / `purge already running`). Окно и счётчики ручного импорта досинк не меняет. `GET /api/keitaro/job`: `running` — только ручной перенос, **`sync_running`** — актуализация; плавающее окно хода импорта на `sync_running` не реагирует. **Purge** удаляет глобальный `keitaro-sync.json` только после того, как глобальный манифест сохранён пустым. Пустой манифест, ошибка чтения и ошибка склада курсор не трогают. Курсоры и манифесты разделов (`keitaro-sync-<board>.json`, `keitaro-import-<board>.json`) этот запрос не стирает. Ошибка чтения каталога списков или страниц не обнуляет манифест.

### Новые кампании

Каждый прогон после старта и до кликов одним GET читает список кампаний Keitaro и ищет кампании, которых нет в карте `campaigns` манифеста. Кампания из карты, чьей группы уже нет в `groups.json`, считается удалённой у нас и не возвращается: её число пишется в `campaigns_deleted`, на карточке — «Пропущено, удалены у нас». Новая кампания, чей id группы уже есть в манифесте, тоже пропускается.

Новые кампании идут по возрастанию id тем же маппером, что «Досинк одной кампании»: потоки с фильтрами, в том числе Bot Protection, и настройки кампании. Записи каталогов только вставляются, как в «Дозагрузке каталога»: уже лежащий id не меняется, удалённый вручную не возвращается. Лендинги скачиваются только для добавленных записей. Группы и их id попадают в манифест как перенесённые.

Лимиты: за прогон не больше **300** GET к трекеру на весь досинк (кампании, каталог и архивы лендингов), не больше **50** кампаний. Остаток ждёт следующего прогона. В `keitaro-sync.json` хранятся `campaigns_cursor` (последний обработанный id), `campaigns_pending` (сколько ждёт), `campaigns_failed` (не перенесённые), `campaigns_paused_until`, `campaigns_error` и `last_campaigns` (перенесено за последний прогон). Ответ 402 или 429, ошибка трекера или хранилища ставят шаг на паузу на час; клики и конверсии в этом прогоне идут дальше, задание не падает. Смена хоста сбрасывает эти поля. В Keitaro уходят только GET, Cloudflare не вызывается, сертификаты не выпускаются.

Карточка пишет в итоге прогона «новых кампаний N», а под курсорами — очередь, пропущенные удалённые, не перенесённые и активную паузу.

### Обновление перенесённых кампаний

Следующим шагом после новых кампаний (клики и конверсии идут дальше как раньше) прогон перечитывает кампании, уже перенесённые из Keitaro, и подтягивает их изменения. В Keitaro уходят только GET: список кампаний (в нём заметки) и по одному запросу потоков на кампанию.

**Сопоставление** — по сохранённому id Keitaro, не по slug. Группа ищется по id группы из манифеста, затем по `keitaro_stream_id=N` в комментариях потоков и по номеру кампании (`num`), и совпадение принимается, только если оно однозначно. Поэтому переименованная у нас кампания находится, а устаревший slug в манифесте исправляется. Кампании, не связанные с Keitaro, не затрагиваются.

**Что обновляется:** название; заметка кампании (`notes`), если в Keitaro она не пуста; вес; домен и источник, если Keitaro их прислал; у потоков — вес, фильтры (с правилами, которые мы не умеем переносить, как раньше), действие и ссылки (редирект, офферы, лендинги, распределение). Новый поток Keitaro добавляется после предыдущего потока из Keitaro. Кампания или поток, выключенные в Keitaro, выключаются и у нас; включить обратно синхронизация не может.

**Что не трогается:** «Уникальность по» и «только IP» (у Keitaro другие параметры, соответствия нет), постбэки, папка, алиасы, заголовок, ответ по умолчанию, владелец и названия потоков; потоки, созданные у нас; заметка, если в Keitaro она пуста. Кампания, удалённая в Keitaro, у нас остаётся и считается в `campaigns_gone` (на карточке «нет в Keitaro N»).

**Лимиты:** не больше **50** кампаний за прогон в общем бюджете **300** GET; остаток идёт по кругу со следующего прогона (`update_cursor`). Ответ 402 или 429 и ошибка трекера ставят на час только этот шаг (`update_paused_until`, `update_error`); не обновлённые кампании — в `update_failed`. Число обновлённых за прогон — `last_updated`. Один проход сохраняет `groups.json` один раз, после чего движок получает `POST /internal/reload`, и новые потоки действуют сразу. Два досинка одновременно не идут (`sync_running`).

Заметка кампании — поле `notes` группы (до 10000 символов, `GET`/`PUT /api/groups`). В интерфейсе заметка — последняя вкладка «Заметки» в шуфладе настроек кампании (вкладки: «Настройки», «Параметры», «Ссылки», «S2S постбеки», «Заметки»; опасная зона — внизу первой). На «Параметрах» идут обычные поля (`keyword`, `site`, `ad_campaign_id`, `creative_id`, `external_id`), затем `cost` и `currency`, один разделитель и группа `sub_id_*`. Это большое поле ввода, оно всегда видно и правится как остальные настройки: введённый текст остаётся при переключении вкладок и сохраняется вместе с кампанией. Поле очищено — заметка у кампании удаляется. Полотно кампании остаётся только потоками, вкладок на нём нет. Движок поле не читает.

Синхронизация пишет заметку Keitaro в это же поле при каждом прогоне, если в Keitaro она не пуста; правка, сделанная у нас, при следующем прогоне заменяется текстом из Keitaro. Пустая заметка в Keitaro локальный текст не стирает.

Карточка пишет в итоге «новых кампаний N, обновлено N, нет в Keitaro N», в подсказке — что перенесённые кампании тоже обновляются, а под курсорами — «Нет в Keitaro», «Не обновлены» и паузу этого шага.

### Расход кликов

Источник правды — цена клика из журнала Keitaro (колонка `cost` в `/admin_api/v1/clicks/log`). Она пишется в `events.cost_cents` в центах, `cost_cur` остаётся пустым: пустой код — валюта трекера, интерфейс показывает её как USD, как и доход. Досинк берёт расход тем же курсором и в тех же окнах, что клики; новой колонки и миграции нет. Цены кампании (`cost_type`, `cost_value`) не переносятся: они дают только строку `approximated`, а движок их не пересчитывает.

Старые клики без расхода не дозаполняются. Строки `events` не переписываются (это тяжёлая мутация ClickHouse), а дедуп по `cid` не даёт импортировать их повторно. Перезалить расход старого периода можно только стиранием импортированных кликов и новым импортом — это решение владельца. По той же причине не попадёт правка расхода, которую Keitaro сделает задним числом позже окна досинка (30 минут). Расход конверсий CPA-кампаний (`cost` журнала конверсий) не хранится: в `conversions` нет такой колонки.

### Дозагрузка каталога

Журналы хранят собственные id Keitaro (`offer_id`, `landing_id`, `network_id`, `source_id`). Если оффер, лендинг, сеть или источник появились в Keitaro после полного переноса, строки ссылаются на id, которого нет в каталоге. После каждого куска досинка и в конце ручного импорта журналов admin собирает id из прочитанных строк и **только дописывает** недостающие записи:

- запись читается по одной через `GET /admin_api/v1/{offers|landing_pages|affiliate_networks|traffic_sources|domains}/{id}` (и группы офферов, лендингов и доменов для папки); в Keitaro ничего не пишется;
- маппинг и слияние те же, что у полного переноса; id, который уже есть в каталоге (из прошлого переноса или созданный здесь), **не меняется**, даже если имя в Keitaro другое;
- id из манифеста, которого нет в каталоге, считается удалённым вручную и не возвращается;
- новые id попадают в манифест `keitaro-import.json` как перенесённые: следующий полный перенос обновит их как свои;
- сеть оффера, которой нет в каталоге, дочитывается вместе с оффером;
- за прогон не больше **300** запросов записей; остаток уходит в следующий прогон;
- ошибка трекера, манифеста или каталога не роняет досинк и импорт: в сообщение досинка (`message` в `keitaro-sync.json`) и в потери импорта попадает строка вида «оффер 850 не найден в каталоге (нет в Keitaro)», «сети 60,61 не найдены в каталоге (ошибка Keitaro)» или «… (лимит 300 за прогон)». Добавленное видно как «каталог +N» в сообщении досинка и `catalog_added` в счётчиках импорта.

**Разовая починка.** Первый прогон досинка на хосте берёт все id, на которые ссылаются `events` и `conversions` этого хоста в ClickHouse, и дозагружает их так же. Когда прогон прошёл без лимита и без ошибки, в `keitaro-sync.json` ставится `catalog_checked: true`, и полный проход больше не повторяется; смена хоста флаг сбрасывает. Отдельной кнопки нет: достаточно дождаться ближайшего досинка или нажать «Запустить» у карточки. Строки ClickHouse не переписываются.

**Домены.** Журналы id домена не хранят, поэтому источник id доменов — сами кампании (группы) в `groups.json`: поле `domain_id` у всех кампаний подключения (для подключения раздела — кампаний этого раздела). Разовая починка проходит по всем таким кампаниям и дозагружает недостающие домены в `domains.json` тем же путём: `GET /admin_api/v1/domains/{id}` и группы `type=domains`, маппинг доменов полного переноса (хост, роль `links`, группа), слияние только вставкой под блокировкой каталога доменов, общий лимит 300 за прогон. Новый домен ложится в том же виде, что после обычного импорта: без проверки, без Cloudflare и регистратора; Cloudflare не вызывается, сертификаты не выпускаются. У существующих доменов не меняется ничего: хост, группа, отключение, результат проверки, поля Cloudflare и регистратора. Домен из манифеста, которого нет в каталоге, считается удалённым вручную. Id, на которые Keitaro ответил 404, остаются строкой «домены 155,156 не найдены в каталоге (нет в Keitaro)»; кампании со ссылкой на них показывают «не найден», пока домен не заведут вручную.

Для доменов флаг свой — `catalog_domains_checked: true` в `keitaro-sync.json`. Общий `catalog_checked` для этого не годится: на хостах, где починка каталога уже прошла, он стоит, и домены бы не догрузились. Флаг ставится после прогона без лимита и без ошибки Keitaro, смена хоста сбрасывает оба флага. Если кампании не прочитались, флаг не ставится и строка «дозагрузка каталога: кампании не прочитаны» уходит в сообщение досинка.

**Номера новых записей.** Счётчики `offer_seq.json`, `landing_seq.json`, `network_seq.json`, `source_seq.json` и `domain_seq.json` поднимаются выше самого большого id из журналов и кампаний (и из манифеста при переносе). Поэтому оффер, созданный вручную, не получит id, под которым в истории уже лежит оффер Keitaro.

**Проверка на проде только чтением.** Сравнить максимальный `id` в `GET /api/offers` с максимальным `offer_id` в конверсиях:

```sql
SELECT max(toUInt64OrZero(offer_id)) FROM conversions WHERE domain = '<хост Keitaro>';
SELECT count() FROM conversions WHERE domain = '<хост Keitaro>' AND offer_id != ''
  AND offer_id NOT IN (<id из /api/offers>);
```

Если максимум в конверсиях больше, чем в каталоге, или второй запрос не ноль — дозагрузка ещё не прошла; смотреть `message` в `keitaro-sync.json` или карточку «Актуализация данных».

Задача cron **«Конверсии»** (Telegram) при объявлении новых постбэков **не анонсирует** строки с `domain`, равным хосту из `keitaro-import.json` (импортированные из Keitaro). Без настроенного Telegram переключатель «Конверсии» в UI не включается.

`PUT /api/cron` без ключа `keitaro_sync` (или с `null`) **сохраняет** прежнюю секцию. `POST /api/cron/run` с job `keitaro_sync` — **202** и запуск в admin (409, если занято или Keitaro/ClickHouse не готовы).

## API

Маршруты за сессией админки.

- `GET /api/keitaro/settings` — `base_url`, `host`, `has_key`, `source` (`file`, `env`, `none`). Токен не отдаётся.
- `PUT /api/keitaro/settings` — тело `{"base_url": "...", "api_key": "..."}`, пустой токен или маска оставляют прежний. Если `keitaro.json` — список подключений, меняются адрес и ключ первой записи, `board_id` и остальные записи остаются. Одиночный объект остаётся одиночным. Версия в файл не пишется. Ответ 200 с телом как у GET. Ошибки: 400 (неверный JSON, адрес или токен; `api_key required for new host` при смене хоста без нового токена), 409 (перенос или стирание идёт; `manifest_host`), 503 (файл не настроен), 500 `save error`. Оба маршрута доступны только администратору с cookie-сессией; запрос с `Api-Key` получает 403.
- `GET /api/keitaro/status` — заданы ли адрес и ключ, и хост. Трекер не вызывается.
- `POST /api/keitaro/check` — проверка ключа и число кампаний без скачивания списка (`ok`, `campaigns`, `api`, `product_version`). Только GET страниц по одной кампании.
- `POST /api/keitaro/import` — старт фона, ответ 202 и `started: true`. Тело включает `"users": true`, если нужен перенос пользователей. `"campaign_id": N` — досинк одной кампании (см. «Досинк одной кампании»). `"filters_only": true` — повторный перенос фильтров (см. «Повторный перенос фильтров»). Пока перенос или стирание уже идут, ответ 409.
- `GET /api/keitaro/job` — этап, счётчики, потери, текст ошибки; `running` — ручной импорт, `sync_running` — актуализация данных; `campaign_id` — кампания последнего досинка одной кампании, у полного переноса поля нет.
- `POST /api/keitaro/purge` — сколько записей снято.
- `GET /api/pages`, `GET /api/pages/{name}`, `PUT /api/pages/{name}`, `DELETE /api/pages/{name}` — файлы HTML, в том числе страницы переноса.

## Ограничения

В снимке около 7.9 тыс. кампаний. Кампании лежат одним массивом в `groups.json`. Страница кампаний читает короткие строки `GET /api/groups?summary=1` (имя, статус, номер и голова каждого потока, без правил и длинных URL). Одна кампания целиком — `GET /api/groups/{id}`.
