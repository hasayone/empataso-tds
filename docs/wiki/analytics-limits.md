# Лимиты аналитики, лог постбеков, память Redis

## Лимиты запросов статистики к ClickHouse

Сводка, графики, отчёт, производительность, разбивки, факты, журналы кликов и конверсий, лог постбеков, подсказки фильтров и окно расхода — запросы admin к ClickHouse. Один заход на сводку запускает сразу несколько сканов `events`. Лимиты задаёт одна функция `analyticsCtx` (`internal/store/analytics.go`): её вызывает каждая точка входа статистики. Вставки движка и запись конверсии лимитов не получают.

| Настройка ClickHouse | Переменная | По умолчанию | Зачем |
|---|---|---|---|
| `max_execution_time` | `EMTDS_CH_ANALYTICS_MAX_EXECUTION` (длительность Go) | `55s` | убивает только зависший скан |
| `priority` | `EMTDS_CH_ANALYTICS_PRIORITY` | `10` | вставка событий идёт с `priority=1`: пока она выполняется, аналитика ждёт |
| `max_threads` | `EMTDS_CH_ANALYTICS_MAX_THREADS` | половина CPU хоста, не меньше 1 | оставляет ядра вставкам и слияниям |
| `max_memory_usage` | `EMTDS_CH_ANALYTICS_MAX_MEMORY_MB` | `1024` | один запрос не съедает память контейнера ClickHouse (3–8 ГБ) |
| `max_bytes_before_external_group_by`, `max_bytes_before_external_sort` | — | половина `max_memory_usage` | большой период уходит на диск и считается дольше, а не падает |

Число `0` у `PRIORITY`, `MAX_THREADS` и `MAX_MEMORY_MB` оставляет значение сервера. Неверное или отрицательное значение оставляет значение по умолчанию. При старте в логе admin видна строка `clickhouse analytics limits` с действующими значениями.

Свои, более жёсткие потолки остаются: подсказки значений фильтра — 10 с, страница журнала с сортировкой не по времени — 20 с. Лимит ключа на тяжёлые маршруты (`heavy`) — не больше двух одновременно выполняемых запросов на API-ключ (`keyHeavyMax`); сессия браузера в него не входит.

Почему 55 с, а не больше. Цепочка ожиданий: ClickHouse `max_execution_time` → admin (у `http.Server` нет `WriteTimeout`, ожидание не ограничено) → nginx. Вход по IP (`emtds.conf`) идёт без `proxy_read_timeout`, то есть 60 с по умолчанию nginx. Хост `admin.*` (`emtds-admin-host.conf`) — 100 с, у Cloudflare перед ним тоже 100 с. С потолком выше 60 с на входе по IP пользователь получил бы страницу 504 от nginx раньше понятного ответа. Чтобы поднять потолок, сначала поднимают `proxy_read_timeout` в `deploy/nginx` (выше 100 с через Cloudflare не выйдет), потом переменную.

Запрос, остановленный лимитом (коды ClickHouse 159, 160, 241) или дедлайном контекста, получает `504` с текстом `query too heavy` и кодом `query_too_heavy`. Остальные ошибки — прежние `500`. Админка показывает «Запрос слишком тяжёлый: сократите период или добавьте фильтр». Для чтений, которые при ошибке молча берут пустое значение, это одно всплывающее сообщение раз в 10 с.

## Ключевые слова

`GET /api/keywords/stats` и `GET /api/keywords/trend` ([ключевые слова](keywords.md)) идут через тот же `analyticsCtx`, поэтому получают все лимиты из таблицы выше. К ним добавлено следующее:

- Период — не больше 92 дней, иначе `400 bad range`. Таблица держит не больше 2000 ключей (запрос просит 2001-й, чтобы отличить обрезку от точного попадания), тренд — не больше 25.
- Семафор на 2 слота на процесс admin. Таблица и тренд берут один слот на время запроса. Третий запрос не ждёт и получает `429 busy` без `Retry-After`. Слот освобождается и при обрыве соединения: страница отменяет прежние запросы при каждой новой загрузке и при уходе со страницы. Лимит ключа на тяжёлые маршруты (две одновременные выгрузки) действует отдельно, поверх семафора.
- Тренд — это два запроса подряд: ключи первых строк таблицы и ряд по дням для них. Оба идут под одним дедлайном, равным потолку `analyticsCtx` (`55s` по умолчанию), а не каждый со своим. ClickHouse при этом считает `max_execution_time` для каждого запроса отдельно.
- `max_query_size` у запросов по ключам — 8 МиБ вместо 256 КиБ по умолчанию. У роли со скоупом в тысячи кампаний список `campaign_id` повторяется в каждой половине запроса (клики и конверсии) и в запросе ключей; 256 КиБ на такой текст не хватает, разбор запроса падает.

Остановленный лимитом запрос отвечает `504 query too heavy`, как остальная статистика. Страница советует выбрать кампанию или сократить период.

## Лог постбеков

Строки `postback_log` engine кладёт в канал на 4096 строк и вставляет синхронными пачками со своим `insert_deduplication_token`, поэтому повтор пачки после тайм-аута не даёт дублей. Ответ партнёру запись лога не ждёт. Если вставка не прошла, пачка уходит в очередь на диске (`<экземпляр>/postlog/` на томе спула) и дописывается позже с исходным временем строк. Пачку, которую ClickHouse устойчиво отвергает при живых остальных вставках, после 5 отказов откладывают в `rejected/` и считают потерей (`postback_log_lost` в метриках, тревога cron). При остановке журнал закрывается в своём бюджете после очередей постбеков и исходящих.

Лог только для просмотра (`GET /api/postback-log`), деньги в нём не считаются: конверсия пишется отдельно в `conversions`.

## Память Redis

Ключи уникальности (`uniq:`, `uniqo:`) и запомненного потока (`st:`) живут не дольше потолка `EMTDS_UNIQ_MAX_SECONDS` (по умолчанию 86400 — сутки; пустое значение и `0` дают сутки, неверное — сутки и строку в логе). Поле кампании `uniq_seconds` не меняется: в Redis ключ просто живёт не дольше потолка, короткое окно не удлиняется. При 10 000 кликов в минуту это около 1,1 ГБ ключей в сутки; без потолка импорт Keitaro (окно в год у большинства кампаний) переполнил бы Redis за сутки. В карточке кампании админка показывает действующее окно с учётом потолка.

Старые ключи engine один раз дочищает при старте: проходит `SCAN uniq:*`, `uniqo:*`, `st:*` маленькими шагами и ставит срок жизни не больше потолка ключам, у которых он больше или не задан. Защита от двух проходов сразу — замок `SET NX` с продлением; маркер `trim:done` без срока жизни хранит потолок, поэтому новый проход идёт только при смене `EMTDS_UNIQ_MAX_SECONDS`. Прогресс — раздел `redis_trim` в [метриках engine](reliability.md#метрики).

Тиры `install.sh` для новых установок: до 12000 MiB RAM — `maxmemory 512mb` и лимит контейнера 768m, от 12000 MiB — `2gb` и 3g. На существующем сервере — `deploy/apply-redis.sh` (только по явной просьбе): `CONFIG SET maxmemory` и `docker update --memory` без пересоздания Redis. Скрипт идемпотентен, лимит контейнера не снижает ниже текущего потребления с запасом 20%, при сбое второго шага пишет «применено частично, повторите». `--check` показывает текущие значения, цель и расхождение с `maxmemory` в command контейнера. `CONFIG SET` действует до перезапуска процесса Redis: после рестарта контейнера или перезагрузки сервера скрипт повторяют; постоянное решение — пересоздание Redis, только с согласия пользователя.

Сессии админки лежат в том же Redis. Если Redis не принял запись сессии или недоступен лимитер входа, вход отвечает `503` с текстом `session store unavailable` до проверки пароля; `401` и `429` прежние.

Redis работает с `maxmemory` и политикой `noeviction`: на маленьком сервере это 512 МБ. Когда память кончается, новые ключи не пишутся, движок по fail-open считает каждый клик уникальным, антифлуд и лимиты потоков молча перестают работать. Политика не меняется. Вместо этого cron следит за памятью.

Раз в минуту cron читает `INFO` (`used_memory`, `maxmemory`, `errorstat_OOM`, `rejected_connections`) и кладёт результат в свой файл состояния (`redis_memory`). Telegram шлёт только cron, admin ничего не отправляет, поэтому двойного сообщения нет. Проверка работает и при выключенных задачах cron; сообщение уходит, если в «Автоматизации» настроен Telegram.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `EMTDS_REDIS_ALERT_PERCENT` | `80` | тревога при заполнении на столько процентов и выше |
| `EMTDS_REDIS_RECOVER_PERCENT` | `70` | тревога снимается ниже этой доли; не выше доли тревоги |
| `EMTDS_REDIS_ALERT_REPEAT` | `6h` | напоминание, пока память высокая; `0` — без напоминаний |
| `EMTDS_ALERT_LANG` | `en` | язык сообщения в Telegram: `ru`, `uk`, `en` |

Сообщения: одно при подъёме выше порога, напоминание раз в `REPEAT`, одно при спаде ниже `RECOVER`. Между 70% и 80% состояние не переключается. При `maxmemory 0` (без лимита) проверка ничего не шлёт. Cron получает `EMTDS_REDIS_ADDR` и `EMTDS_REDIS_PASSWORD` в `deploy/docker-compose.app.yml`.

Пока тревога поднята и последняя проверка не старше 10 минут, `GET /api/notices` добавляет строку `<время> redis memory 87% (450 MiB of 512 MiB)`. Админка показывает по ней жёлтую плашку над страницей (ru/uk/en) и читает notices не чаще раза в минуту. Остановленный cron плашку не держит: состояние старше 10 минут не показывается.
