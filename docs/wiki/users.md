# Пользователи панели

Помимо входа по паролю из окружения контейнера админки, в `users.json` хранятся учётные записи с ролями и ограничениями. Они входят по логину и паролю, видят только отмеченные разделы и только те сущности, которые разрешены грантами. Управление списком — у администраторов.

## Типы доступа

| Тип | Где задаётся | Поведение |
| --- | --- | --- |
| Администратор окружения (root) | `KUZTDS_ADMIN_USER`, `KUZTDS_ADMIN_PASSWORD_HASH` или файл пароля | Полный доступ ко всем разделам и API. В сессии нет `uid`. В `GET /api/users` и на странице пользователей показывается первой строкой с `source: env`; не редактируется, не выключается и не удаляется через API; пароль — через `POST /api/password`. |
| `ADMIN` | запись в `users.json` | Полный доступ, как у root, но с собственным логином и хешем в файле. |
| `USER` | запись в `users.json` | Список разделов в `access.sections`, гранты по шести ресурсам, опционально скрытые метрики в `access.hidden`. |
| API-ключ с доступом `admin` | файл ключей | Полный доступ к Admin API, как у администратора. Ключ не открывает `/api/users`, `/api/me`, смену пароля и управление ключами. |

Сессия по API-ключу помечается как API: маршруты с `cookieOnly` отвечают `403 cookie session required`.

Хэш пароля администратора окружения при первом старте записывается в файл из `KUZTDS_ADMIN_PASSWORD_FILE` (на томе это `admin.hash`, режим `0600`), если файла ещё нет и пароль задан в окружении. Дальше вход берёт этот файл, и пароль из окружения его не заменяет. Пустой или нечитаемый файл не даёт админке стартовать. Сам пароль в браузере не хранится: сессия — cookie `kuztds_admin`.

Если нет ни пароля в окружении, ни `admin.hash`, админка стартует без пароля. Панель показывает форму первого входа: логин, пароль и почта главного администратора. `POST /api/setup` записывает `admin.hash` и соседний `admin.json` (логин и почта, режим `0600`) и сразу открывает сессию. Пока форма не сохранена, остальной API отвечает как неавторизованный; открыты `GET /api/health`, `GET /api/brand`, `GET /api/setup` и `POST /api/setup`. Повторный `POST` — `409`. Следующий старт берёт логин из `admin.json`, он важнее `KUZTDS_ADMIN_USER`. Почта видна у администратора окружения в `GET /api/me` и в профиле. Письмо не отправляется. Заданный пароль окружения эту форму не включает.

Сброс пароля делается одноразовым кодом с сервера, без письма. Команда `kuztds-admin -recovery` печатает код один раз и не спрашивает новый пароль. Логин кода — `KUZTDS_RECOVERY_LOGIN`, а если она пуста, то `KUZTDS_ADMIN_USER`. Рядом с `admin.hash` лежат только хэш кода, логин и срок около 15 минут (`recovery.json`, режим `0600`). Повторный запуск заменяет прежний код. Форма входа отправляет логин, код и новый пароль на `POST /api/recover`: верный код записывает новый хэш корневому логину в `admin.hash` или пользователю в `users.json` и гасит код. Неверный код и просроченный код отвечают одинаково. Открытый файл с паролями приложение не ведёт.

## Файл users.json

Путь задаёт `KUZTDS_USERS_FILE`. Если переменная не задана, но настроен `KUZTDS_GROUPS_FILE`, по умолчанию файл лежит в том же каталоге, что и `groups.json`. Пустой путь отключает хранилище: вход возможен только под администратором окружения, `GET /api/users` отдаёт только строку администратора окружения, создание пользователей — `503 users disabled`.

Запись файла — JSON-массив с отступами, права `0600`. Отсутствующий файл при старте даёт пустой набор пользователей. Битый JSON, дубликаты `id` или `login`, неверный `type` или формат хеша — админка не стартует с ошибкой загрузки `users.json`.

## Модель записи

Публичные ответы API не содержат поле `hash`.

```json
{
  "id": "случайный токен",
  "login": "operator",
  "type": "USER",
  "enabled": true,
  "prefs": { "lang": "ru", "tz": "Europe/Kyiv" },
  "access": {
    "sections": ["dashboard", "flows", "offers"],
    "grants": {
      "campaigns": { "mode": "selected", "ids": ["alias-camp"], "labels": ["FolderName"] },
      "offers": { "mode": "read" }
    },
    "hidden": ["profit"]
  },
  "created_at": "2026-10-01T12:00:00Z",
  "keitaro_id": 42,
  "access_source": "manual",
  "role_id": "id роли из roles.json, необязательно"
}
```

`prefs.lang` — `ru`, `en`, `uk` или пусто. При входе, если в браузере язык ещё не выбран, интерфейс берёт это значение. Числа и даты в интерфейсе форматируются локалью языка: `ru-RU`, `uk-UA`, `en-US`. Деньги в таблицах и сводке — `moneyText` (два знака, группировка разрядов, пустой код валюты — `$`). CSV пишет числа без группировки (`csvNum`), деньги — машинным числом `1234.50` (`csvMoney`) с валютой в заголовке колонки; при расходе в нескольких валютах деньги в CSV остаются текстом. `prefs.tz` — имя пояса IANA или пусто. `access_source` — `manual` или `keitaro` (источник прав при импорте). `keitaro_id` связывает запись с пользователем Keitaro. Поле `source` есть только в ответах `GET /api/users`: `env` для администратора окружения, `file` для записей файла; в `users.json` не хранится.

## Разделы панели

Раздел из `access.sections` открывает пункт меню и связанные маршруты API. Администратор (`ADMIN`, root, API-ключ) видит все разделы, включая админские.

| ID | Что открывает |
| --- | --- |
| `dashboard` | Сводка: `GET /api/stats/summary`, `timeseries`, `breakdown`, `facts` |
| `flows` | Кампании: `PUT /api/groups`, постбеки кампании, расход `GET|POST|DELETE /api/spend`, `GET /api/stats/performance` |
| `offers` | CRUD `/api/offers` |
| `landings` | CRUD `/api/landings` и файлы лендинга |
| `networks` | CRUD `/api/affiliate-networks` |
| `sources` | CRUD `/api/traffic-sources` |
| `domains` | CRUD `/api/domains`, `POST /api/domains/{id}/check` |
| `logs` | Журнал кликов, экспорт, значения полей; удаление журнала — только администратор |
| `conversions` | `GET /api/postbacks`; журнал S2S postback — только администратор |
| `report` | `GET /api/report` |
| `keywords` | `GET /api/keys` |
| `lists` | Чтение списков; запись `PUT /api/lists/{name}` — только администратор |
| `tools` | `GET /api/lookup`, `POST /api/simulate` |
| `groups` | Подпись «группа» в каталогах (отдельного экрана нет) |

Только администратор:

| ID | Что открывает |
| --- | --- |
| `users` | CRUD `/api/users` и смена пароля/доступа |
| `api_keys` | Управление API-ключами |
| `integrations` | Keitaro: status, check, import, job, purge |
| `automation` | Cron |
| `pages` | HTML-страницы `@page:` |
| `bot_protection` | Настройки ботов |
| `settings` | `PUT /api/ui` |

Без привязки к разделу (`secAny`), но только для авторизованной сессии: `GET /api/me`, `POST /api/password`, `POST /api/logout`, `GET /api/notices`, `GET /api/log-fields`, `GET /api/ui`, `GET /api/groups`.

## Гранты по ресурсам

Ключи в `access.grants`: `campaigns`, `offers`, `landings`, `sources`, `networks`, `domains`.

| mode | Чтение | Запись | Создание |
| --- | --- | --- | --- |
| `full` | все записи | все | да |
| `read` | все | нет | нет |
| `selected` | id из `ids` или подпись из `labels` | только видимые | нет |
| `created` | свои (`created_by` = id пользователя) плюс id/labels из гранта | только видимые | да |

Для кампаний в `labels` попадает поле `folder` (группа кампании). Для офферов, лендингов, сетей, источников и доменов — поле `group` каталога.

Если раздел каталога открыт, а ключа ресурса в `grants` нет, действует режим `read`: список и чтение всех записей, без создания и правки.

В `ids` и `labels` не больше 500 элементов каждый; дубликаты и пробелы по краям отбрасываются.

## Скрытые поля

В `access.hidden` допустимы имена полей журнала и группа `cost`; полный порядок работы и места, где поле не показывается, описаны в [Роли](roles.md). Доступ можно задать и ролью: пользователь с `role_id` берёт разделы, гранты и скрытые поля из роли, свой `access` у него не действует и при назначении роли обнуляется.

При `profit` из JSON статистики убираются ключи `profit`, `revenue`, `payout`, `depsum`. При `cost` — `cost_cents`, `cost`, `cost_cur`, `currency`, `spend`. Фильтр журнала или статистики по скрытому полю даёт `400 bad filter: hidden field …`.

Все методы `/api/spend` при скрытом `cost` отвечают `403 forbidden` до чтения файла расхода.

Интерфейс дополнительно прячет столбцы: при `profit` — `revenue`, `profit`, `roi`, `epc`, `uepc`, `epv`, `payout`, `depsum`; при `cost` — `cost`, `spend`, `cpc`, `cpa`, `cpm`, а также `roi` и `profit`; при `status` — лиды, продажи, отклонённые и их CR; при `uniq` — уники, при `bot` — боты. Список берётся из `hidden` ответа `GET /api/me`. Описание — в [Роли](roles.md#интерфейс).

## Страница «Пользователи»

Таблица: логин, тип, роль, состояние, язык, пояс, источник, дата. В колонке «Роль» стоит название роли, «Свой доступ» (у пользователя без роли), «Роль не найдена» (роль удалена или `roles.json` недоступен) или тире у администратора. Под таблицей — блок «Роли» (создание, правка, удаление, «Перечитать»).

Форма пользователя содержит выбор роли. Пустой выбор — свой доступ. Администратору роль не назначается: выбор скрывается при типе `ADMIN`. Интерфейс шлёт `role_id` только при изменении выбора; при создании без роли поле не уходит, а `access` форма не отправляет никогда (сервер ответил бы `400 user with a role has no own access`). Снятие роли — `role_id: ""`; своего доступа после этого нет, его задаёт пункт меню «Доступ». У пользователя с ролью этого пункта нет: сервер ответил бы `409 user has a role`.

## Коды 403 и 404

- Нет раздела для маршрута — `403 forbidden`.
- Админский маршрут (удаление журнала, запись списков, postback-log) для `USER` — `403`.
- Запись каталога или кампания вне видимости — `404 not found` (GET/PUT/DELETE по id).
- Нет права на изменение — `403 forbidden`.
- `PUT /api/groups`: правка чужой кампании — `403 foreign campaign`; кампания только для чтения — `403 read-only campaign`; создание без права — `403 cannot create campaigns`; новая ссылка на невидимую сущность — `400 unknown offer/landing/…`.

## Кампании и каталоги

`GET /api/groups` для `USER` возвращает только кампании, видимые по гранту `campaigns`. `PUT /api/groups` принимает массив целиком: невидимые кампании должны совпасть с файлом, иначе отказ; видимые можно менять в пределах `canWrite`; новые — только при `canCreate`.

Ссылки в потоке (оффер, лендинг, домен, источник, другая кампания) при сохранении проверяются: новый id должен быть виден по соответствующему ресурсу.

Новые строки каталога получают `created_by` = id текущего пользователя. При импорте из Keitaro в `created_by` попадает `uid` сессии, запустившей перенос.

Домены для `USER`: при создании роль по умолчанию `links`; нельзя выставить `primary`, роль `admin` или `both` — `403 primary and admin role are set by an administrator`. При правке `primary` и `role` берутся из сохранённой записи.

## Статистика и журналы

Запросы с `f=` к статистике и журналам дополняются ограничением по кампаниям: для `selected` и `created` в SQL уходит `campaign_id IN (…)` по видимым alias; пустой набор заменяется на `ScopeNone`, совпадений нет.

Для кликов поле `campaign_id` мапится на `group_id` с базовой волной схемы. Для конверсий то же поле использует колонку `group_id` волны `ext`. Пока волна `ext` на таблице `conversions` не готова, любое условие с полем этой волны (в том числе серверный фильтр по кампаниям) не выполняет запрос: журнал конверсий и `GET /api/postbacks` для ограниченного пользователя возвращают пустой список, без ошибки. После появления колонки фильтр по кампаниям работает.

## Сессии

Сессия пользователя из `users.json` хранит отпечаток хеша пароля. Выключение учётки или смена пароля (в том числе через `PUT /api/users/{id}/password` или `POST /api/password`) обнуляет отпечаток — старые куки получают `401`.

Сессии администратора окружения без `uid` живут, пока совпадает отпечаток root-пароля; смена пароля root рвёт такие сессии. Старые куки root без поля `uid` остаются сессией администратора окружения.

Вход: логин без учёта регистра; неизвестный или выключенный пользователь без пароля проверяется против `DummyHash`, чтобы время ответа не выдавало наличие логина.

## Защиты

- Логин, совпадающий с `KUZTDS_ADMIN_USER`, нельзя занять в `users.json` — `409`.
- Логины с префиксом `apikey:` запрещены.
- Снять последнего администратора из файла можно: администратор окружения остаётся и этого достаточно, ответ не `409`.
- Нельзя выключить или удалить себя — `409 cannot disable yourself` / `cannot delete yourself`.
- Пароль не короче шести символов; пустой пароль при создании или в `PUT …/password` снимает возможность входа.

## Интерфейс

В меню пользователя пункт «Пользователи» ведёт на `#/settings/users` (нужен раздел `users`). На странице профиля третья вкладка «Пользователи» рядом с «Профиль» и «API ключи». Таблица, создание, правка, пароль, включение и удаление. У типа `USER` в меню строки — «Доступ»: разделы, режимы по ресурсам, id и подписи, скрытые метрики. Администратор окружения идёт первой строкой. В колонке источника у него подпись «Владелец окружения, полные права», тип — «Администратор», язык и пояс — те же, что в интерфейсе, словами, а не кодами ru и manual. Дата — «Задан при установке». Меню действий у этой строки нет; под этой учёткой в строке есть кнопка «Пароль» на смену пароля в профиле. У остальных администраторов источник — «Полные права», у пользователей — «Свои права», перенесённых из Keitaro — «Перенесён из Keitaro». Карточки «Аккаунт» на вкладке профиля нет.

На переносе Keitaro отдельная галочка «Пользователи»; подсказка: перенесённые пользователи выключены и без пароля.

## Проверка

В образе `kuztds-src`:

```bash
go test ./internal/security/ -run Users
go test ./internal/admin/ -run 'Users|NormalizeAccess|UserPages|RouteMatrix|Hidden|Scope|KeitaroImportUsers'
go test ./internal/bridge/ktimport/ -run MapUsers
```

Интеграционные тесты ClickHouse для этой темы не обязательны, если схему не меняли.
