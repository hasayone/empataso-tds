# Роли

Роль — именованный набор доступа: разделы, режимы по ресурсам и скрытые поля. Пользователь с `role_id` берёт доступ из роли. Изменение роли применяется ко всем её пользователям сразу, без нового входа.

## Файл roles.json

Путь задаёт `EMTDS_ROLES_FILE`; по умолчанию файл лежит рядом с `users.json`, в `/var/lib/emtds`. Запись атомарная, права `0600`, формат — JSON-массив с отступами.

```json
[
  {
    "id": "случайный токен",
    "name": "Баеры",
    "access": {
      "sections": ["dashboard", "flows", "logs"],
      "grants": { "campaigns": { "mode": "created" }, "offers": { "mode": "read" } },
      "hidden": ["cost", "ip"]
    }
  }
]
```

- Нет файла — ролей нет, всё работает как у пользователей с собственным `access`.
- Файл повреждён (битый JSON, пустой файл, повторный `id` или имя, админский раздел, неизвестное или нескрываемое поле в `hidden`, режим `selected`) — пользователи с ролью остаются без доступа, администраторы работают полностью, изменение ролей отвечает `503 roles unavailable`, файл не перезаписывается.
- Починив файл руками, не перезапуская админку, вызовите `POST /api/roles/reload`: файл проходит ту же проверку, что при старте. Хороший файл снимает блокировку, плохой оставляет роли пустыми и отвечает `503 roles unavailable: <причина>`.
- Путь к файлу пустой — хранилище ролей выключено: список ролей пуст, создание и перечитывание — `503`, назначить роль нельзя.
- Роль, которой уже нет в файле, закрывает доступ её пользователям: нет разделов, нет записей ни в одном ресурсе.
- Роли живут в памяти одного процесса админки, как и `users.json`: изменение через API видит только процесс, который его принял. При нескольких копиях админки после правки файла перечитайте роли в каждой копии (`POST /api/roles/reload`) или перезапустите её.

## Правила роли

- Имя — от 1 до 64 символов, без пробелов по краям и управляющих символов; уникально без учёта регистра.
- В `sections` допустимы только разделы пользователя: `dashboard`, `flows`, `offers`, `landings`, `networks`, `sources`, `domains`, `logs`, `conversions`, `report`, `keywords`, `lists`, `tools`, `groups`. Админские (`users`, `api_keys`, `integrations`, `automation`, `pages`, `bot_protection`, `settings`) роль не открывает.
- Режим `selected` в роли запрещён: он перечисляет записи одного пользователя. Режим `created` хранится без `ids` и `labels`: так он записывается, и так же он лежит в памяти после чтения `roles.json` при старте и после `POST /api/roles/reload`, даже если в файле списки остались. Режим `created` показывает только записи, которые создал сам пользователь; список `ids` или `labels` в нём ничего не открывает. Собственный `access` пользователя нормализуется так же.
- Роль нельзя назначить пользователю типа `ADMIN`; при повышении пользователя до `ADMIN` роль снимается. Администратор всегда имеет полный доступ.
- Роль, которую кто-то использует, не удаляется: `409 role in use`.
- Собственный доступ пользователя с ролью не действует. При создании с `role_id` непустой `access` — `400 user with a role has no own access`; при назначении роли собственный доступ обнуляется, и после снятия роли пользователь остаётся без разделов, пока ему не выдадут доступ заново (`PUT /api/users/{id}/access`).
- У пользователя с ролью `PUT /api/users/{id}/access` отвечает `409 user has a role`.
- Пользователь, перенесённый из Keitaro и уже имеющий роль, при повторном импорте и очистке не меняется.

## Скрытые поля

В `access.hidden` — имена полей журнала и группа `cost`; список с признаком `hideable` отдаёт `GET /api/log-fields`. `profit` и `cost` скрывают сразу все свои поля: `cost` — `cost_cents`, `cost_cur`. Поле `ts` скрыть нельзя: на нём построены все таблицы и графики. Поле `step` внутреннее и в списке не показывается.

Скрытое поле не попадает:

- в JSON журнала, конверсий, отчёта, сводки, временного ряда, разбивки, `performance` и фактов — убираются ключи поля и его производные (`group`, `unique`, `uniq_first`, `bots`, `revenue`, `payout`, `depsum`, `cost`, `spend`, `currency` и т. п.);
- в CSV-экспорт журнала — столбец не пишется;
- в `GET /api/log-fields` и список значений фильтра;
- в Sub ID: значение скрытого `sub_id_N` в строках заменяется пустым;
- в `payout` и `payout_currency` офферов при скрытом `profit`: в списке и карточке их нет, правка оффера такой ролью сохранённую выплату не меняет, у нового оффера выплата пустая.

Поле, значение которого повторяет скрытое или уточняет его, скрывается вместе с ним: скрытый `status` скрывает `original_status` и `prev_status`, `os` — `os_version`, `browser` — `browser_ver`, `brand` и `device` — `device_model`. Обратного нет: скрытое производное поле родителя не скрывает. Ключи `original_status` и `prev_status` убираются из JSON так же, как остальные ключи поля.

Фильтр `f=`, `dim` разбивки, `GET /api/log-values?field=` и старые параметры запроса (`group`, `stream`, `country`, `status`, `offer` и другие) по скрытому полю отвечают `400 bad filter: hidden field …`. `GET /api/keys`, `GET /api/keywords/stats` и `GET /api/keywords/trend` при скрытом `keyword` и все `/api/spend` при скрытом `cost` — `403 forbidden`.

### Скрытый status

Факты (`GET /api/stats/facts`) при скрытом `status` отдают строки конверсий свёрнутыми: остаются только подтверждённые (`lead` и `sale`, как в сводке и отчёте), по ключу «оффер, сеть, кампания» одной строкой со `status: "sale"` и суммой `n`, `profit` и `depsum`. Отклонённые и прочие статусы не передаются. Числа совпадают с `performance` и отчётом; разделить лиды и продажи при скрытом `status` нельзя.

### Скрытие в ключевых словах

Раздел `keywords` открывает таблицу ключей с деньгами: клики, уникальные, конверсии, лиды, продажи, отказы, доход и депозиты по каждому ключу, плюс ряд по дням ([ключевые слова](keywords.md)). Поля роли действуют так:

| Скрыто | Что меняется |
| --- | --- |
| `keyword` | `GET /api/keywords/stats`, `GET /api/keywords/trend`, `GET /api/keys` и `GET /api/keys/download` — `403 forbidden`; страница показывает отказ |
| `status` | Из ответа уходят `leads`, `sales`, `rejected`; `conv` и `profit` остаются и считают все статусы. В таблице скрыты колонки «Лиды», «Продажи», «Отклонено»; CR остаётся |
| `profit` | Уходят `profit` и `depsum`, в тренде — массивы `profit`. В таблице скрыты «Доход» (колонка `revenue`) и «DepSum», в подсказке тренда нет строки дохода |
| `uniq` | Уходит `unique`; колонка «Уникальные» скрыта |
| `campaign_id` | Выбор кампании на странице не показывается. Запрос идёт по всем видимым кампаниям, без `f=campaign_id` |

Скрытая цена (`cost`) колонку «Доход» не убирает: деньги ключа — это выплата, а не прибыль за вычетом расхода. Серверный ответ при скрытом `cost` не меняется.

Условия фильтра, сохранённые на поле, скрытом для роли, в запрос не уходят: страница выкидывает их до отправки, а не получает `400`. Если колонка сохранённой сортировки скрыта, сортировка сбрасывается на порядок сервера.

Скоуп кампаний роли ограничивает и таблицу, и тренд: считаются только видимые роли кампании (по режиму ресурса `campaigns` и по доступным [разделам](boards.md)). Условие `f=campaign_id:eq:<чужая кампания>` даёт пустую таблицу. `GET /api/keys` и `GET /api/keys/download` для чужой кампании отвечают `404 not found`.

Ключ движок читает под именем из источника и под тремя именами запроса: `keyword`, `q`, `utm_term` ([откуда берётся ключ](keywords.md#откуда-берётся-ключ)). Админка и движок берут один список (`config.KeywordParams`) и одно правило занятости имени (`config.KeywordNameTaken`). При скрытом `keyword` админка считает так:

- `q` читает ключ всегда, даже если источник назначил его другому полю. Роль не может привязать видимое поле источника (Sub ID, `site`, `ad_campaign_id`, `creative_id`, `external_id`) к `q`, а при смене источника кампании — перейти на источник, где видимое поле читает `q`: `400`.
- `keyword` и `utm_term` читают ключ, только пока они не заняты другим параметром источника или ценой кампании. Привязка видимого поля к такому имени отнимает его у ключа, поэтому скрытое значение через него не читается.

Со стороны движка то же правило: имя `keyword` или `utm_term`, занятое другим полем источника или совпавшее с `cost_param` либо `currency_param`, ключом не становится. Значение скрытого Sub ID, дополнительного поля или цены, привязанное к такому имени, в ключ не попадает. Для `q` это не так: `q` остаётся ключом, поэтому его привязка видимого поля закрыта.

### Скрытая кампания

`campaign` (название кампании) и `campaign_id` (адрес кампании) скрываются независимо. Название скрывается в журнале, отчёте и фактах, но остаётся видно в разделе кампаний: каталог кампаний выдаётся по разделу и режиму ресурса `campaigns`, а не по полям журнала. `campaign_id` связывает строки статистики с кампаниями и нужен самому разделу кампаний, поэтому с `campaign` его не скрывают; скрыть его можно отдельно, но таблицы кампаний тогда теряют статистику.

### Ограниченный доступ к кампаниям

Если у пользователя или роли режим ресурса `campaigns` не `full` и не `read` (`created`, `selected` и т. п.), столбцы «Первоисточник» (`origin_campaign`, `origin_campaign_id`) и поля корня цепочки (`root_cid`, `origin_stream`, `origin_keyword`) скрываются принудительно: в JSON, CSV, фильтрах, сортировке и каталоге полей, даже если поле не указано в `hidden`. Так нельзя увидеть названия чужих кампаний через цепочку hop.

## Макросы

Скрытие закрывает API и журнал, но ссылка потока, оффера или исходящего постбэка может сама подставить скрытое значение в адрес чужого сервера. Поэтому пользователь, которому поле скрыто, не может добавить в ссылку макрос этого поля: сохранение кампании (`PUT /api/groups`, `PUT /api/groups/{id}`), оффера и лендинга (`POST` и `PUT`), исходящих постбэков кампании (`PUT /api/campaigns/{id}/postbacks`) отвечает `400 macro <макрос> uses hidden field <поле>`.

Правила проверки:

- Строка со скрытым макросом проходит, только если в сохранённой записи на том же месте стоит такая же строка дословно: то же поле того же потока или исходящего постбэка (поток находится по имени, постбэк по `id`; без уникального имени или `id` — по позиции в списке). Любое изменение такой строки (другой хост, добавленный параметр, второе вхождение) и перенос в другое поле, другой поток или другой постбэк — `400`. Новая запись со скрытым макросом невозможна. Строки без скрытых макросов проверка не сравнивает: правка соседних полей, порядок потоков и постбэков, статусы постбэков меняются свободно. Переименование потока, в ссылке которого стоит скрытый макрос, тоже `400`: имя определяет место строки.
- Регистр не важен.
- Макрос `{имя}` подставляет любой параметр адреса клика, а имя параметра для ключевого слова, Sub ID, дополнительных полей (`site`, `ad_campaign_id`, `creative_id`, `external_id`) и цены клика задают источник трафика и кампания. Поэтому пользователю, у которого скрыто хотя бы одно из полей `keyword`, `sub_id_1`…`sub_id_12`, `site`, `ad_campaign_id`, `creative_id`, `external_id`, `cost`, нельзя писать новый `{имя}`, которого нет в таблице ниже и среди безопасных: ответ `400 macro {имя} may read a hidden field`. Сюда же относятся `{sub_id_13}`–`{sub_id_15}` (журнал хранит только 12 Sub ID, но движок заполняет эти макросы из параметра адреса, который источник привязал к `sub_id_13`…`sub_id_15`) и `{site}`, `{ad_campaign_id}`, `{creative_id}`, `{external_id}`: они читают параметр адреса клика с тем же именем. Имя сверяется с точным написанием: `{Keyword}` — это параметр, а не макрос. Без таких скрытых полей `{имя}` разрешён. Такой макрос, уже стоящий в сохранённой записи на том же месте, сохраняется дословно, как и макрос скрытого поля.
- Таким пользователям нельзя менять привязку параметров: в источнике трафика — имя параметра для `keyword`, скрытых `sub_id_N` и скрытых дополнительных полей, а также для `sub_id_13`…`sub_id_15` (задать, изменить, очистить); в кампании — `cost_param` и `currency_param` при скрытом `cost`; смена источника кампании на источник, у которого скрытое поле или `sub_id_13`…`sub_id_15` привязаны к параметру. Нельзя и привязать видимый параметр источника к имени параметра скрытого поля (привязанному имени, а для `keyword` ещё и к `q`, а также к `keyword` и `utm_term`, пока эти два имени не заняты другим параметром источника, для непривязанного скрытого поля — к его собственному имени): видимое поле получило бы скрытое значение. Та же проверка действует при смене источника кампании: кампанию нельзя перевести на источник (например, подготовленный администратором), где видимое поле читает имя параметра скрытого поля или, при скрытом `cost`, имя цены и валюты этой кампании; кампания, уже сохранённая на таком источнике, без смены источника пересохраняется. Ответ — `400`. Остальные поля источника и кампании меняются свободно, значения параметров скрытых полей остаются как были.
- Скрытая цена (`cost`) защищена и со стороны имён. Имена цены и валюты (`cost_param`, `currency_param`) задаёт кампания, а видимый Sub ID, `keyword` или дополнительное поле читает параметр, который ему назначил источник, а без назначения — параметр со своим именем (`sub_id_N`, `site` и т. д.; `keyword` ещё читает `q` всегда, а `keyword` и `utm_term` — пока они не заняты другим полем или ценой). Если такое имя совпадёт с именем цены или валюты, цена попадёт в видимый Sub ID журнала и в `{sub_id_N}`. Поэтому при скрытом `cost`: источник нельзя сохранить так, чтобы видимое поле стало читать имя цены или валюты любой кампании (новая привязка, привязка нового источника и очистка привязки, после которой поле возвращается к собственному имени); кампании нельзя сменить источник на такой, у которого видимое поле читает имя цены или валюты этой кампании; `cost_param` и `currency_param` менять нельзя вообще. Привязка, уже стоящая в сохранённой записи, и источник кампании без смены источника, где видимое поле уже читало это имя, проходят как есть. Администратор и роль без скрытого `cost` ограничений не имеют. Ответ — `400 source maps <поле>, a hidden field`: в нём только имя поля источника, имя и значение цены не называются. Отказ всё же показывает, совпало ли присланное имя с именем цены; значения цены он не раскрывает.
- Список кампаний для сверки имён цены сервер читает в контексте запроса и только когда параметры источника действительно изменились: пересохранение источника с теми же параметрами (например, переименование) кампании не читает.
- Строка `offer_query` сети дописывается к адресу оффера до подстановки макросов, поэтому на неё действуют те же правила, что на ссылку кампании: скрытый макрос в ней проходит, только если стоит дословно в сохранённой записи, новый `{имя}` при скрытом `keyword`, `sub_id_N`, дополнительном поле или `cost` — `400`. Поле `postback_url` сети движок не читает, это заметка для кабинета партнёра: макросы в нём не проверяются.
- Оффер нельзя привязать к сети, у которой в `offer_query` есть запрещённый пользователю макрос: новый оффер, смена `network_id` и смена `url` оффера такой сети дают `400`. Если у пользователя открыт раздел `networks` и эта сеть ему видна, текст называет макрос: `network offer_query: macro … uses hidden field …`. Иначе текст фиксированный и ничего не говорит о содержимом сети: `network offer_query holds a macro of a hidden field`. Переименование и правка остальных полей такого оффера проходят.
- Если в `curl`, `b_curl` или `remote.url` потока стоит запрещённый пользователю макрос, вывод этого потока заморожен: `out` (весь блок: тип, адрес, офферы, лендинги, заголовок) и вывод для ботов (`bots.redirect`, `bots.out`, `bots.header`) менять нельзя — `400 stream … sends a hidden field`. Остальные поля потока (вес, статус, переключатели ботов) и порядок потоков меняются свободно. Поток находится по имени, при повторяющемся или пустом имени — по позиции.
- Движок подставляет макросы в файл, который назван в `entry` лендинга, а `entry` может указывать на файл в любом каталоге и с любым расширением (имя без расширения выполняется как PHP). Поэтому проверяется любой файл лендинга: `PUT /api/landings/{id}/files/…` и загрузка архива (`POST …/archive`, каждый файл архива, в том числе бинарные) пропускают запрещённый макрос, только если файл с тем же путём уже хранится с теми же байтами. Файл без запрещённых макросов не сравнивается.
- Точку входа выбирает одна функция `config.LandingEntry`, её же вызывает движок: непустой `entry`, прошедший `SafeLandingRel`, → `index.php` → `index.html` → ничего. Недопустимый `entry` (абсолютный путь, `..`, `\`, сегмент с точкой в начале) движок при выборе страницы пропускает и берёт `index.*`; в каталоге такой `entry` не сохраняют — ответ `400 entry must be a relative path inside the landing`. После любой операции, меняющей лендинг (`PUT` записи, `PUT` или `DELETE` файла, загрузка архива — по содержимому архива до распаковки), считается получившаяся точка входа (путь и байты). Тот же файл с теми же байтами — разрешено; другой — его текст проверяется без исключения «те же байты на том же месте», ответ `400 landing entry <путь>: …`. Повторная загрузка того же архива без смены точки входа проходит. Архив больше 50 MiB суммарно, с более чем 2000 записями, не zip, с битой записью или неверной контрольной суммой — `400 bad archive` для всех, без изменений на диске: распаковка идёт во временный каталог `.unzip-<id>-<случайные цифры>` рядом с лендингом, подмена каталога лендинга одним `rename` только при успехе. Каталог лендинга и staging — `0755`, записанные файлы — `0644`. При старте админки `RecoverUnzip(time.Hour)`: осиротевшие `.unzip-*` и `.unzip-*.old` старше часа удаляются; `.unzip-*.old`, если каталога лендинга нет, возвращается на место независимо от возраста. Id лендинга не может начинаться с точки (`config.SafeLandingID`, как у движка). PHP-точка входа проверяется как текст; `include` других файлов остаётся оговоркой про код лендинга ниже. Замена лендинга в потоке на лендинг администратора — сознательно выданное право: проверяется содержимое, а не выбор лендинга.

| Поле | Макросы |
| --- | --- |
| `keyword` | `[KEY]`, `{keyword}` |
| `domain` | `[DOMAIN]`, `[PATH]` |
| `ip` | `[IP]` |
| `country` | `[COUNTRY]`, `[()COUNTRY()]`, `{country}` |
| `city` | `[CITY]`, `[()CITY()]` |
| `region`, `asn`, `org` | `[REGION]`, `[ASN]`, `[ORG]` |
| `timezone` | `[TIMEZONE]`, `[UTC]` |
| `lang`, `device`, `operator` | `[LANG]`, `[DEVICE]`, `[OPERATOR]` |
| `useragent` | `[USERAGENT]` |
| `cid` | `[CID]`, `{subid}` |
| `root_cid` | `{root_subid}` |
| `origin_campaign_id` | `{origin}` |
| `status` | `{status}` |
| `profit` | `{payout}` |
| `sub_id_1`…`sub_id_12` | `{sub_id_N}`; для 1–5 ещё `[PAR-N]` |

Безопасные, не подставляющие значений клика: `[RANDNUM-…]`, `[RANDSTR-…]`, `[RANDLINE-…]`, `[RANDDFL-…]`, `[REMOTE]`, `{offer}`. Макросы `{sub_id_13}`–`{sub_id_15}` читают параметр адреса клика и в безопасные не входят: они лежат в отдельной таблице чтения адреса (`macroQueryRead`) и запрещены по тому же правилу, что новый `{имя}`. Таблицы в коде (`macroFields`, `macroSafe`, `macroQueryRead`) сверяются тестом со списком макросов `internal/render`: новый макрос без записи в таблице тест не пропустит.

Ожидаемое поведение: `{gclid}`, `{clickid}` и любые другие новые `{имя}` для ролей со скрытым `keyword`, `sub_id_N`, `site`, `ad_campaign_id`, `creative_id`, `external_id` или `cost` запрещены, потому что `{имя}` читает любой параметр адреса клика. Нужное имя администратор записывает сам, а роль оставляет его без изменений.

Оговорка: скрытие не закрывает код лендингов. Файл лендинга с собственным JS или PHP может прочитать данные посетителя сам (IP, язык, user-agent) и отправить их куда угодно, а PHP-файл ещё и выполняется; проверка макросов этого не останавливает. Права на запись лендингов стоит давать только тем, кому доверяют. Полный список записываемых маршрутов и полей с макросами сверяется тестами `access_inventory_test.go`: новое поле, тип или маршрут без записи в них тест не пропустит.

## Интеграции (только администратор)

Раздел `integrations` админский: роль не может его выдать, маршруты с `admin: true` в `routeAccess` для обычного пользователя всегда `403 forbidden`, даже если раздел каким-то образом попал в access.

**Keitaro** — `GET/PUT /api/keitaro/settings`, `GET /api/keitaro/status`, `POST /api/keitaro/check`, `POST /api/keitaro/import`, `GET /api/keitaro/job`, `POST /api/keitaro/purge`. Импорт пишет данные в обход проверок макросов, привязок параметров и цены. Тест `TestKeitaroRoutesAreAdminOnly` перечисляет все маршруты `/api/keitaro/` и падает, если новый маршрут доступен роли.

**Namecheap** — учётная запись и проверка API: `GET/PUT /api/registrars/namecheap`, `POST /api/registrars/namecheap/test` (раздел `integrations`). Проверка и регистрация домена: `POST /api/registrars/namecheap/check` и `POST /api/registrars/namecheap/register` помечены `admin: true` (даже пользователь с разделом `domains` не вызовет их). Для роли и обычного пользователя все эти маршруты — `403`.

## AI-ассистент

Раздел `assistant` в коде заложен, но в бете доступ к ассистенту только у администраторов ([AI-ассистент](ai-assistant.md)). Роль и собственный `access` его не открывают: `assistant` не входит в допустимые разделы роли и пользователя, а `GET /api/ai/status` отвечает не-администратору `allowed: false`, остальные `/api/ai/*` — `403`. Настройки ассистента лежат в разделе `integrations` и тоже только для администратора. Открытие для пользователей после беты — одна правка: константа беты и добавление `assistant` в список разделов пользователя.

## Интерфейс

Администратор работает с ролями на странице «Пользователи» (`#/settings/users`): под таблицей пользователей идёт блок «Роли».

- Таблица ролей: название, разделы, скрытые поля, число пользователей, кнопки правки и удаления. «Новая роль» открывает редактор, «Перечитать» вызывает `POST /api/roles/reload` и показывает число ролей.
- Редактор роли — тот же, что «Доступ» пользователя (`accessEditorHTML`, `readAccessEditor`): разделы, режим по каждому ресурсу, скрытые поля. У роли нет режима «выбранные» и нет списков записей: режим «созданные» уходит без `ids` и `labels`. Скрываемые поля берутся из `GET /api/log-fields`, в списке только поля с `hideable: true`, плюс группы «Прибыль и доход» и «Расход» (`cost` заменяет `cost_cents` и `cost_cur`). Поле, уже записанное в роли, остаётся в списке и не теряется при сохранении.
- Ресурс без гранта в редакторе стоит в режиме «По умолчанию (чтение)» и при сохранении без правок остаётся без гранта: сервер читает такой ресурс как `read`, но доступ не расширяется. Записи (`ids`, `labels`), которых нет в каталоге, остаются отмеченными и не теряются.
- Удаление спрашивает подтверждение; роль с пользователями сервер не удаляет (`409 role in use`), интерфейс показывает перевод ответа.
- Хранилище ролей выключено или файл повреждён (`503 roles unavailable`): вместо таблицы стоит понятное сообщение, «Перечитать» остаётся доступной для починки. Выбор роли в форме пользователя при этом пуст.
- Тексты ошибок переведены на три языка: `roles unavailable` (с причиной и без), `user has a role`, `role in use`, `unknown role`, роль для администратора, имя роли занято или неверно, режим `selected` в роли, `macro … uses hidden field …`, `macro {имя} may read a hidden field`, параметры источника и цены кампании скрытого поля, фильтр по скрытому полю, `forbidden`. Любой другой текст на `macro …` показывается по префиксу в общем шаблоне «Макрос не разрешён: …». Переводятся все всплывающие ошибки панели.

### Интерфейс пользователя с ролью

Страницы читают `GET /api/me`: `pages`, `access` и `hidden`. Столбец или карточка скрывается, когда на ней держится скрытое поле:

- `profit` убирает доход, депозит, прибыль, ROI, EPC, uEPC и выплату оффера; `cost` (и `cost_cents`, `cost_cur`) — расход, CPC, ROI и прибыль; `uniq` — уники и uEPC; `bot` — боты;
- `status` убирает лиды, продажи, отклонённые и CR подтверждённых и отклонённых: факты приходят одной строкой `sale`, делить их нельзя, остаются клики, конверсии и CR;
- столбцы журнала и конверсий по скрытому полю не показываются, таблица последних кликов на сводке теряет скрытые поля;
- таблица эффективности сводки, её экспорт, карточки сводки, итоговая полоса кампаний и подсказка графика пропускают скрытые метрики;
- форма оффера при скрытом `profit` не показывает выплату и валюту и не отправляет их: сервер сохраняет прежнюю выплату;
- журнал кликов: при скрытом `uniq` столбца «Визит» нет (иначе каждому не-боту рисовалось бы «повтор»); при скрытых `os` и `browser` нет столбца «ОС / браузер», при одном скрытом показывается только видимая часть;
- карточки сводки по скрытому полю (страна, устройство, ОС, браузер, домен, провайдер) и такие же дополнительные измерения не рисуются и не предлагаются в панелях;
- отсутствующие в ответе ключи интерфейс не требует: `hidden` без списка читается как пустой, а `access.hidden` служит запасным источником;
- форма источника трафика: параметры скрытых `keyword`, `site`, `ad_campaign_id`, `creative_id`, `external_id` и `sub_id_1`…`sub_id_15` (`sourceKeyLocked`) только для чтения; значение на сервер уходит сохранённое. Смена привязки скрытого поля сервер отклоняет (`400`); ключи параметров вне формы при сохранении не теряются;
- кампания: при скрытом `cost` поля `cost_param` и `currency_param` только для чтения и обратно в кампанию не читаются;
- над редакторами потока, ссылок кампании и оффера стоит подсказка: новые макросы `{имя}` вне списка и макросы скрытых полей не сохраняются, поток со скрытым макросом нельзя переименовать, его ссылку и назначение нельзя менять. В редакторе потока, где при скрытом поле в `curl`, `b_curl` или `remote.url` стоит `[..]` или `{..}`, над блоком назначения добавляется предупреждение, что назначение может быть закрыто для изменения. Подсказка только предупреждает, интерфейс правил макросов не знает: решает сервер, отказ `400` приходит переведённым — тексты про параметры источника и цены, смену источника, `network offer_query: …` (внутренний текст переводится отдельно), заморозку назначения потока (`stream … sends a hidden field`) и любой `macro …` по префиксу.

## API

Все маршруты — только кука и раздел `users` (администратор). API-ключ получает `403 cookie session required`.

| Метод | Путь | Тело | Успех | Ошибки |
| --- | --- | --- | --- | --- |
| GET | `/api/roles` | — | `200`, массив ролей по имени, у каждой `users` — число пользователей | `503` файл не используется |
| POST | `/api/roles` | `name`, `access` | `201`, роль | `400` имя, раздел, ресурс, режим, поле; `409` имя занято; `503` |
| POST | `/api/roles/reload` | — | `200 {"status":"reloaded","roles":N}` | `503 roles unavailable: <причина>` |
| GET | `/api/roles/{id}` | — | `200` | `404`; `503` |
| PUT | `/api/roles/{id}` | `name`, `access` (оба необязательны) | `200` | `400`; `404`; `409` имя занято; `503` |
| DELETE | `/api/roles/{id}` | — | `204` | `404`; `409 role in use`; `503` |

Роль назначает `POST /api/users` с `role_id` и `PUT /api/users/{id}` с `role_id`; пустая строка снимает роль. Неизвестная роль, роль для `ADMIN` и роль вместе с собственным `access` — `400`. Запись пользователя без роли не содержит `role_id`.

`GET /api/me` отдаёт действующий доступ: `pages`, `access` (для пользователя с ролью — доступ роли), `role` (`id`, `name`; нет у пользователя без роли или с потерянной ролью) и `hidden` — отсортированный массив скрытых id с учётом групп и производных полей (никогда не `null`; у администратора пустой массив). Интерфейс читает `hidden` и запасной `access.hidden` (`hiddenFields`), по ним прячет столбцы и фильтры.

Скрытые поля в собственном `access` пользователя без роли действуют так же, как в роли: те же API, CSV, офферы, макросы и интерфейс. Запись в `users.json` менять не нужно.

## Откат версии

Сборка без ролей не знает `role_id` и `roles.json`, а собственный доступ пользователя при назначении роли обнулён. Перед откатом: у каждого пользователя с ролью снимите роль (`PUT /api/users/{id}` с `"role_id": ""`) и выдайте собственный доступ (`PUT /api/users/{id}/access`); иначе после отката он останется без разделов. Файл `roles.json` старая сборка не читает и не трогает.
