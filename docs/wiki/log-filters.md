# Фильтры и столбцы журналов

Кнопка «Фильтры» в нижней строке открывает один конструктор. Он есть у журнала кликов, журнала конверсий и отчёта `#/report`. Клики и отчёт фильтруют таблицу `events`. Конверсии фильтруют `conversions`. Набор условий показывает счётчик на кнопке и чипы под ней. Снятие чипа убирает одно условие. «Сбросить фильтры» очищает черновик. «Применить» оставляет строки, у которых выбрано поле и хотя бы одно значение.

## Конструктор

В одной форме каждое поле можно выбрать только в одной строке: занятые поля не предлагаются в других строках. «Добавить фильтр» неактивна, когда свободных полей не осталось или открыто уже 20 строк. В запрос уходит не больше 20 условий. При «Применить» повторы одного поля схлопываются до первой строки (`dedupeConds`). Несколько значений `in`/`nin` — несколько параметров `f` или чипы; для свободных полей Enter и запятая в `in` добавляют отдельные значения. Выбор из списка пишет ключ напрямую в условие, без разбора текста по запятой.

Каталожные поля, страна и статус — только выбор из списка (полные каталоги админки ∪ значения периода из `GET /api/log-values`). Список открывается сразу после выбора поля: кампании, офферы, лендинги, сети, источники, страны и статусы берутся из каталога, пустой ответ периода каталог не прячет. Поток, ОС, браузер, город и подобные — подсказки из log-values, текст допустим. У устройства сразу есть телефон, компьютер и планшет (`phone`, `computer`, `tablet`), остальные значения периода добавляются к ним. Subid, Sub ID, IP, keyword, referer, site, out, xrw, Ad Campaign ID, Creative ID, External ID — свободный ввод. Список под полем: поиск по подстроке без учёта регистра, стрелки и Enter, Esc закрывает список. У операторов «Из списка» и «Исключение списка» значения копятся чипами внутри поля; уже выбранные ключи из списка пропадают; Backspace в пустом вводе снимает последний чип. У «Равно» и «Не равно» остаётся одно значение. В запрос уходит ключ, как в `f=field:op:value`; в списке и в чипе показывается человекочитаемое имя. Статусы — подписи «Лид», «Продажа», «Отклонён» (ключи `lead`, `sale`, `rejected`). Для «Устройство» — фраза и код, например «Мобильный телефон · phone». У оффера, лендинга, сети, источника и id кампании рядом с id — имя из каталога; при наличии группы в каталоге опции группируются с заголовком, без группы — подпись «Без группы». Список ограничен 50 совпадениями; при большем числе строк подсказка просит уточнить поиск.

Поля в конструкторе сгруппированы: Данные, Гео, Устройство, Источник, Sub ID. В списке каждое поле, у которого на этой таблице есть столбец, даже если его волна ещё не готова. Поле без столбца на таблице в список не входит. Поле, которого нет в этих группах, стоит в группе «Без группы». Несколько разных полей в одной форме складываются через «и» и уходят в запрос отдельными `f=`.

## Операторы

| Оператор | Подпись | Смысл |
| --- | --- | --- |
| `eq` | Равно | значение входит в список |
| `ne` | Не равно | значения нет в списке, и само поле не пустое |
| `in` | Из списка | то же сравнение, что у «равно», несколько значений |
| `nin` | Исключение списка | то же, что у «не равно», несколько значений |
| `contains` | Содержит | значение столбца содержит подстроку, без учёта регистра |
| `not_contains` | Не содержит | подстроки в значении нет, и само поле не пустое |

«Содержит» и «Не содержит» есть только у текстовых полей: Subid, Sub ID 1…30, реферер, User-Agent, ключевик, сайт, External ID, Ad Campaign ID, Creative ID, TID, IP, домен, страница, вывод, поток, город, ОС, браузер и подобные. У чисел, дат, ASN, бота, уникальности, страны, устройства, статусов, кампании и её id, id оффера, лендинга, сети и источника этих операторов нет: конструктор их не показывает, а сервер отвечает `400`. Признак берётся из `GET /api/log-fields`: у такого поля `text: true` (`store.Field.Text`, один список на сервер и админку). При смене поля строка с подстрочным оператором возвращается к «Равно», если новое поле не текстовое. Строка держит одно значение, подсказка в поле ввода — «Часть значения». Значение уходит целиком, запятые его не делят; пустое или из одних пробелов — `400`. Несколько `f=` с `contains` одного поля — «содержит любое из», с `not_contains` — «не содержит ни одного».

В ClickHouse условие — `positionCaseInsensitiveUTF8(столбец, ?) > 0` (или `= 0` и `столбец != ''` у «Не содержит»); подстрока передаётся параметром, `%`, `_` и `\` ищутся как обычные символы. Поиск подстроки читает столбец целиком за период, индексы и сортировка таблицы его не ускоряют. Действуют те же лимиты, что у остальных фильтров: период, 20 условий, 200 значений, размер страницы и потолок CSV. На большом периоде сначала сужайте выборку кампанией, страной или датами.

«Равно» и «не равно» в конструкторе держат одно значение. «Из списка» и «исключение списка» копят несколько: Enter или запятая добавляют значение. Пустая строка из поля ввода не уходит.

«Не равно» и «исключение списка» добавляют к сравнению требование, что значение столбца не пустая строка. Строка с пустым городом не попадает в выборку «город не равно Warsaw». Ноль ASN в измерении тоже считается пустым: в сравнении он выглядит как пустая строка, а не как `AS0`.

У статуса перед сравнением значение обрезается по краям и приводится к нижнему регистру. Остальные поля сравниваются как введены.

## Формат `f=`

Повторяемый параметр `f=field:op:value`. Двоеточие делит строку на три части, значение может содержать свои двоеточия. Одинаковые поле и оператор склеиваются в одно условие, в порядке первого появления. Несколько `eq` одного поля становятся `in`, несколько `ne` — `nin`. У `contains` и `not_contains` значение не делится по запятой и не экранируется, как у `eq` (`f=sub_id_1:contains:abc`). Пустое значение после второго двоеточия сохраняется.

У `in` и `nin` одно значение в параметре может перечислять несколько элементов через запятую, как в старых закладках (`f=country:in:ru,us` → `ru` и `us`). Несколько параметров `f` с тем же полем и оператором объединяются в один список; разбор каждого значения идёт **до** слияния повторных `eq`/`ne` в `in`/`nin` (например `f=site:eq:a,b` и `f=site:eq:c` → `in` с двумя значениями `a,b` и `c`, а не три части `a`, `b`, `c`). Экраны только `\\` и `\,`; любой другой одиночный `\` в значении сохраняется (`C:\tmp` остаётся как есть). У `eq` и `ne` значение в URL **не** экранируется и **не** раскодируется, запятая внутри одного `f=` не делит значение. У `in`/`nin` при сборке ссылки админка экранирует `\` и `,`; на сервере после split применяются только `\\` и `\,`. В конструкторе условия хранятся как введены; ручной ввод для `in`/`nin` делится по запятой один раз (части с trim); выбор из списка кладёт ключ целиком. SPA **не** читает `f=` из адресной строки — только формирует параметры для API. Кампания без имени в `campaign` / `origin_campaign` не предлагается — только через `campaign_id` / `origin_campaign_id`.

Незнакомое поле, поле без столбца на этой таблице, оператор вне шести (`eq`, `ne`, `in`, `nin`, `contains`, `not_contains`; список — `store.CondOps`), подстрочный оператор у нетекстового поля или с пустым значением, пустой список значений, больше 20 условий или больше 200 значений в одном условии дают `400` и текст `bad filter:`. Скрытое для роли или ключа поле нельзя фильтровать никаким оператором: `400` и `bad filter: hidden field`.

Фильтр по полю, чья волна на таблице ещё не готова, не отвечает ошибкой: журнал отдаёт пустую страницу и запрос не выполняет. Сводка и список значений в этом случае отдают пустой список и `200`.

`GET /api/log-fields` отдаёт каталог полей и готовность волн `ready`. Без статистики каталог всё равно `200`, а `ready` пустой. `GET /api/log-values` принимает `table` (`events` или `conversions`), `field`, `from`, `to` и `limit`. `limit` не больше 500, пустой или больший становится 500. Поле без измерения — `400`. Неготовая волна — `200` и пустой список.

Старое имя измерения `group` сервер читает как `campaign`.

## Лимиты страниц

Журнал кликов `GET /api/logs`: `limit` по умолчанию 100, потолок 1000, `offset` ниже нуля становится нулём. CSV `GET /api/logs/export` берёт те же фильтры, `offset` 0 и не больше 50 000 строк. При обрезке сервер ставит `X-Export-Truncated: 1`; админка скачивает файл через `fetch` и показывает предупреждение. Ячейка, которая начинается с `=`, `+`, `-`, `@` или перевода строки, получает ведущий апостроф.

На вкладке «Трафик» журнала кликов внизу закреплён блок: итог «Клики N», пагинация (назад, вперёд, размер страницы, диапазон «с–по из N») и экспорт CSV/HTML справа. Размер страницы по умолчанию 100, хранится в аккаунте. На вкладках «Postbacks и S2S» и «Системный» блок скрыт; таблица postback-log сортируется в браузере по заголовкам.

Журнал конверсий `GET /api/postbacks`: вместе со старыми параметрами принимает `f=`, `limit` и `offset`. Внизу закреплён блок: итог «Конверсии N», сумма дохода за период, пагинация и экспорт. Размер по умолчанию 50, потолок своего значения 1000. Смена страницы запрашивает новый `offset`. У API `limit` выше 1000 возвращается к 200.

## Сортировка столбцов

Клик по заголовку сортируемого столбца включает сортировку; повторный клик разворачивает порядок. Текстовые столбцы первым кликом идут А–Я, числовые и даты — по убыванию. У заголовка показывается `aria-sort` и стрелка.

Журнал кликов и журнал конверсий сортируются на сервере по всему выбранному периоду: в запрос добавляются `sort` (имя поля из каталога) и `dir=asc|desc`, страница сбрасывается на первую. Без сортировки сервер отдаёт клики по времени по убыванию. Не сортируются: OS / browser, Visit, период продажи, группа кампании, столбцы `*_num`, маски IP, User-Agent, реферер, вывод, страница и любой столбец, которого нет в готовых полях этой таблицы. Если запрос с сортировкой не прошёл, таблица один раз перезагружается без `sort` и `dir`; сохранённая в аккаунте сортировка не стирается.

Остальные таблицы админки (кампании, каталоги, отчёт, API-ключи, пользователи и др.) сортируют уже загруженные строки в браузере. Строка «Всего» в отчёте остаётся внизу; экспорт отчёта учитывает текущий порядок строк.

`GET /api/report` принимает `f=` по кликам. Без параметров страницы ответ прежний: массив строк, группы кликов режутся лимитом `store.SliceLimit` (2000, по убыванию визитов); с `meta=1` ответ `{rows, truncated}`, и `truncated: true` значит, что групп было больше лимита (запрос просит 2001). Конверсии этим лимитом не режутся: группы вне лимита приходят строками с `hits = 0`.

Постраничный режим включается любым из `limit`, `offset`, `sort`. `limit` — от 1 до 100000, по умолчанию 1000; `offset` — от 0; `sort` — `group`, `stream`, `country`, `offer`, `source`, `hits`, `uniq`, `bots`, `conv`, `cr`, `profit`, `depsum`, `cost`; `dir` — `asc` или `desc` (по умолчанию `desc`). Ответ — `{rows, total, offset, limit, sort, dir, sort_cur, totals, truncated}`. Сервер читает до 100000 групп визитов (`store.PageMaxRows`), сливает с ними расход и конверсии, сортирует весь набор и отдаёт окно. При равных значениях порядок решают кампания, поток, страна, оффер и источник по возрастанию, поэтому граница страницы не плавает между запросами. CR сортируется как `conv / max(hits, 1)`, оффер и источник — по названию из каталога, страна — по коду. Расход сортируется по одной валюте, той, где общий расход больше (`sort_cur`); строки без расхода в ней идут в конце при любом направлении. `totals` — суммы всего набора: `hits`, `unique` (сумма `uniq_first`), `bots`, `conv`, `profit`, `depsum`, `cost` по валютам; проценты в итогах не складываются, а считаются из сумм. Если групп больше 100000, `truncated: true`: в строках только первые 100000 групп по визитам, а визиты, уники и боты в `totals` досчитывает отдельный запрос по всем событиям. Плохие `limit` или `offset` — `400 bad page`; неизвестная сортировка, плохой `dir` или сортировка по полю, скрытому от роли, — `400 bad sort`.

Страница `#/report` ходит в постраничном режиме. Над таблицей и под ней — общий пагинатор: первая, предыдущая, номера страниц, следующая, последняя, «Строки 1–1000 из N» и выбор 100, 500, 1000 или 2000 строк на странице. Размер страницы хранится в виде страницы `report` (`page`). Сортировка по столбцу, новый фильтр, период и вход на страницу возвращают на первую страницу. Пока идёт запрос, таблица и пагинаторы приглушены. Строка итогов видна всегда и подписана «Итого по всем строкам: N». При `truncated` над таблицей спокойная заметка, что в отчёте 100000 групп с наибольшим числом визитов, а итоги учитывают все визиты. Экспорт с `#/report` — значок с меню CSV/HTML: файл получает весь набор в текущей сортировке одним запросом до 100000 строк вместе с итогами; если строк больше, тост говорит, сколько попало в файл. `GET /api/stats/breakdown` принимает `dim`, `limit` и `f=` по кликам. `limit` пустой или выше 1000 становится 50. Сводка запрашивает шесть значений. Измерение вне каталога или поле без измерения — `400`. Неготовая волна измерения — пустой список и `200`.

`GET /api/stats/summary`, `GET /api/stats/timeseries`, `GET /api/stats/performance` и `GET /api/stats/facts` принимают `from`, `to` и те же `f=` по кликам. У ряда timeseries параметр `step` в секундах, не меньше 3600.

## Виды таблиц аккаунта

Сортировка, фильтры, столбцы и размер страницы каждой таблицы — настройка пользователя, а не браузера. Они лежат в `views.json` рядом с `ui.json` (путь переопределяет `EMTDS_VIEWS_FILE`), запись на пользователя: `uid` из `users.json` или `env:<логин>` для администратора окружения. Чтение — `GET /api/me/views`, запись — `PUT /api/me/views` всем объектом, только сессией браузера, не больше 64 КБ. Неизвестные страницы сервер отбрасывает.

Страницы: `range` (период), `dashboard`, `flows`, `logs`, `conversions`, `report`, `offers`, `networks`, `landings`, `sources`, `domains`, `users`, `roles`, `keywords`, `keyword_stats` (кампания, условия и сортировка статистики по ключам, см. [ключевые слова](keywords.md)), `automation` (порядок карточек). Панели «Кто заходит» и своё измерение тоже в снимке аккаунта, страница `dashboard`. Внутри — `sort` `{k, dir}`, у журналов и отчёта `conds`, у страниц со шестерёнкой `cols` `[{id, on}]`, у кампаний, кликов, конверсий и доменов `page`, у кампаний ещё `q`, `state`, `source`, `folder`, `view` (`table` или `grid`) и `compact`, у кликов `tab` и `pblogSort`. Нет `cols` — у аккаунта своего набора столбцов нет.

Виды применяются при входе до первой отрисовки, поэтому таблица сразу открывается с прежней сортировкой. Клик по заголовку и «Применить» в окне столбцов пишут сразу, поиск и фильтры — после паузы 400 мс. При закрытии вкладки, уходе в фон и выходе недосланный снимок отправляется. При возврате на вкладку виды перечитываются не чаще раза в 5 секунд: настройка из другого браузера подхватывается, а старая вкладка её не перезаписывает. Если в этой вкладке есть недосланные изменения, они важнее. Размер страницы, вид и компактность кампаний, которые раньше лежали в `localStorage`, при первом входе переносятся в аккаунт, и ключи браузера удаляются. Тема, язык, пояс и порядок пунктов меню остаются в браузере.

## Столбцы по умолчанию

Шестерёнка есть у журнала кликов, журнала конверсий и отчёта. Порядок и включение хранятся в аккаунте (поле `cols` страницы в `/api/me/views`, см. «Виды таблиц аккаунта»). Пока у аккаунта своего набора нет, берётся общий набор из `ui.json` (`cols`), а без него — набор ниже. `PUT /api/ui` админка столбцами больше не пишет. Порядок столбцов сохраняется только кнопкой «Применить» в окне колонок, а флаг миграции столбцов кампаний ставится после успешной записи. Сброс возвращает набор ниже. Пока хотя бы один столбец включён, последний включённый снять нельзя.

Клики, включены: время клика, кампания, поток, страна, устройство, OS / browser, бренд, Visit, IP, ключевик, вывод.

Клики, выключены: город, регион, язык, оператор, тип, реферер, User-Agent, домен, subid, ASN, провайдер, часовой пояс, Sub ID 1…30, оффер, лендинг, партнёрская сеть, источник, числовые id оффера, лендинга, сети и источника, id кампании, сайт, X-Requested-With, Ad Campaign ID, Creative ID, External ID, обе маски IP, версия ОС, версия браузера, поисковик, уникальность, Via, страница.

Конверсии, включены: subid, Sub ID 1, Sub ID 2, кампания, первоисточник (`origin_campaign`), поток, оффер, партнёрская сеть, страна, доход, статус, время конверсии, период продажи, оригинальный статус, город, регион.

Конверсии, выключены: группа кампании, лендинг, источник, сайт, X-Requested-With, реферер, поисковик, ключевик, id кампании, числовые id каталога, Ad Campaign ID, External ID, Creative ID, Sub ID 3…30, оператор, провайдер, язык, устройство, User-Agent, ОС и версия, браузер и версия, бренд, IP и обе маски, время клика, предыдущий статус, TID, домен, страница.

Отчёт, включены: кампания, поток, страна, оффер, источник, визиты, уники, боты, конверсии, прибыль, DepSum, расход. CR выключен.

Столбец «Расход» показывает цену кликов строки (`cost` в `GET /api/report`: центы по коду валюты, пустой код — USD). Он появляется, только если хотя бы у одной строки периода есть цена; без данных его нет в таблице, CSV и HTML. Итог складывает расход по каждой валюте отдельно, несколько валют пишутся через «·». В CSV расход одной валюты — число, а валюта стоит в заголовке; при нескольких валютах ячейка остаётся текстом. Сортировка идёт по одной валюте — той, где расход строк больше всего (подсказка заголовка «Сортировка по USD»); строки без расхода в ней остаются в конце при любом направлении. ROI, прибыль и uEPC из расхода в отчёте не считаются. Ячейки расхода вне обрезанных `store.SliceLimit` строк не добавляются. Пользователь со скрытым `cost` столбца не видит, ключ `cost` из ответа убирается.

## Вычисляемые столбцы

Их нет в каталоге `GET /api/log-fields`. Значение считается в браузере из уже пришедшей строки.

Период продажи — разница между временем конверсии и временем клика. Нет времени клика или нечитаемой даты — пусто. Отрицательная разница показывается как ноль. От суток — дни и часы, иначе часы и минуты, иначе минуты, иначе секунды. Столбец виден, когда готовы и время конверсии, и `click_ts`.

IP 1.2.*.* оставляет два первых октета IPv4, IP 1.2.3.* — три. Адрес не из четырёх десятичных октетов даёт пустую ячейку. Оба столбца выключены и зависят от поля `ip`.

OS / browser на кликах склеивает ОС и браузер. Visit показывает бота, уникальный визит или повтор. Группа кампании — папка кампании из каталога, не столбец журнала. Столбцы «ID оффера», «ID лендинга», «ID сети» и «ID источника» показывают числовой id. Соседние столбцы с теми же полями показывают имя из каталога.

ASN в ячейке и в измерении пишется с приставкой `AS`. Ноль остаётся пустым.

Волна `net` на кликах — ASN, провайдер, часовой пояс, Via. Волна `click` на обеих таблицах — Sub ID 1…12, оффер, лендинг, источник, сеть. Волна `sub` на обеих таблицах — Sub ID 13…30 (`String`, миграция `011_sub_id_30.sql`). Движок эти колонки сам не добавляет. Пока миграцию не применили, фильтр по Sub ID 13…30 отдаёт пустую страницу и запрос не выполняет, а столбцы в шестерёнку не попадают. Старые строки не переписываются: новые колонки пустые. На конверсиях в `ext` ещё регион, язык, ОС, версия ОС, браузер, версия браузера, бренд, IP, ключевик, поисковик, реферер, User-Agent, id кампании, ASN, провайдер, время клика, оригинальный статус, предыдущий статус и TID. Волна `model` на обеих таблицах — `device_model` (`LowCardinality(String)`, миграция `007_device_model.sql`). Движок добавляет колонку сам при старте (`ALTER … ADD COLUMN IF NOT EXISTS`). Старые строки остаются с пустой моделью. Строки конверсий берут модель клика при записи; импорт Keitaro пишет `device_model` из журнала Keitaro. В CSV журнала конверсий после `device_model` стоит `depsum`. Модель в фильтре журнала и в отчёте сравнивается как обычное поле. Волна `step` — только таблица `events`: колонка `step` (`UInt8`, `DEFAULT 0`, миграция `008_step.sql`). `1` — второй шаг клика: запрос `/offer` с `cid`, который движок выдал на лендинге; такое событие несёт `cid` лендинга. `0` — первый шаг: лендинг, прямой оффер и любой запрос `/offer` без своего `cid` (без `cid` или с чужим); у такого запроса общий ключ уникальности первого шага и полная цена. Движок добавляет колонку сам при старте, а `ADD COLUMN` с постоянным `DEFAULT` меняет только метаданные таблицы и не пересобирает куски; строки, записанные раньше, читаются как `0`. Импорт Keitaro пишет `step = 0`. Поле `step` служебное: его нет в списке полей интерфейса, в журнале, в CSV и в редакторе ролей, и конструктор фильтров его не предлагает. Порядок выкатки: применить `008_step.sql` или запустить новый образ, затем проверить колонку `SELECT name FROM system.columns WHERE database = 'emtds' AND table = 'events' AND name = 'step'`. Пока колонки нет, движок пишет в лог при старте предупреждение, а шаг `/offer` пишет уникальность по общему ключу первого шага, поэтому уники кампании не удваиваются; после появления колонки перезапустите движок.

Уники кампании и потока считаются по первому шагу (`uniq = 1 AND step = 0`): сводка дашборда, график, performance, переданные визиты (`addForwarded`: визит, который поток передал в другую кампанию, добавляется потоку-отправителю по тому же правилу) и веса ручного расхода. Когда условие отбирает события по офферу или сети (`eq`, `in`), считается обычный `uniq = 1`: оффер и сеть стоят на шаге `/offer`, и нужен уник самого оффера. Отчёт считает уники по тому же правилу: пока он группирует по офферу (столбец оффера есть, когда есть колонки кликов), строка несёт свои уники, у строки лендинга и строки оффера они свои, и складывать `unique` по строкам нельзя. Рядом в строке отчёта лежит `uniq_first` — уники первого шага; их сумма по строкам равна уникам сводки. Ячейки строк отчёта показывают `unique`, а строка итогов на странице, в CSV и в HTML суммирует `uniq_first` (если поля нет в строках, старый бэкенд, — `unique`); CR итога пересчитывается из сумм, `uniq_first` отдельным столбцом не показывается, и скрытый `uniq` убирает столбец и итог уников. Фактические данные каталога строк не фильтруют по шагу: у лендинга и оффера уник свой, уники разных шагов не складываются. В фактических данных каталога у строки есть `uniq` (свои уники строки) и `uniq_first` (уники первого шага); сумма `uniq_first` по строкам кампании равна уникам кампании. Клики (hits) считаются по каждому событию. Цена клика пишется на строку первого шага. Строка шага `/offer` несёт ноль центов и ту же метку валюты: так видно, что клик пришёл с ценой. Поэтому фильтр по `cost_cur` находит и строку лендинга, и строку шага оффера, а ручной расход пропускает клик с центами или с меткой валюты и не оплачивает его второй раз. В фактических данных каталога валюта строки без центов пуста, поэтому метка шага оффера не открывает отдельную валюту.

У этих полей на кликах волна другая: регион, язык, ОС, браузер, IP, ключевик, поисковик, реферер, User-Agent и id кампании лежат в `base`, ASN и провайдер — в `net`.

Пока волна не готова, столбец не попадает в шестерёнку. В конструкторе фильтров поле со столбцом на таблице остаётся. `GET /api/log-fields` показывает это в `ready`: для таблицы и имени волны `false`. База в этой карте всегда готова.

Волна `origin` — `origin_campaign` и `origin_campaign_id` на кликах и конверсиях (`010_origin.sql`). Фильтр по названию первоисточника сравнивает строку с учётом регистра. Движок раз в минуту перепроверяет наличие колонок, пока волна не готова, и начинает писать их без перезапуска процесса.

Волна `root` (`015_root.sql`) — `root_cid` на кликах и конверсиях и, только на конверсиях, `origin_stream_name` и `origin_keyword`. Все колонки `String` с `DEFAULT ''` (у потока — `LowCardinality`). Пустой `root_cid` значит, что клик сам корень. Миграция только добавляет колонки, старые строки не переписываются и читаются пустыми. В шестерёнке столбцы выключены. Клик цепочки пишет корневой cid, прямой клик оставляет поле пустым. Конверсия копирует его и, когда строка корня найдена, поток и ключ первого клика. Набор колонок читается при старте. Пока волна origin или root не готова, процесс раз в минуту перечитывает `system.columns` и включает её без перезапуска.

## Срок хранения копий

Таблица `events` удаляет строку через 365 дней после `ts`: актуальный TTL задаёт `migrations/clickhouse/009_events_ttl.sql` (`MODIFY TTL ts + INTERVAL 365 DAY`, `materialize_ttl_after_modify = 0`). На чистой базе init-скрипты сначала создают таблицу с 21 днём в `001_events.sql`, затем `009` выставляет год. Таблица `conversions` удаляет строку через 365 дней после `ts`: `TTL ts + INTERVAL 365 DAY` в `migrations/clickhouse/004_conversion_status.sql`. Столбцы `ip`, `useragent` и `referer` в `conversions` — обычные колонки той же таблицы, своего TTL у них нет. Копия живёт столько же, сколько строка конверсии: 365 дней от времени постбека. Срок клика в `events` на эту копию не влияет.

Порядок выкатки на существующей базе: выполнить `009_events_ttl.sql` вручную (или дождаться прогона init только на новой базе — на уже живой ClickHouse каталог init не перезапускается). Проверка: `SELECT create_table_query FROM system.tables WHERE database = 'emtds' AND name = 'events'` — в определении есть `toIntervalDay(365)`.

Индекс `idx_cid` на `events` (`013_events_cid_index.sql`, `bloom_filter(0.01) GRANULARITY 1`) движок ставит сам при старте, только метаданными. Старые куски получают его ручным `MATERIALIZE INDEX` — порядок в [Производительность](performance.md).
