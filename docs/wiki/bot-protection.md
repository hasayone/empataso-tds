# Защита от ботов

Два независимых уровня. Профиль установки решает, бот ли посетитель, до выбора потока: от него зависит правило `bot`. Переключатели потока в блоке «Боты» срабатывают уже после выбора: они пишут метку в журнал и заголовок `X-Kuztds-Bot` и могут отдать боту другой ответ. На правило `bot` этот второй проход не влияет.

## Профиль установки

Карточка «Защита от ботов» на странице `#/settings` (меню «Профиль»), раздел «Защита от ботов». Раздел доступа `bot_protection` есть у администратора.

`GET /api/bot-protection` отдаёт набор. `PUT /api/bot-protection` сохраняет его. Тело — поля `config.Bots`, кроме ответа: `redirect`, `out` и `header` при записи обнуляются. Файл — `bot_protection.json` рядом с `groups.json` (`KUZTDS_BOT_FILE`). Нет файла, файл не читается или JSON не разбирается — набор по умолчанию (`DefaultBotProfile`). Путь к файлу не задан — запись отвечает `503`.

По умолчанию включены подписи User-Agent (`ch_ua`), пустой User-Agent (`ch_empty_ua`) и IP-списки поисковиков (`ch_bot_ip_baidu`, `ch_bot_ip_bing`, `ch_bot_ip_google`, `ch_bot_ip_mail`, `ch_bot_ip_yahoo`, `ch_bot_ip_yandex`, `ch_bot_ip_others`). `ch_proxy` и `ch_non_mobile` выключены. Выключены и пустой реферер, пустой язык, IPv6, PTR, чёрный список User-Agent и `save_ip`. Ложь в файл не пишется.

На той же карточке чёрный список User-Agent: одна полная строка на линию, совпадение точное. Это файл `ua_blacklist.dat`, его пишут через `PUT /api/lists/ua_blacklist.dat`.

Движок читает профиль до выбора потока, когда загружены и подписи, и индекс IP. Любая непустая метка включает признак `bot` у посетителя. Правило потока `bot`: `0` — не фильтрует, `1` («да») — только боты, `2` («нет») — только люди. Сам ответ профиля не задаёт.

## Фильтры потока

Обычный поток берёт первое совпадение. `filter_or: true` — пункт «любое из этих условий»: хватает одного настроенного условия. «Все эти условия» оставляет флаг выключенным. На схеме между условиями стоит «или». Лимит показов остаётся обязательным и проверяется последним; условие, которое не прошло, счётчик не тратит. Подробнее — [правила потока](router-rules.md).

`bot`, `proxy` и `ip_version` устроены как `0` / `1` / `2`.

- `bot`: `1` — только боты, `2` — только люди. Признак ставит профиль, не блок «Боты».
- `proxy`: `1` — «только прокси», `2` — «без прокси».
- `ip_version`: `1` — «только IPv4», `2` — «только IPv6». IPv4 включает IPv4-mapped. Невалидный адрес не проходит ни `1`, ни `2`.

Списки в редакторе:

- IP-список (`ip_list`): «в списке» — флаг `2`, «не в списке» — флаг `1`. В редакторе адреса чипами; в правиле остаётся имя файла `.dat`.
- User-Agent (`ua_text`): «содержит» — флаг `2`, «не содержит» — флаг `1`. Сравнение — подстрока, без учёта регистра, либо выражение `/…/`.
- Параметр URL (`get`), в том числе Sub ID 3: значение `sub_id_3=…` или одно имя. «Равно» — флаг `2`, «не равно» — флаг `1`. Имя без значения требует непустой параметр. Сравнение значения без учёта регистра.

В режиме «или» условие списка проходит, когда посетитель совпал с флагом `2`, и проходит у всех, кто не совпал, при флаге `1`. Список, которым ловят, ставят на `2`.

## Переключатели потока

Блок «Боты» в редакторе потока, подпись «Считать ботом, если». Те же поля `ch_*`, что у профиля, плюс ответ. После выбора потока детекция идёт по ним заново и возвращает метку для журнала и заголовка `X-Kuztds-Bot`. Пустая метка в заголовке пишется как `-`. Если поток не выбран, для журнала остаются только подписи User-Agent.

Пустой `redirect` и значение `skip` («то же, что люди») оставляют обычный ответ потока. Метка в журнал всё равно пишется. Другой `redirect` подменяет ответ: тело из `out`, тип из `header`, если он задан.

`save_ip` («дописывать IP найденных ботов в списки поисковиков») дописывает IP в `ip_<метка>.dat` только для меток `baidu`, `bing`, `google`, `mail`, `yahoo` и `yandex`, и только если этой строки в индексе ещё нет. Процесс помнит уже дописанный адрес до перезапуска. Метки `proxy` и `device` в файл не попадают. Шаг `save_ip` стоит до проверки IP-списков поисковиков, поэтому одно попадание в такой список файл в этом проходе не пополняет.

## Порядок проверок

Функция `detectBot` берёт первую сработавшую включённую проверку. Дальше список не идёт, кроме `save_ip` и блока IP-списков ниже.

1. Подписи (`ch_ua`). Сначала подстрока User-Agent: `baidu`, `bing` (и `msnbot`), `google`, `mail.ru` → метка `mail`, `yahoo`, `yandex.com/bots` → метка `yandex`. Затем подстрока из `signature_ua.dat` → `sign_ua`. Если метки нет — подстрока реферера из `signature_ref.dat` → `sign_ref`. Пустой User-Agent подписями не бот. Имена в `signature_ua.dat` правят в «Списках», одна подстрока на строку.
2. Прокси (`ch_proxy`). Посетитель с признаком прокси → метка `proxy`.
3. Не телефон и не планшет (`ch_non_mobile`). Тип `computer` → метка `device`. Телефон, планшет и пустая строка типа эту метку не получают. На клике пустой User-Agent уже разобран как `computer`, поэтому при включённой проверке он получает `device`.
4. IPv6 (`ch_ipv6`). Адрес задан и это не IPv4 → метка `ipv6`. У обычного клика IPv4-mapped уже приведён к IPv4, метка ему не ставится.
5. Пустой User-Agent (`ch_empty_ua`). Пустая строка или один пробел → `empty_ua`.
6. Пустой реферер (`ch_empty_ref`). Пусто или «-» → `empty_ref`.
7. Пустой язык (`ch_empty_lang`). Пусто или «-» → `empty_lang`.
8. PTR (`ch_ptr`). Обратная зона, ожидание до 2 секунд, берётся первое имя. В имени ищутся `baidu`, `bing` или `msnbot`, `google`, `mail.ru`, `yahoo`, `yandex` — метка того же движка. Нет совпадения — проверка метку не ставит.
9. Чёрный список User-Agent (`ch_list_ua`). Точное равенство строке из `ua_blacklist.dat` → `ua_blacklist`.
10. `save_ip`, если метка уже есть. См. выше.
11. IP-списки поисковиков, если метки всё ещё нет. Порядок: `baidu`, `bing`, `google`, `mail`, `yahoo`, `yandex`, `others`. Файлы `ip_<имя>.dat`. Берётся первое попадание, метка — имя списка.

## Как узнаётся прокси

На клике внешние API не вызываются. Признак прокси локальный, один и тот же у правила `proxy`, у проверки `ch_proxy` и у поля `proxy` в справочнике IP и в симуляторе.

Сначала адрес ищут в `ip_proxy.dat`. Если его там нет, название организации из базы ASN сравнивают с подстроками из `proxy_org.dat`. Регистр не учитывается. Пустая организация и «-» не прокси.

`proxy_org.dat` в каталоге данных заменяет встроенный список `internal/detect/proxy_org.dat`. Пока файла нет, работает встроенный. Правка — «Списки», `GET` и `PUT /api/lists/proxy_org.dat`. Пустые строки и строки с `#` не читаются.

Список `ip_proxy` наполняет работа cron `ip_lists` («Списки IP ботов» в «Автоматизации»). У новой установки работа выключена, пока её не включат. В том же наборе по умолчанию есть источники краулеров (`ip_google`, `ip_bing`, `ip_others` и другие). На `ip_proxy` из них смотрят пять:

| Источник | Режим |
| --- | --- |
| `https://raw.githubusercontent.com/X4BNet/lists_vpn/main/output/datacenter/ipv4.txt` | replace |
| `https://raw.githubusercontent.com/X4BNet/lists_vpn/main/output/vpn/ipv4.txt` | merge |
| `https://iplists.firehol.org/files/proxylists_1d.ipset` | merge |
| `https://iplists.firehol.org/files/socks_proxy_1d.ipset` | merge |
| `https://iplists.firehol.org/files/tor_exits.ipset` | merge |

Уже сохранённый конфиг эти строки сам не получает: массив источников в файле заменяет набор по умолчанию целиком. Их добавляют вручную в «Автоматизации», работа `ip_lists`.

Результат `ip_lists` — одно число на файл, сколько строк в нём после последнего источника, который этот файл записал. Имена по алфавиту через запятую: `ip_google: 1657, ip_proxy: 58773`. Ошибка запуска — отдельное поле `error` статуса и отдельная строка в карточке; текст результата остаётся в `message`.

Бейдж службы (`serviceBadge`): при ошибке конфига — «Ошибка конфигурации», в подсказке текст `config_error`. «Не настроено» — у Telegram без токена или чата и у geo без источников или без обоих файлов; если источники есть, а обоих файлов нет, подсказка «Файл не найден». Пока успешного запуска не было — «Ждёт первого запуска». После запуска бейдж показывает следующий запуск.

## Аналог потока Bot Protection

Поток с «любое из этих условий» (`filter_or: true`). Хватает одного условия. При обычном выборе берётся первый подходящий поток, поэтому этот ставят выше остальных. Ответ задаёт блок «Тогда»; для ловушки это обычно «Стоп» или 404. Лимит показов, если он включён, всё равно обязателен.

- Бот: «да» (`bot: 1`) — только боты. Признак ставит профиль установки.
- Прокси: «только прокси» (`proxy: 1`).
- Тип устройства — одна проверка на три флага. В редакторе отмечено значит разрешено, флаг `1` тип отсекает. Чтобы условие в режиме «или» прошло у компьютера, телефоны и планшеты оставляют неотмеченными (`phone: 1`, `tablet: 1`). Телефон и планшет тогда этому условию не проходят. На клике пустой User-Agent уже является `computer`.
- Списки, которыми ловят посетителя, стоят на флаге `2`, иначе при «или» условие пройдёт у всех, кто в список не попал. IP-список — «в списке». User-Agent — «содержит». Sub ID 3 — параметр URL `sub_id_3=…`, режим «равно».

На схеме между условиями стоит «или». Перенос такого потока из Keitaro описан в [переносе из Keitaro](keitaro.md).

## Симулятор и справочник IP

«Инструменты». «Проверить посетителя» ходит в `POST /api/simulate`. Ответ показывает, какой поток подошёл и какое правило отсекло остальные. В объекте `visitor` есть поле `proxy`. Правила потока, включая `proxy` и `ip_version`, проверяются. Детекция ботов не запускается: лимит показов и антифлуд тоже не тратятся.

`GET /api/lookup?ip=` отдаёт то, что движок узнал бы по адресу. В объекте `visitor` есть поле `proxy`. Негодный адрес отвечает `400`.
