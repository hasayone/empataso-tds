# Защита от ботов

Два независимых уровня. Профиль установки решает, бот ли посетитель, до выбора потока: от него зависит правило `bot`. Переключатели потока в блоке «Боты» срабатывают уже после выбора: они пишут метку в журнал и заголовок `X-Emtds-Bot` и могут отдать боту другой ответ. На правило `bot` этот второй проход не влияет.

## Профиль установки

Карточка «Защита от ботов» на странице `#/settings` (меню «Профиль»), раздел «Защита от ботов». Раздел доступа `bot_protection` есть у администратора.

`GET /api/bot-protection` отдаёт набор. `PUT /api/bot-protection` сохраняет его. Тело — поля `config.Bots`, кроме ответа: `redirect`, `out` и `header` при записи обнуляются. Файл — `bot_protection.json` рядом с `groups.json` (`EMTDS_BOT_FILE`). Нет файла, файл не читается или JSON не разбирается — набор по умолчанию (`DefaultBotProfile`). Путь к файлу не задан — запись отвечает `503`. Движок проверяет файл не чаще раза в 5 секунд: сохранённый профиль действует на клики не позже чем через 5 секунд ([Кэши горячего пути](hot-path-caches.md)).

По умолчанию включены подписи User-Agent (`ch_ua`), пустой User-Agent (`ch_empty_ua`), IP-списки поисковиков (`ch_bot_ip_baidu`, `ch_bot_ip_bing`, `ch_bot_ip_google`, `ch_bot_ip_mail`, `ch_bot_ip_yahoo`, `ch_bot_ip_yandex`, `ch_bot_ip_others`) и проверка прокси (`ch_proxy`, но с оговоркой: [ниже](#прокси-по-умолчанию)). Выключены `ch_non_mobile`, пустой реферер, пустой язык, IPv6, PTR, чёрный список User-Agent и `save_ip`. Ложь в файл не пишется. Единственное исключение — `ch_proxy`: явное `false` в файле остаётся, потому что отсутствие ключа теперь значит «по умолчанию включено».

`PUT /api/bot-protection` не заменяет файл целиком, а сливает тело с сохранённым профилем по ключам: ключи тела заменяют сохранённые, ключи, которых в теле нет, остаются. Поэтому клиент, который не показывает какой-то переключатель (например `save_ip`), его не теряет. Значение `null` убирает ключ. Неизвестные ключи и `redirect`, `out`, `header` отбрасываются. Не объект, не булево значение переключателя или тело больше 1 МиБ — `400`. В ответ идёт то же, что отдаёт `GET`.

Ответ `GET` и `PUT` — это переключатели, которые включены (выключенные не пишутся), плюс три служебных ключа:

- `ch_proxy` — всегда есть, `true` или `false`: так видно состояние галки. Если в файле ключа нет, показывается `true`.
- `proxy_default` — `true`, когда в файле нет значения `ch_proxy` (или файла нет совсем) и действует умолчание.
- `private_relay` — `true`, когда список `ip_private_relay.dat` в каталоге данных есть и не пуст.

На той же карточке чёрный список User-Agent: одна полная строка на линию, совпадение точное. Это файл `ua_blacklist.dat`, его пишут через `PUT /api/lists/ua_blacklist.dat`.

Движок читает профиль до выбора потока, когда загружены и подписи, и индекс IP. Любая непустая метка включает признак `bot` у посетителя. Правило потока `bot`: `0` — не фильтрует, `1` («да») — только боты, `2` («нет») — только люди. Сам ответ профиля не задаёт.

## Фильтры потока

Обычный поток берёт первое совпадение. `filter_or: true` — пункт «любое из этих условий»: хватает одного настроенного условия. «Все эти условия» оставляет флаг выключенным. На схеме между условиями стоит «или». Лимит показов остаётся обязательным и проверяется последним; условие, которое не прошло, счётчик не тратит. Подробнее — [правила потока](router-rules.md).

`bot`, `proxy` и `ip_version` устроены как `0` / `1` / `2`.

- `bot`: `1` — только боты, `2` — только люди. Признак ставит профиль, не блок «Боты». Ботом считается любая непустая метка, в том числе `proxy` ([метки](#метки)).
- `proxy`: `1` — «только прокси», `2` — «без прокси».
- `ip_version`: `1` — «только IPv4», `2` — «только IPv6». IPv4 включает IPv4-mapped. Невалидный адрес не проходит ни `1`, ни `2`.

Списки в редакторе:

- IP-список (`ip_list`): «в списке» — флаг `2`, «не в списке» — флаг `1`. В редакторе адреса чипами; в правиле остаётся имя файла `.dat`.
- User-Agent (`ua_text`): «содержит» — флаг `2`, «не содержит» — флаг `1`. Сравнение — подстрока, без учёта регистра, либо выражение `/…/`.
- Sub ID 1…12 — правило `sub_ids` (см. [правила потока](router-rules.md)): значения читаются по параметрам источника кампании. Фильтр Keitaro `sub_id_N` при импорте становится этим правилом.
- Параметр URL (`get`): значение `sub_id_3=…` или одно имя; для Sub ID есть отдельное правило `sub_ids`, оно читает параметр через источник кампании. «Равно» — флаг `2`, «не равно» — флаг `1`. Имя без значения требует непустой параметр. Сравнение значения без учёта регистра.

В режиме «или» условие списка проходит, когда посетитель совпал с флагом `2`, и проходит у всех, кто не совпал, при флаге `1`. Список, которым ловят, ставят на `2`.

## Переключатели потока

Блок «Боты» в редакторе потока, подпись «Считать ботом, если». Те же поля `ch_*`, что у профиля, плюс ответ. После выбора потока детекция идёт по ним заново и возвращает метку для журнала и заголовка `X-Emtds-Bot`. Пустая метка в заголовке пишется как `-`. Если поток не выбран, для журнала остаются только подписи User-Agent.

Пустой `redirect` и значение `skip` («то же, что люди») оставляют обычный ответ потока. Метка в журнал всё равно пишется. Другой `redirect` подменяет ответ: тело из `out`, тип из `header`, если он задан.

`save_ip` («дописывать IP найденных ботов в списки поисковиков») дописывает IP в `ip_<метка>.dat` только для меток `baidu`, `bing`, `google`, `mail`, `yahoo` и `yandex`, и только если этой строки в индексе ещё нет. Пишутся только адреса, которые подтвердил DNS: поисковик по User-Agent, обратное имя в домене краулера, прямой поиск вернул тот же адрес. Метка по одному User-Agent, `fake_…`, `apple` (у него нет файла списка), `proxy`, `device` и метки от `ch_ptr` в файл не попадают. Процесс помнит уже дописанный адрес до перезапуска. Шаг `save_ip` стоит до проверки IP-списков поисковиков, поэтому одно попадание в такой список файл в этом проходе не пополняет.

## Порядок проверок

Функция `detectBot` берёт первую сработавшую включённую проверку. Дальше список не идёт, кроме `save_ip` и блока IP-списков ниже.

1. Подписи (`ch_ua`). User-Agent проходит через [встроенный набор](#встроенный-набор-подписей-user-agent) и файл `signature_ua.dat` за один проход. Если метка — у поисковика, адрес ещё [проверяется по DNS](#проверка-поисковиков-по-dns): метка может стать `fake_…`. Если по User-Agent метки нет — подстрока реферера из `signature_ref.dat` → `sign_ref`. Пустой User-Agent подписями не бот.
2. Прокси (`ch_proxy`). Посетитель с признаком прокси → метка `proxy`. Включена ли проверка на самом деле, зависит от [правила по умолчанию](#прокси-по-умолчанию).
3. Не телефон и не планшет (`ch_non_mobile`). Тип `computer` → метка `device`. Телефон, планшет и пустая строка типа эту метку не получают. На клике пустой User-Agent уже разобран как `computer`, поэтому при включённой проверке он получает `device`.
4. IPv6 (`ch_ipv6`). Адрес задан и это не IPv4 → метка `ipv6`. У обычного клика IPv4-mapped уже приведён к IPv4, метка ему не ставится.
5. Пустой User-Agent (`ch_empty_ua`). Пустая строка или один пробел → `empty_ua`.
6. Пустой реферер (`ch_empty_ref`). Пусто или «-» → `empty_ref`.
7. Пустой язык (`ch_empty_lang`). Пусто или «-» → `empty_lang`.
8. PTR (`ch_ptr`). Работает по [той же проверке DNS](#проверка-поисковиков-по-dns), но для посетителей с обычным User-Agent. Клик не ждёт ответа DNS. Пока ответа в кэше нет, метки нет. Когда ответ есть: PTR-имя адреса лежит в домене краулера → метка этого движка, если прямой поиск вернул тот же IP, иначе `fake_<движок>`. Имя вне доменов краулеров метку не даёт.
9. Чёрный список User-Agent (`ch_list_ua`). Точное равенство строке из `ua_blacklist.dat` → `ua_blacklist`.
10. `save_ip`, если метка уже есть и её подтвердил DNS. См. выше.
11. IP-списки поисковиков, если метки всё ещё нет. Порядок: `baidu`, `bing`, `google`, `mail`, `yahoo`, `yandex`, `others`. Файлы `ip_<имя>.dat`. Берётся первое попадание, метка — имя списка.

## Встроенный набор подписей User-Agent

Движок сам знает типичных ботов, ничего настраивать не нужно. Набор лежит в `internal/detect/signature_ua_default.dat` и зашит в программу. Все подстроки (поисковики, встроенный набор и строки пользователя) собираются в один автомат Ахо-Корасик: User-Agent просматривается один раз, регистр не важен, память на клик не выделяется.

Файл набора разбит на разделы, раздел задаёт метку:

| Раздел | Метка | Что внутри |
| --- | --- | --- |
| `[headless]` | `headless` | автоматизированные браузеры: `headlesschrome`, `puppeteer`, `playwright`, `selenium`, `phantomjs` и другие |
| `[http_client]` | `http_client` | библиотеки и командные клиенты, считаются всегда: `curl/`, `wget/`, `python-requests`, `go-http-client`, `axios/`, `scrapy` и другие |
| `[http_client_bare]` | `http_client` | `okhttp/` и `java/`: считаются клиентом только если в User-Agent нет `mozilla/` |
| `[crawler]` | `crawler` | краулеры, SEO-сервисы, ИИ-агенты и боты предпросмотра ссылок: `ahrefsbot`, `semrushbot`, `gptbot`, `claudebot`, `facebookexternalhit`, `twitterbot`, `slackbot` и другие |
| `[scanner]` | `scanner` | сканеры уязвимостей и сети: `sqlmap`, `nikto`, `nmap`, `masscan`, `nuclei`, `zgrab` и другие |

Общие слова вроде `bot`, `spider`, `crawler`, `safari`, `wv`, `instagram`, `fban`, `telegram`, `sogou` в набор сознательно не входят: они встречаются в User-Agent настоящих людей.

Отдельно, вне файла, стоят подстроки поисковиков: `baidu`, `bing`, `msnbot`, `google`, `mail.ru`, `yahoo`, `yandex.com/bots` и `applebot`. Они дают метки `baidu`, `bing`, `google`, `mail`, `yahoo`, `yandex` и `apple`.

Два служебных правила:

- Человеческие токены гасят метки поисковиков. Если в User-Agent есть `bingsapphire`, `bingweb`, `baiduboxapp`, `baidubrowser`, `bdbrowser`, `googleplay`, `yjapp`, `jp.co.yahoo` или `bingo`, строка считается обычной: внутренние браузеры Bing, Baidu, Yahoo Japan, игры с каналом Google Play. Остальные метки (`headless`, `scanner` и т.д.) такая строка получить может.
- `mozilla/` выключает только «голые» шаблоны (`okhttp/`, `java/`). Обычный браузер с `mozilla/` по ним ботом не станет.

Если в одной строке сработало несколько шаблонов, побеждает самая сильная метка. Порядок от сильной к слабой: поисковики (`baidu`, `bing`, `google`, `mail`, `yahoo`, `yandex`, `apple`), затем `sign_ua`, `headless`, `scanner`, `http_client`, `crawler`.

### Свой файл `signature_ua.dat`

Файл в каталоге данных **дополняет** встроенный набор, а не заменяет его. Правка — «Списки», `GET` и `PUT /api/lists/signature_ua.dat`, одна подстрока на строку, регистр не важен.

- Обычная строка добавляет шаблон с меткой `sign_ua`. Заголовки разделов `[…]` в этом файле игнорируются, строки с `#` — комментарии.
- Строка `-шаблон` отключает встроенный шаблон с тем же текстом. Например, `-curl/` выключает `curl/`. Отключить можно только шаблоны из файла набора. Поисковики, `mozilla/` и человеческие токены отключить нельзя.
- Удалили файл — на следующем чтении остаётся один встроенный набор.
- Лимиты: не больше 20000 строк, не длиннее 256 байт каждая, не больше 256 КиБ в сумме. Лишнее отбрасывается, в лог идёт одно предупреждение на каждый лимит.

Движок смотрит на файл раз в минуту (`EMTDS_RELOAD_INTERVAL`) и перечитывает его, только если изменились время или размер.

## Метки

Любая непустая метка делает посетителя ботом: она попадает в журнал, в заголовок `X-Emtds-Bot` и в признак `bot` для правила потока.

| Метка | Что значит |
| --- | --- |
| `baidu`, `bing`, `google`, `mail`, `yahoo`, `yandex` | поисковик: User-Agent назвал его, а адрес подтверждён списком `ip_<имя>` или DNS (или DNS ещё не ответил и клик помечен по одному User-Agent). Эти же метки ставят IP-списки поисковиков и `ch_ptr` |
| `apple` | Applebot. Списка IP нет, подтверждается только DNS |
| `fake_google`, `fake_bing`, … | User-Agent назвался поисковиком (или обратное имя адреса лежит в его домене), но адрес не подтверждён: подделка |
| `others` | адрес из списка `ip_others` (прочие краулеры и ИИ-боты) |
| `headless` | автоматизированный браузер |
| `http_client` | библиотека или командный клиент |
| `crawler` | краулер, SEO-сервис, ИИ-агент или бот предпросмотра ссылок |
| `scanner` | сканер уязвимостей или сети |
| `sign_ua` | строка из вашего `signature_ua.dat` |
| `sign_ref` | подстрока реферера из `signature_ref.dat` |
| `proxy` | адрес прокси, VPN или хостинга (`ch_proxy`) |
| `device` | компьютер, а не телефон или планшет (`ch_non_mobile`) |
| `ipv6` | адрес IPv6 (`ch_ipv6`) |
| `empty_ua`, `empty_ref`, `empty_lang` | пустой User-Agent, реферер или язык |
| `ua_blacklist` | точное совпадение со строкой из `ua_blacklist.dat` |

## Проверка поисковиков по DNS

Назваться Googlebot может кто угодно. Если включён `ch_ua` и User-Agent говорит, что это поисковик, движок проверяет адрес методом FCrDNS (forward-confirmed reverse DNS):

1. По IP ищется PTR-имя. Первое имя, которое лежит в домене краулера, считается его именем.
2. Для этого имени делается прямой поиск A/AAAA.
3. Адрес подтверждён, если среди ответов есть тот же IP.

Домен проверяется точно или как поддомен через точку (`crawl-1.googlebot.com` подходит, `evilgooglebot.com` нет).

| Метка | Домены PTR |
| --- | --- |
| `google` | `googlebot.com`, `google.com` |
| `bing` | `search.msn.com` |
| `yandex` | `yandex.ru`, `yandex.net`, `yandex.com` |
| `baidu` | `baidu.com`, `baidu.jp` |
| `yahoo` | `crawl.yahoo.net` |
| `mail` | `go.mail.ru` |
| `apple` | `applebot.apple.com` |

Если адрес уже есть в списке `ip_<метка>` (Google, Bing и другие, их наполняет cron), он подтверждается сразу, без DNS. Для `apple` списка нет.

Проверка идёт в фоне, клик на DNS не ждёт:

- Первый клик с нового адреса получает метку по User-Agent, например `google`.
- Когда проверка закончилась, следующие клики получают `google` (подтверждён) или `fake_google` (обратное имя не в домене Google, в домене другого поисковика, нет совсем или прямой поиск вернул другой адрес).
- Бот или нет, от проверки не зависит: и `google`, и `fake_google` — боты. Меняется метка в журнале и заголовке, а подтверждённый адрес может попасть в `save_ip`.
- Если все места проверки заняты (16 одновременных проверок для User-Agent поисковика, 8 для `ch_ptr`), новая проверка не запускается и ничего не запоминается: клик получает метку по User-Agent, повторная попытка будет на следующем клике. Один адрес проверяется одной проверкой за раз.

Время и кэш:

- Тайм-аут одной проверки — 2 секунды на обратный и прямой поиск вместе.
- Результат помнится по адресу: найденное имя (подтверждённое или нет) — 10 минут, «имени нет» — 1 минута. В кэше два поколения по 16384 адресов.
- Временная ошибка DNS (тайм-аут, сбой сервера) не означает подделку. Адрес считается «неизвестным» на 15 секунд, метка остаётся по User-Agent. Третья такая ошибка подряд для одного адреса становится окончательным ответом «не подтверждён» (`fake_…`) на 1 минуту. Любой полученный ответ счётчик ошибок обнуляет.
- Ответ «имя не найдено» (NXDOMAIN) окончательный сразу.

`ch_ptr` работает по тому же кэшу, но для посетителей с обычным User-Agent: если PTR-имя адреса лежит в домене краулера, метка будет `google` и т.д. (имя подтверждено прямым поиском) или `fake_google` (не подтверждено). Первый клик с нового адреса ещё без метки. `ch_ptr` адрес в файл не сохраняет.

## Как узнаётся прокси

На клике внешние API не вызываются. Признак прокси локальный, один и тот же у правила `proxy`, у проверки `ch_proxy` и у поля `proxy` в справочнике IP и в симуляторе.

Сначала адрес ищут в `ip_proxy.dat`. Если его там нет, название организации из базы ASN сравнивают с подстроками из `proxy_org.dat`. Проверяются оба написания организации, если базы расходятся: основное (`Org`, у DB-IP) и второе (`OrgAlt`, у MaxMind) — см. [гео-базы](geo-databases.md). Регистр не учитывается. Пустая организация и «-» не прокси.

Исключение: адрес из списка `ip_private_relay.dat` прокси не считается, даже если он есть в `ip_proxy` или организация подошла под шаблон. Это диапазоны iCloud Private Relay от Apple, за ними сидят обычные владельцы iPhone. Исключение общее для правила `proxy`, проверки `ch_proxy`, справочника IP и симулятора. Список читается только после совпадения, поэтому обычным кликам он ничего не стоит.

`proxy_org.dat` в каталоге данных заменяет встроенный список `internal/detect/proxy_org.dat`. Пока файла нет, работает встроенный. Правка — «Списки», `GET` и `PUT /api/lists/proxy_org.dat`. Пустые строки и строки с `#` не читаются.

Список `ip_proxy` наполняет работа cron `ip_lists` («Списки IP ботов» в «Автоматизации»). У новой установки работа выключена, пока её не включат. В том же наборе по умолчанию есть источники краулеров (`ip_google`, `ip_bing`, `ip_others` и другие). На `ip_proxy` из них смотрят пять:

| Источник | Режим |
| --- | --- |
| `https://raw.githubusercontent.com/X4BNet/lists_vpn/main/output/datacenter/ipv4.txt` | replace |
| `https://raw.githubusercontent.com/X4BNet/lists_vpn/main/output/vpn/ipv4.txt` | merge |
| `https://iplists.firehol.org/files/proxylists_1d.ipset` | merge |
| `https://iplists.firehol.org/files/socks_proxy_1d.ipset` | merge |
| `https://iplists.firehol.org/files/tor_exits.ipset` | merge |

Уже сохранённый конфиг эти строки сам не получает: массив источников в файле заменяет набор по умолчанию целиком. Их добавляют вручную в «Автоматизации», работа `ip_lists`.

Шестой источник — для списка исключений `ip_private_relay`: `https://mask-api.icloud.com/egress-ip-ranges.csv`, режим `replace`. Это CSV Apple (строка вида `172.224.226.0/27,GB,GB-EN,London,`): из каждой строки берётся только первое поле, адрес или сеть. Лимит ответа для него 64 МБ (у остальных списков 32 МБ). В отличие от пяти выше, этот источник есть в наборе по умолчанию и добавляется в уже существующий `cron.json` один раз: при чтении конфига недостающий источник появляется в памяти, а ключ `ip_private_relay` в поле `seeded` запоминает, что он уже предлагался. Если источник потом удалить в «Автоматизации», он не вернётся. Работа `ip_lists` должна быть включена, иначе список не скачается.

Результат `ip_lists` — одно число на файл, сколько строк в нём после последнего источника, который этот файл записал. Имена по алфавиту через запятую: `ip_google: 1657, ip_proxy: 58773`. Ошибка запуска — отдельное поле `error` статуса и отдельная строка в карточке; текст результата остаётся в `message`.

Бейдж службы (`serviceBadge`): при ошибке конфига — «Ошибка конфигурации», в подсказке текст `config_error`. «Не настроено» — у Telegram без токена или чата и у geo без источников или без обоих файлов; если источники есть, а обоих файлов нет, подсказка «Файл не найден». Пока успешного запуска не было — «Ждёт первого запуска». После запуска бейдж показывает следующий запуск.

## Прокси по умолчанию

В профиле установки проверка прокси (`ch_proxy`) по умолчанию включена. «По умолчанию» значит, что в `bot_protection.json` нет ключа `ch_proxy` (или нет самого файла). Правило такое:

- Ключа нет: движок включает проверку только когда загружен непустой список `ip_private_relay` (см. выше). Пока списка нет, проверка выключена, и это защита: без исключения для Private Relay метку `proxy` получили бы обычные владельцы iPhone.
- Ключ есть, `true` или `false`: так и работает, список не нужен. С явным `true` и без списка Private Relay исключения не будет.

Что видно в админке, карточка «Защита от ботов»:

- Под галкой «Прокси» заметка. «Проверка прокси: по умолчанию.» — список загружен, проверка работает. «Проверка прокси: по умолчанию; включится после загрузки списка iCloud Private Relay (Автоматизация → ip_lists).» — списка пока нет, проверка не работает. Тот же признак отдаёт `GET /api/bot-protection` (`proxy_default`, `private_relay`).
- Если галку не трогали, при сохранении ключ `ch_proxy` не пишется, умолчание остаётся.
- **Выключить:** снять галку и сохранить. В файл попадёт явное `ch_proxy: false`.
- **Вернуть умолчание:** когда `ch_proxy` записан явно, под галкой появляется ссылка «Сбросить проверку прокси к умолчанию». То же самое — `PUT /api/bot-protection` с телом `{"ch_proxy":null}`.
- Смена состояния «список появился или исчез» пишется в лог движка один раз: `bot profile: default proxy check`.

Чего ждать после включения:

- **Старый профиль.** Профиль, сохранённый до этой версии с выключенным прокси, ключа `ch_proxy` не содержит: ложь раньше в файл не писалась. Теперь такой профиль читается как «по умолчанию включено». Чтобы оставить проверку выключенной, снимите галку и сохраните ещё раз.
- **Ложные срабатывания.** iCloud Private Relay исключён по списку Apple. Всё остальное, что попало в `ip_proxy` или чьё название организации подошло под `proxy_org.dat`, получит метку `proxy`: корпоративные VPN, Opera VPN, Cloudflare WARP, Google One VPN и подобные. Это обычные посетители. Если для вашего трафика они важны, проверку лучше выключить, а прокси отсекать правилом потока `proxy` там, где это нужно.
- **Сдвиг статистики.** Метка `proxy` — это метка бота, поэтому посетитель с ней попадает в фильтр «Бот» (правило `bot: 1`) и выпадает из «только людей» (`bot: 2`). Доля ботов в сводке и отчётах вырастет сразу после включения. Сравнивать периоды до и после включения напрямую нельзя.

## Аналог потока Bot Protection

Поток с «любое из этих условий» (`filter_or: true`). Хватает одного условия. При обычном выборе берётся первый подходящий поток, поэтому этот ставят выше остальных. Ответ задаёт блок «Тогда»; для ловушки это обычно «Стоп» или 404. Лимит показов, если он включён, всё равно обязателен.

- Бот: «да» (`bot: 1`) — только боты. Признак ставит профиль установки.
- Прокси: «только прокси» (`proxy: 1`).
- Тип устройства — одна проверка на три флага. В редакторе отмечено значит разрешено, флаг `1` тип отсекает. Чтобы условие в режиме «или» прошло у компьютера, телефоны и планшеты оставляют неотмеченными (`phone: 1`, `tablet: 1`). Телефон и планшет тогда этому условию не проходят. На клике пустой User-Agent уже является `computer`.
- Списки, которыми ловят посетителя, стоят на флаге `2`, иначе при «или» условие пройдёт у всех, кто в список не попал. IP-список — «в списке». User-Agent — «содержит». Sub ID 3 — правило `sub_ids` с ключом `sub_id_3`, режим «равно» (флаг `2`). Условие `get` с параметром `sub_id_3=…` читает query без источника.

На схеме между условиями стоит «или». Перенос такого потока из Keitaro описан в [переносе из Keitaro](keitaro.md).

## Симулятор и справочник IP

«Инструменты». «Проверить посетителя» ходит в `POST /api/simulate`. Ответ показывает, какой поток подошёл и какое правило отсекло остальные. В объекте `visitor` есть поле `proxy`. Правила потока, включая `proxy` и `ip_version`, проверяются. Детекция ботов не запускается: лимит показов и антифлуд тоже не тратятся.

`GET /api/lookup?ip=` отдаёт то, что движок узнал бы по адресу. В объекте `visitor` есть поле `proxy` (с исключением Private Relay, как на клике) и, когда базы расходятся, `org_alt` и `asn_alt` ([гео-базы](geo-databases.md)). Негодный адрес отвечает `400`.
