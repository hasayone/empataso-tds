# Правила потока

Обычный поток берёт первое совпадение, где прошли все условия.

- `filter_or: true` — достаточно одного настроенного условия. В редакторе это пункт «любое из этих условий»; «все эти условия» оставляет флаг выключенным. На схеме между условиями стоит «или». Лимит показов остаётся обязательным и проверяется последним.
- `weight: true` у группы — среди подходящих потоков выбор по полю `weight` потока, а не всегда первый.
- `sticky_stream: true` у группы (нужны `weight: true`, окно `uniq_seconds` больше нуля и движок, не `?api=`) — вернувшийся посетитель получает тот же поток. Поток запоминается на `uniq_seconds` как непрозрачная подпись: 22 знака base64url, первые 16 байт HMAC-SHA256 от id группы и имени потока. Имя потока в cookie и в Redis не попадает. Ключ подписи выводится из ключа cid (`EMTDS_CID_KEY` или файл `cid.key`, см. [макросы](macros-sources.md)), поэтому подпись нельзя собрать для нужного потока без ключа, и она не годится для другой группы. Подпись общая для потока, а не для посетителя: она одинакова у всех. Поэтому чужая cookie с подписью потока даёт этот же поток, но только если поток проходит все правила и лимит; в обход правил поток не выдаётся. При `uniq_method=cookie` подпись лежит в cookie `zts_<id группы>` (`HttpOnly`, `SameSite=Lax`), при `ip` — в Redis под `st:<id группы>:<ip>`. Запомненный поток проходит те же условия и тот же лимитер, что и выбранный жребием, поэтому лимит списывается один раз. Если подпись не совпала ни с одним потоком группы, поток выключен, его вес ноль, условия не проходят или лимит исчерпан, посетитель выбирается заново и запись обновляется. Запоминается группа, которая отдала ответ: при `redirect=group` у каждой группы своя запись. Ответ такой группы получает `Cache-Control: private, no-store`. Без Redis при `uniq_method=ip` режим не работает. Ошибка Redis не мешает клику: поток выбирается заново. Каждый вызов Redis ограничен 150 мс; при зависшем Redis визит ждёт до 2×150 мс (чтение и запись). Режим по IP верен, только если движок видит реальный адрес посетителя: за прокси или CDN нужен `EMTDS_TRUSTED_PROXIES`, иначе все посетители делят один адрес и один поток; при сомнении выбирают `uniq_method=cookie`.

Память Redis при `uniq_method=ip`: один ключ на пару «IP, группа с `sticky_stream`», срок жизни — `uniq_seconds`, но не дольше потолка `EMTDS_UNIQ_MAX_SECONDS` (по умолчанию сутки). Ключ с накладными расходами Redis занимает порядка 150 байт, то есть миллион адресов за окно — около 150 МБ. Общий Redis держит и счётчики лимитов, поэтому для него ставят `maxmemory` с запасом и политику `noeviction`: вытеснение молча сбросило бы счётчики лимита. При заполнении Redis отказывает в записи, и посетитель просто выбирается заново.
- Несколько офферов — выбор URL по `share`.
- Если у потока есть и лендинг, и оффер, первый ответ — лендинг. Оффер открывается по пути `/<поток>/offer`.

`proxy` и `ip_version` устроены как `unique` и `bot`: `0` — выключено.

- `proxy`: `1` (флаг A) — только прокси, `2` (флаг B) — только не прокси.
- `ip_version`: `1` (флаг A) — только IPv4, `2` (флаг B) — только IPv6. IPv4 включает IPv4-mapped: адрес `::ffff:1.2.3.4` проходит `1` и не проходит `2`. Невалидный адрес не проходит ни `1`, ни `2`.

В режиме `filter_or` `proxy` и `ip_version` — отдельные условия. Хватает одного. Лимит показов после них всё равно обязателен.

Прокси считается локально, на клике внешние API не вызываются. Адрес есть в списке `ip_proxy.dat`, либо название организации сети из базы ASN содержит подстроку из `proxy_org.dat`. Сравнение без учёта регистра. Пустое имя и «-» прокси не дают. Встроенный список — `internal/detect/proxy_org.dat`. Файл `proxy_org.dat` в каталоге данных его заменяет. Его правят в «Списках»: `GET` и `PUT /api/lists/proxy_org.dat`. Откуда берётся `ip_proxy` — в [защите от ботов](bot-protection.md).

Признак для правила `bot` ставит профиль установки до выбора потока. Блок «Боты» у потока на этот признак не влияет: он пишет метку в журнал и может отдать боту отдельный ответ. Подробнее — [Защита от ботов](bot-protection.md). В редакторе потока условие «Бот» — переключатель: включён значит `1` (только боты), выключен значит `2` (только люди). Новое условие сразу включено. Ноль по-прежнему значит, что условия нет.

У типа устройства флаг `1` блокирует этот тип, `0` его не фильтрует. Неизвестное устройство (не `computer`, `phone` и `tablet`) движок не режет. В редакторе это переключатель «да» / «нет» и выбор компьютеров, телефонов и планшетов. Пустой выбор пишет три нуля и ничего не фильтрует. «да» пропускает выбранные типы и блокирует остальные из трёх. «нет» блокирует выбранные и пропускает остальные. Сохранённое правило без блокировок открывается как «да» с пустым выбором. Если блокировок не больше, чем разрешённых типов, открывается «нет» со списком заблокированных, иначе «да» со списком разрешённых.

В потоке адреса списка IP и значения условий-списков задаются чипами. Если чипы выше двух рядов, список свёрнут: «Ещё» раскрывает его, «Свернуть» возвращает. «Добавить текстом» даёт одну строку на значение, «Чипами» возвращает чипы; черновик при переключении не теряется. Режим только на время открытого редактора и в JSON кампании не пишется. Сохранение IP пишет файл `ip-` и 12 hex SHA-1 текста с суффиксом `.dat` до кампаний, движок подхватывает его сам при перечитывании групп.

Правило `model` — модель устройства, точное совпадение без учёта регистра. Флаг `1` исключает модель из списка, флаг `2` пропускает только её. Модель берётся из User-Agent Android (`SM-S918B` из `Android 13; SM-S918B Build/…`). Модель длиннее 64 знаков обрезается, управляющие символы удаляются. Движок читает `Sec-CH-UA-Model`, только когда браузер прислал его сам; `Accept-CH` он не ставит. Поэтому у Chrome с урезанным User-Agent (модель `K`) и у всех устройств iOS модель пустая. Пустая модель не проходит список «только» (флаг `2`) и не попадает в исключения (флаг `1`): белый список по модели отсекает iOS и такие Chrome. Ту же модель пишет журнал в поле `device_model` ([журналы](log-filters.md)).

Правила `sub_ids` — Sub ID 1…30 в условии «Когда». Ключ — `sub_id_1`…`sub_id_30`, значение — `{flag, values, empty}`. Флаг `1` исключает совпадение, флаг `2` оставляет только его. `values` сравниваются целиком без учёта регистра. `empty: true` относит к совпадению пустой Sub ID. Правило без флага или без значений и без `empty` выключено. Значение читается так же, как в журнале: по имени параметра из источника кампании (`source_id`), а без источника по самому имени. При `redirect=group` значения и ключевое слово пересчитываются по источнику новой группы: ключ берётся из параметра, который сопоставил её источник, а без него остаётся ключ запроса из `keyword=`, `q=` или `utm_term=` ([ключевые слова](keywords.md#откуда-берётся-ключ)). Правило участвует и в «все условия», и в «любое из этих» (`filter_or`) отдельным условием; причина отказа в симуляторе — ключ, например `sub_id_3`. Условие `get` (`sub_id_3=значение`) — отдельное: оно читает query как есть, без источника. Ключ вне `sub_id_1`…`sub_id_30` или флаг не 1 и не 2 сервер отклоняет ответом 400. Симулятор берёт источники из каталога сервера.

`POST /api/simulate` возвращает выбранный URL. Поле `roll` фиксирует жребий в тесте. Симулятор гоняет правила потока и не запускает детекцию ботов.
