# Обновление EmTDS

Агент обновлений — хостовый скрипт `deploy/update.sh` (работает как root). Обновления применяются только вручную: командой из CLI или кнопкой «Обновить» в «Настройки → О системе». Таймер `emtds-update.timer` самостоятельно применение не инициирует — он раз в час проверяет, есть ли новая версия, и обрабатывает запросы кнопки.

## Установка одной командой

На чистом сервере (Ubuntu 22.04 или 24.04, Debian 12) от root:

```bash
curl -fsSLo /root/emtds-install.sh https://raw.githubusercontent.com/hasayone/empataso-tds/main/deploy/install.sh && bash /root/emtds-install.sh --repo https://github.com/hasayone/empataso-tds.git --channel main
```

Скрипт запускают файлом через `bash`, не через `curl | bash`. Файл `install.sh` лежит вне клона, поэтому работает как загрузчик: ставит `git`, делает полный клон `--repo` (история нужна для проверки fast-forward) во временный каталог, переводит его на версию канала, атомарно переименовывает в `/opt/emtds` и продолжает уже оттуда с теми же аргументами. Адрес репозитория в скрипт не зашит: его передаёт `--repo`, дальше агент берёт его из `origin` клона и пишет в `/etc/emtds/update.env`.

| Флаг | Назначение |
|------|------------|
| `--repo URL` | адрес репозитория, обязателен в режиме загрузчика; учётные данные в адресе запрещены |
| `--channel main\|release` | канал обновлений; без флага — `release` (в однострочнике — `main`) |
| `--allowed-signers FILE` | необязательный файл ключей подписи: до запуска проверяется подпись коммита или тега и файл кладётся в `/etc/emtds/allowed_signers` (см. [Подпись](#подпись-ssh-подпись)) |
| `--no-edge` | не ставить nginx и не применять `apply-edge.sh` (админка тогда только через `ssh -L 8090:127.0.0.1:8090`) |

Установщик сам ставит `git`, Docker (если нет `docker compose`) и nginx (Ubuntu 22.04 и 24.04, Debian 12), создаёт `.env` с паролем ClickHouse и токеном первого входа, собирает образ с вшитым коммитом, поднимает стек и включает агент обновлений. Если маркер `/etc/emtds/installed` уже есть, повторный запуск ничего не делает и только напоминает про `/etc/emtds/up.sh` и `update.sh --check`.

**Токен первого входа.** В конце установки в консоль печатается адрес входа (`https://<публичный IP>/`, например `https://203.0.113.10/`; сертификат самоподписанный, браузер предупредит) и токен `EMTDS_SETUP_TOKEN` из 32 знаков. Он хранится в `/opt/emtds/.env` и нужен один раз: форма первого входа просит его вместе с логином, паролем и почтой главного администратора, без него `POST /api/setup` отвечает `403`. Пароль администратора в `.env` не пишется. После создания администратора токен не используется.

## Версии — где видно

- **`GET /api/version`** (только администратор) — возвращает `admin`, `engine`, `cron` (commit, version, channel), образы Docker трёх контейнеров и флаг рассинхрона.
- **Настройки → О системе** (`#/settings/about`, только администратор; старый адрес `#/settings/updates` ведёт сюда) — версия и коммит админки, движка и cron с датой и каналом сборки, канал агента и ссылка на `CHANGELOG.md` по коммиту сборки (если репозиторий на GitHub); блок «Обновление»: доступная версия, возраст последней проверки, список коммитов, «Что нового», ручные шаги и команды CLI, кнопки «Обновить», «Откатить» и «Проверить сейчас»; блок «Сервер»: процессоры, нагрузка, память, диск, время работы, ClickHouse, Redis и cron (данные `GET /api/system`, читаются при открытии страницы и по кнопке «Обновить», не по таймеру). Пункт меню «О системе» и строка версии в меню пользователя ведут туда же.
- **Логи** — строки `engine listening`, `admin api listening`, `cron started` содержат `version` и `commit`.

`/internal/version` движка закрыт nginx и внешним запросом недоступен.

При dev-сборке (нет `-X` флагов) version = `dev`, commit = `""`. Кнопка неактивна на dev-сборке.

## Каналы обновлений

| Канал | Описание | Цель |
|-------|----------|------|
| `release` | значение по умолчанию в `install.sh` и `update.sh --install` | максимальный тег `vX.Y.Z`, который является предком `origin/main` |
| `main` | канал прода (его передаёт однострочник) | верхушка `origin/main`: любой принятый пуш в `main` — доступное обновление |

Канал задаётся в `/etc/emtds/update.env` (ключ `EMTDS_UPDATE_CHANNEL`; его пишет установщик из `--channel`) и не меняется агентом самостоятельно. Теги `vX.Y.Z` дают версиям имена.

## Что принимает агент

- **Только fast-forward.** Цель обязана быть потомком текущего коммита (`merge-base --is-ancestor`); тег — предком `origin/main`. Понижение через кнопку невозможно, а `--force-version` есть только в CLI и просит ввести sha в терминале.
- **Закреплённый origin.** Перед каждым `git fetch` агент ставит `origin` из `EMTDS_UPDATE_REPO` в `/etc/emtds/update.env` (файл root, права 0600); учётные данные в адресе запрещены, хуки репозитория и внешняя программа подписи игнорируются.
- **Force-push в `main` агент не примет:** если `origin/main` переписан и не является потомком текущего коммита, в `check.json` попадает ошибка, кнопка «Обновить» неактивна, сборка не запускается. Не делайте force-push в `main`.
- **Проверка раз в час** (`EMTDS_UPDATE_CHECK_HOURS=1`): агент делает `git fetch` по https публичного репозитория, без GitHub API; админка в интернет не ходит и только читает `check.json`. Кнопка «Проверить сейчас» запускает проверку сразу, не чаще раза в 5 минут. Если GitHub недоступен, причина пишется в `check.json.error`, кнопка показывает `no_update`, стек работает дальше. При входе администратор видит баннер новой версии и возраст проверки. На баннере есть «Обновить» — тот же запрос в inbox, что и кнопка «О системе», — и «Скрыть до следующей версии» или «Скрыть на 24 часа». Скрытие хранится в браузере (`localStorage`, ключ `emtds-upd-hide`) и действует только для той цели, для которой нажато: новый коммит или конец суток показывают баннер снова. Жёлтая точка на аватаре и значок пункта «О системе» не скрываются.

Кнопка «Обновить» в «О системе» видна всегда и стоит над отчётом последнего прогона. Если нажать её нельзя, причина написана под ней. Пока идёт перенос или актуализация Keitaro, кнопка выключена, страница перепроверяет состояние раз в 15 секунд и включает кнопку после окончания переноса; перенос при этом не прерывается.

## Ченжлог и «Что нового»

[`CHANGELOG.md`](../../CHANGELOG.md) ведётся по Keep a Changelog: раздел `## [Unreleased]` и разделы версий `## [vX.Y.Z] - <дата>`. **Правило: каждое заметное изменение — строка в `[Unreleased]`** в том же коммите, что и изменение. Агент берёт «Что нового» (`check.json.notes`) из добавленных строк `git diff <текущий>..<цель> -- CHANGELOG.md`; если diff пуст, берётся аннотация тега (без блока подписи). Размер ограничен 16 КиБ. При выпуске версии содержимое `[Unreleased]` переносят в раздел с номером и тегом.

Telegram-уведомление о новой версии шлёт только cron (дедупликация — `announced.json`); на канале `main` новая цель анонсируется не чаще раза в час, итог прогона (`ok`, `rolled_back`, `failed`) — сразу.

## Первая установка агента (`update.sh --install`)

`install.sh` вызывает `update.sh --install` автоматически, если на сервере есть git-дерево и systemd; в режиме клона сбой этого вызова останавливает установку. Вручную — из каталога кода:

```bash
sudo bash deploy/update.sh --install \
  --repo https://github.com/hasayone/empataso-tds.git \
  --channel main \
  --tds-dir /opt/emtds
```

**Что создаётся:**

| Путь | Права | Содержимое |
|------|-------|------------|
| `/etc/emtds/update.env` | 0600 root | настройки агента |
| `/etc/emtds/deploy_key` | 0600 root | приватный ключ SSH (только для адреса `git@…` или `ssh://…`, создаётся, если нет) |
| `/etc/emtds/deploy_key.pub` | — | публичная часть (печатается в терминал) |
| `/etc/emtds/known_hosts` | 0644 root | отпечаток хоста git-сервера (только для SSH-адреса) |
| `/var/lib/emtds-update/` | 0700 root | история, логи прогонов, сборки |
| `/var/lib/emtds-update/inbox/` | 0700 10001:10001 | входящие запросы кнопки |
| `/var/backups/emtds-update/` | 0700 root | архивы бэкапов |
| `/usr/local/lib/emtds/update.sh` | 0755 root | рабочая копия скрипта |
| `/etc/systemd/system/emtds-update.service` | 0644 | oneshot-юнит |
| `/etc/systemd/system/emtds-update.timer` | 0644 | таймер 60 с |

После установки таймер включается: `systemctl enable --now emtds-update.timer`.

## Deploy key

Нужен только для SSH-адреса репозитория (`git@…`, `ssh://…`); для публичного `https://` (как в однострочнике) ключ не создаётся. Скрипт создаёт ключ `ssh-keygen -t ed25519` и **печатает только публичную часть** с инструкцией:

```
=== Deploy key (добавьте в GitHub → Settings → Deploy keys) ===
ssh-ed25519 AAAA... emtds-deploy@hostname
=== Только read-only доступ ===
```

Добавьте публичный ключ в **GitHub → Settings → Deploy keys** без галочки Write access. Приватный ключ никогда не печатается, не логируется и не попадает в том.

Если репозиторий на GitHub, скрипт сам запишет `/etc/emtds/known_hosts`, сверив отпечаток с опубликованным. Для других git-серверов — вручную:

```bash
ssh-keyscan -t ed25519 git.example.com | sudo tee /etc/emtds/known_hosts
# Сверьте отпечаток с официальной документацией git-сервера.
```

## update.env

Файл `/etc/emtds/update.env` (права 0600, владелец root). Принимаются только ключи из белого списка; любой неизвестный ключ или команда вызывают отказ.

```ini
EMTDS_UPDATE_REPO=https://github.com/hasayone/empataso-tds.git
EMTDS_UPDATE_CHANNEL=main
EMTDS_UPDATE_CHECK_HOURS=1
EMTDS_UPDATE_KEEP_IMAGES=3
EMTDS_UPDATE_KEEP_BACKUPS=5
TDS_DIR=/opt/emtds
```

| Ключ | Значение |
|------|----------|
| `EMTDS_UPDATE_REPO` | адрес репозитория (`https://…`, `git@…` или `ssh://git@…`); учётные данные в URL запрещены |
| `EMTDS_UPDATE_CHANNEL` | `release` или `main` |
| `EMTDS_UPDATE_CHECK_HOURS` | интервал проверки в часах (по умолчанию 1) |
| `EMTDS_UPDATE_KEEP_IMAGES` | сколько образов `emtds:<sha12>` хранить (по умолчанию 3) |
| `EMTDS_UPDATE_KEEP_BACKUPS` | сколько бэкапов хранить (по умолчанию 5) |
| `TDS_DIR` | абсолютный путь к каталогу кода (git-репо) |

## Подпись (SSH-подпись)

**Политика.** Подпись **выключена по умолчанию**: пока в `/etc/emtds/allowed_signers` нет ни одной строки ключа, ни агент, ни админка подпись не требуют, кнопки «Обновить» и «Откатить» работают, CLI не нуждается в `--unsigned`. Источник правды один — этот файл; отдельной переменной в `update.env` нет. Админка узнаёт политику из `agent.json` (`signing`), а результат проверки конкретной цели лежит в `check.json` (`signed`). Подпись включается позже одним файлом: положите ключ в `/etc/emtds/allowed_signers` (или передайте `install.sh --allowed-signers FILE`). С этого момента подпись требуется везде: кнопка «Обновить» принимает только подписанную цель, «Откатить» — только подписанную предыдущую версию, таймер обойти проверку не может, а CLI допускает неподписанную цель только с явным `--unsigned`.

**Битый файл не выключает подпись.** Если `allowed_signers` есть, но не читается как обычный файл (каталог, битая ссылка, ошибка чтения) или у него небезопасные права, подпись считается включённой, и обновление останавливается с ошибкой, пока файл не исправят. Выключает подпись только отсутствие файла или читаемый файл без строк ключа. `update.sh --status` пишет `signing: on` или `signing: off`.

### Настройка разработчика

```bash
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global tag.gpgSign true
git config --global commit.gpgSign true
```

Проверка работает только при включённой политике:

- **Канал `release`** — проверяется подпись тега (`git verify-tag`).
- **Канал `main`** — проверяется подпись коммита (`git verify-commit`).

### allowed_signers на сервере

Файл `/etc/emtds/allowed_signers` (права 0644, владелец root, без записи для группы и остальных) создаётся вручную или флагом `--allowed-signers` установщика (не берётся из репозитория). Формат строки — стандартный git SSH allowed_signers:

```
developer@example.com namespaces="git" ssh-ed25519 AAAA...
```

Каждая строка — один ключ-разработчик. При установке скрипт сообщает, что подпись выключена, если в файле нет ключей.

Пока в файле нет ключей, `signing=false` в `agent.json`: админка не показывает красного бейджа «Не подписано», а у цели нет блокировки `unsigned`; в «О системе» стоит нейтральная плашка «Подпись выключена». Когда ключи есть, а цель не подписана, кнопка неактивна («Подпись включена, цель не подписана»), CLI требует `--unsigned`.

**Риск без подписи.** Тот, кто получит право пуша в `main` (взлом GitHub-аккаунта или токена), получает выполнение своего кода на сервере после нажатия «Обновить». Защищают: только fast-forward, закреплённый origin из файла root, обновление только по кнопке администратора с вводом 7 символов sha, показ коммитов и «Что нового», откат. Вне кода рекомендуется 2FA на GitHub и защита ветки `main` с обязательным CI.

## Обновление кнопкой

**Настройки → О системе** (только администратор). Кнопка «Обновить» неактивна, если:

| Код блокировки | Причина |
|----------------|---------|
| `updater_absent` | `agent.json` старше 10 минут или агент не видит inbox |
| `unsigned` | подпись включена (в `allowed_signers` есть ключ), а цель не подписана; при выключенной подписи код не появляется |
| `no_update` | нет доступного обновления или `check.json` старше 24 часов |
| `manual_steps` | изменения требуют ручных шагов (добавьте `--schema-ok` в CLI) |
| `keitaro_running` | идёт импорт из Keitaro |
| `request_pending` | запрос уже ждёт обработки |
| `running` | прогон уже выполняется |
| `dev_build` | текущая сборка dev |

Нажатие кнопки требует ввести первые 7 символов SHA целевого коммита. Запрос пишется агентом из admin в inbox (`/var/lib/emtds-update/inbox/request`) атомарно. Таймер `emtds-update.timer` забирает файл при следующем запуске (раз в 60 секунд) и запускает прогон.

Кнопка «Проверить сейчас» — не чаще одного раза в 5 минут.

**Откат кнопкой — только на один шаг.** «Откатить» возвращает предыдущую выкатанную версию, если последняя запись истории — успешное обновление на текущий коммит. Блокировки те же, что у «Обновить», кроме `no_update`, `manual_steps` и `unsigned` (подпись проверяет агент), плюс `no_previous`: после успешного отката цепочку откатов кнопкой продолжить нельзя, глубже — только CLI `--rollback`. Образ предыдущей версии `emtds:<sha12>` должен быть на хосте, иначе агент откажет (`no_image`). При включённой подписи агент проверяет подпись предыдущей версии и при её отсутствии отказывает (`unsigned`).

API-ключ не может вызвать `/api/update/apply`, `/api/update/rollback`, `/api/update/check` — только cookie-сессия администратора.

## Обновление командой (CLI)

Все команды запускаются от root; рабочая копия скрипта — `/usr/local/lib/emtds/update.sh`.

```bash
# Проверить наличие обновления, записать check.json (без применения):
sudo /usr/local/lib/emtds/update.sh --check

# Обновить по каналу из update.env:
sudo /usr/local/lib/emtds/update.sh --channel

# Обновить до конкретного SHA или тега:
sudo /usr/local/lib/emtds/update.sh --to abc123...

# Показать план без изменений (fetch разрешён):
sudo /usr/local/lib/emtds/update.sh --dry-run

# Показать состояние:
sudo /usr/local/lib/emtds/update.sh --status

# Откат на предыдущую версию:
sudo /usr/local/lib/emtds/update.sh --rollback
```

**Модификаторы:**

| Флаг | Когда использовать |
|------|--------------------|
| `--unsigned` | применить цель без проверенной подписи при включённой подписи (только CLI; при выключенной подписи не нужен) |
| `--schema-ok` | подтвердить выполнение ручных шагов (миграции, схема) |
| `--keitaro-idle` | пропустить гейт Keitaro — подтвердить, что перенос не запущен |
| `--force-version` | подтвердить понижение версии интерактивно |

## Что происходит при обновлении

1. **Захват lock** `/run/emtds-update.lock` — два прогона не запускаются одновременно.
2. **Проверка окружения** — есть `server.env` и `compose.app.yml`, TDS_DIR — git-репо.
3. **git fetch** из закреплённого `origin` (адрес из `update.env`); для SSH-адреса — через deploy key со `StrictHostKeyChecking=yes`.
4. **Выбор и проверка цели** — по каналу или по `--to`. Понижение версии без `--force-version` запрещено.
5. **Проверка подписи** — только если в `/etc/emtds/allowed_signers` есть ключи: `git verify-tag` (release) или `git verify-commit` (main). Иначе шаг пропускается.
6. **Ручные шаги** — если diff `HEAD..цель` затрагивает `migrations/clickhouse/`, `internal/store/schema*.go` или `deploy/docker-compose.yml`, прогон останавливается и перечисляет файлы. Флаг `--schema-ok` подтверждает, что шаги выполнены.
7. **Проверка ресурсов** — MemAvailable ≥ 2 ГБ, свободно на `/var/lib/docker` ≥ 5 ГБ, ClickHouse `/ping` и Redis `PING` отвечают.
8. **Бэкап** (каталог 0700, umask 077): архив `STATE_DIR` и `.env`; снимок тома без `geo/` через `docker run --user 10001 --network none`. Хранятся 5 последних.
9. **Сборка** — `docker build` из `git archive <sha>` в тег `emtds:<sha12>`. Если сборка упала — прогон завершается, диск не изменён.
10. **Гейт Keitaro** — агент пишет `update/pending` с id прогона; admin под своей блокировкой, убедившись, что `keitaro idle` и нет активных writers, отвечает `update/ready.json` с тем же id. Новые записи в Keitaro блокирует код `update_pending`. Если admin не отвечает 10 минут — прогон останавливается с текстом «нет ready.json от admin за 10 минут — идёт перенос или актуализация Keitaro», контейнеры не пересоздаются (кроме `--keitaro-idle`). Простой подтверждается сам, как только перенос закончился, если `pending` ещё действует. `--keitaro-idle` при живом переносе не используйте: он оборвёт перенос.
11. **Вторая фаза** — `git checkout --detach <sha>`, проверка `compose config` (порты только `127.0.0.1:`, нет `docker.sock`), `apply-edge.sh` при наличии nginx, retag `emtds:<sha12> → emtds:local`.
12. **Пересоздание сервисов** по одному: engine → admin → cron. Каждый — `up -d --no-build --force-recreate --no-deps`. ClickHouse, Redis, php не трогаются.
    - **Cron**: ожидает, пока не завершатся задачи `geo_db` и `virustotal` (до 10 минут). Если ждать дольше — cron остаётся старым с флагом `cron_lagging: true` в `state.json`.
13. **Проверка здоровья** — healthcheck Docker healthy, `clickhouse connected` и `redis connected` в логах, `/healthz` движка и `/api/health` admin отвечают.
14. **Простой engine** — несколько секунд пока контейнер поднимается. При автооткате — дважды.
15. **Финал** — `state.json`, строка в `/var/lib/emtds-update/history`, удаление `pending`, очистка старых образов и `docker builder prune`.

**Провал второй фазы** — агент откатывает: retag `emtds:<prev12> → emtds:local`, checkout предыдущего SHA, apply-edge, пересоздание engine/admin/cron. Если при этом ClickHouse или Redis недоступны — откат не делается, итог `failed` с причиной «инфраструктура».

## Откат

```bash
sudo /usr/local/lib/emtds/update.sh --rollback
```

Откат на предыдущую версию из `/var/lib/emtds-update/history`. Образ `emtds:<prev12>` должен быть на хосте. Это тот же прогон через вторую фазу, только без сборки.

**Автооткат** при провале второй фазы выполняется агентом без участия оператора.

**Схема БД при откате** — автоматического отката SQL-миграций нет. Если при обновлении применялась миграция `migrations/clickhouse/`, откатить схему нужно вручную. Флаг `--schema-ok` при следующем применении подтверждает, что шаги выполнены.

## Процесс релиза

1. Каждое заметное изменение — строка в `[Unreleased]` файла `CHANGELOG.md`; коммиты идут в ветку `main`, CI-тесты зелёные. Пуш в `main` без force — это и есть выкладка для серверов на канале `main`: администратор увидит обновление после ближайшей проверки (раз в час) или по кнопке «Проверить сейчас» и применит его кнопкой «Обновить» или командой `update.sh --channel`. Ручной `docker compose build` и копирование кода в `/opt/emtds` на сервере не делают: они дают dev-сборку и грязное дерево, а агент работает от git-истории и вшитого коммита.
2. Для именованной версии `[Unreleased]` переносят в раздел `[vX.Y.Z]` и ставят аннотированный тег (подпись `-s` нужна, только когда включена подпись):
   ```bash
   git tag -a -s v1.2.3 -m "Release v1.2.3\n\nDescription"
   git push origin v1.2.3
   ```
3. Workflow `.github/workflows/release.yml` при push тега `v*.*.*`:
   - прогоняет `go test -count=1 ./...`;
   - проверяет, что тег аннотированный и его коммит — предок `origin/main`;
   - собирает release notes из аннотации тега и `git log <prev>..<tag>`;
   - создаёт GitHub release через `gh release create`.

Actions закреплены по SHA. `permissions: contents: write` — только у job релиза.

## Файловый контракт (`/var/lib/emtds/update/`)

Каталог `update/` живёт рядом с `groups.json` внутри тома. Каждый файл имеет ровно одного писателя.

| Файл | Писатель | Содержимое |
|------|----------|------------|
| `agent.json` | updater | пульс каждые 5 минут: версия скрипта, repo, channel, signing, images |
| `check.json` | updater | результат последней проверки: текущий SHA, цель, список коммитов, `signed` (результат проверки цели), `notes` (добавленные строки `CHANGELOG.md`, иначе аннотация тега), `error` |
| `state.json` | updater | ход и итог прогона: id, action, phases, result, reason |
| `log.txt` | updater | хвост лога прогона ≤ 256 КиБ (маскированный) |
| `pending` | updater | id прогона, ждущего гейт Keitaro |
| `ready.json` | admin | подтверждение idle Keitaro с тем же id |
| `announced.json` | cron | дедуп Telegram-уведомлений |
| `request` | admin | запрос кнопки (читает updater через `--timer`) |

## Коды отказов и неполадки

| Ситуация | Что делать |
|----------|------------|
| «агент не установлен» (`updater_absent`) | запустите `update.sh --install`, проверьте таймер `systemctl status emtds-update.timer` |
| Кнопка не активна — `unsigned` | подпись включена (в `/etc/emtds/allowed_signers` есть ключ), а цель не подписана: подпишите тег или коммит либо уберите ключи из файла, если подпись не нужна |
| Кнопка не активна — `no_update`, в `check.json` есть `error` | `origin/main` не потомок текущего коммита (force-push) или GitHub недоступен; при force-push агент цель не примет, историю в `main` не переписывают |
| Кнопка «Откатить» — `no_previous` | кнопка откатывает только на один шаг; глубже — CLI `update.sh --rollback` |
| `request_pending` держится, прогон не начинается | зависший `request` в inbox чистится таймером при следующем запуске; проверьте логи `journalctl -u emtds-update` |
| Lock `/run/emtds-update.lock` занят | другой прогон активен; дождитесь завершения или перезагрузки. `--status` покажет состояние без захвата lock |
| Перенос из Keitaro блокирует обновление | дождитесь `GET /api/keitaro/job` → `running: false` и `sync_running: false`, затем «Обновить»; `--keitaro-idle` — только если перенос точно не идёт |
| Прогон завис, `state.json` показывает `running` | таймер при следующем захвате lock найдёт зависший `pending` и запишет `result: failed` с причиной `interrupted` |
| Ручные шаги после `--schema-ok` | выполните миграции вручную, затем повторно запустите с `--schema-ok` |

**Где смотреть логи:**

```bash
# Таймер и прогоны:
journalctl -u emtds-update -n 100 --no-pager

# Полный лог конкретного прогона:
cat /var/lib/emtds-update/runs/<id>.log

# Лог в томе (хвост ≤ 256 КиБ):
# «Настройки → О системе» → лог в интерфейсе; или GET /api/update/log
```
