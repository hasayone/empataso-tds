# Перенос конфигурации Keitaro в emtds

Один запуск читает конфигурацию и пишет группы и каталоги в локальную emtds. Маппер не распаковывает файлы лендингов. Архив локального лендинга читается отдельно: GET `/admin_api/v1/landing_pages/{id}/download`, тело до 64 МБ, без разбора JSON. На Keitaro уходят GET из allowlist и, если их вызывают отдельно, два POST журнала: `/admin_api/v1/clicks/log` и `/admin_api/v1/conversions/log`. `report/build` и любой другой POST остаются запрещены. Живое чтение включается флагом `--live`.

## Вход

Сухой прогон читает `testdata/export.json`. Сеть не открывается, токен не нужен.

Живое чтение читает `tds/internal/bridge/.env`:

- `KEITARO_BASE_URL` — адрес трекера без `/admin_api`
- `KEITARO_API_KEY` — ключ Admin API
- `EMTDS_ADMIN_URL` — локальная админка, по умолчанию `http://127.0.0.1:8090`
- `EMTDS_ADMIN_USER` — логин локальной админки
- `EMTDS_ADMIN_PASSWORD` — пароль локальной админки

Пустой ключ или адрес останавливает `--live` до сети.

## Запуск

Из каталога `tds/internal/bridge`:

```text
go run ./cmd/kt-import
go run ./cmd/kt-import --apply
go run ./cmd/kt-import --live --apply
```

`--apply` логинится в локальную админку, сливает группы и делает один `PUT /api/groups`. Затем пишет каталоги по одной записи: сети, источники, домены, лендинги, офферы. Новый id уходит `POST`, id из манифеста этого прогона, который уже есть в админке, уходит `PUT`. `--live` без `--apply` только печатает JSON и отчёт.

Одноразовый контейнер, без перезапуска:

```text
docker compose -f deploy/docker-compose.yml run --rm --no-deps kt-import
```

## Выход

JSON групп, каталогов и отчёта: перенесено, выключено, пропущено, приближено. В результате есть `manifest`: id групп, офферов, лендингов, сетей, источников, доменов и имена файлов `lists` и `pages`. Query-параметры URL в отчёте заменены на `***`.

Id каталога — числовой id Keitaro строкой: оффер 796, лендинг 2, сеть 12, источник 3, домен 47. Кампания становится группой с id равным alias. Пустой alias даёт missing-alias-N. Занятый alias получает суффикс -dup- и id кампании. Имя группы — имя кампании Keitaro. Номер num — id кампании. Поток называется как в Keitaro; пустое имя становится stream и id потока. В comment остаётся keitaro_stream_id=N. Строка отчёта о потоке ссылается на stream и id, о лендинге — на landing и id, дальше так же для оффера, сети, источника и домена.

Слияние заменяет запись с тем же id, только если этот id есть в манифесте. Локальная запись с тем же id остаётся, в отчёт пишется конфликт «id занят локальной записью». Если номер импортированной группы совпал с номером локальной группы, которой нет в манифесте, импорту выдаётся следующий свободный номер и строка «номер N занят, выдан M». Пустой номер по-прежнему дописывается после максимального уже заданного. Повторная замена сохраняет прежний номер, если новый пришёл нулём. Вычищение убирает только id из манифеста и номера не пересчитывает.

Кампания типа weight остаётся включённой, у группы `weight: true`. `filter_or` остаётся одним потоком. Доли офферов и лендингов пишутся числовыми id.

Локальный лендинг попадает в каталог с `local: true`, пустым `url` и пустым `entry`. Поток, в котором есть такой лендинг, остаётся включённым: `redirect` равен `landing`, доли лендингов в `landings`, доли офферов в `offers`, `out` пустой. `LocalLandingIDs` возвращает числовые id этих лендингов, чтобы админка скачала архивы. Локальный оффер по-прежнему выключает поток. Лендинг только с URL остаётся прежним редиректом.

Живое чтение: GET тела до 64 МБ, POST журнала до 32 МБ. `PUT /api/groups` по-прежнему до 8 МБ. Группы читаются тремя запросами `/admin_api/v1/groups?type=campaigns`, `offers` и `landings`. Потоки кампаний читаются пулом из 8. Журналы листаются по 10000 строк. Смещение растёт на число полученных строк. Сортировка кликов — `datetime`, конверсий — `postback_datetime`, обе по возрастанию. Чтение останавливается на пустой странице или когда смещение дошло до `total`. Если `total` нет или он 0, останавливает короткая страница. Две одинаковые страницы подряд дают ошибку «журнал не двигается». Колонки `payout` у конверсий нет: берутся `revenue` и `cost`, страна — `country_code`. У кликов `is_bot` и `is_unique_campaign` приходят булевыми. Имена стран оффера переводятся в ISO2, в том числе Polynesie Francaise → PF, Guyane → GF, Territory of the French Southern and Antarctic Lands → TF. `status404`, `404` и `404_not_found` становятся `404_not_found` с пустым `out`: текст payload не переносится. `show_html` и `html` остаются `show_page_html`. Неизвестный `action_type` остаётся включённым потоком `stop` и пишется в отчёт как приближение. `campaign` становится редиректом `group`, в `out` — id группы цели (её alias). Пустой payload даёт «целевая кампания не задана». Неизвестная цель остаётся `stop` и строкой «целевая кампания N не найдена».

Текст `show_page_html`, `show_html_404`, `show_text` и `javascript` длиннее 512 байт после замены макросов уходит в `pages`: имя `page-` и 12 hex sha1, суффикс `.html`, в `out` пишется `@page:` и это имя. Одинаковые страницы делят один файл. Короткий текст остаётся в `out`.

Фильтр `ip` становится `ip_list`: файл `ip-` и 12 hex sha1 текста, суффикс `.dat`, содержимое в `lists`. Одинаковые списки делят один файл. Негодный адрес отбрасывается, в отчёт попадает одна строка и не больше трёх примеров. `isp` становится `org`. `asn` переносит только номера. `device_model` становится правилом `model` с точным совпадением и потерей `approximated` («словарь моделей Keitaro отличается от токена UA»), `sub_id_1`…`sub_id_30` — правилом `sub_ids` с ключом `sub_id_N`: точное совпадение, а режим подстроки и регулярка из одних литералов (`/Fonbet|Bovada/`) — «содержит» (`contains: true`); сложная регулярка (классы, квантификаторы, якоря, группы) и пустой список значений не переносятся и попадают в отчёт. Поле `empty` правила `sub_ids` импорт не задаёт. Два фильтра одного Sub ID или два `parameter` склеиваются только без смены смысла (два reject при «все условия», два accept при `filter_or`), иначе второй пропускается с отчётом. `proxy`, `ipv4`, `ipv6`, `ipv_4`, `ipv_6` и `ip_version` пропускаются, поток из-за них не выключается. Неизвестное `{name}` остаётся в строке и в отчёт не пишется. `offer_param` из одного токена пишется в `offer_param`, остальное — в `offer_query` без ведущих `?` и `&`. Ссылки офферов и лендингов с одним URL склеиваются, доли складываются.

## Ошибки

- Пустой `KEITARO_API_KEY` или `KEITARO_BASE_URL` при `--live`.
- Метод не GET или путь вне allowlist — запрос не отправляется. Исключение: два POST журнала и GET архива лендинга.
- Ответ не JSON-массив — импорт останавливается, частичная запись не делается. Архив лендинга JSON-массивом не считается.
- Запись с тем же id, которого нет в манифесте, не перезаписывается.
- Цепочка `group → group` глубже 3 или тело больше 8 МБ — запись отменяется.
- Локальная админка ответила не 200.
